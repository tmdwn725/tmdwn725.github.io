## 엔진 위의 제품과 조건 3개

[개인 에이전트를 올리려고 설계한 서비스 구조](/posts/service-architecture-designed-for-a-personal-agent/)에서는 게이트웨이 아래를 정했다. 모델 호출이 모두 llm-hub 한 곳을 지나고, 에이전트는 그 위에 올라간다. 이 글은 그 위쪽, 에이전트를 실행하는 엔진에 대한 이야기다.

엔진 위에 지금 올라가는 제품은 sage 하나다. 코딩 에이전트 sage_code는 두 번째 후보로 검토하고 있지만, 만들지는 아직 정하지 않았다.

| 제품 | 용도 | 지금 상태 |
|---|---|---|
| sage | 평생 쓸 개인 비서. 메모리·스킬·일정·메일·도구 68개 | 운영 중 |
| sage_code | Claude Code와 Codex를 대신할 코딩 에이전트 | 검토 중 |

조건은 3개다.

1. **멀티모델.** Claude, GPT, GLM, DeepSeek, 그리고 DGX Spark에서 직접 띄우는 오픈 모델을 한 엔진으로 돌린다. 특정 회사 제품에 묶이지 않는 나만의 작업 에이전트를 만든다
2. **라이브러리.** 제품이 엔진을 import 해서 쓴다. 엔진을 별도 프로세스로 띄워 조종하는 구조는 택하지 않는다
3. **그룹 공용 SDK의 원형.** 회사에서 여러 계열사가 쓸 에이전트 SDK의 원형으로 삼는다. 그래서 공부용 장난감이 아니라 버전과 배포까지 갖춘 패키지로 만든다

두 번째 조건은 처음부터 있던 것이 아니다. "Agent SDK"라는 이름의 제품들을 코드로 확인한 뒤에 생긴 조건이다. 그 전에 라이브러리와 SDK라는 두 단어부터 정리한다. 제품들을 비교할 때 둘이 계속 섞여 쓰이기 때문이다.

## 라이브러리와 SDK의 차이

두 단어는 기준이 다르다. 라이브러리는 **코드를 쓰는 방식**, SDK는 **무엇을 위해 묶었는지**를 가리킨다. 그래서 한 패키지가 라이브러리이면서 SDK일 수 있다.

| 용어 | 뜻 | 호출하는 쪽 | 예 |
|---|---|---|---|
| 라이브러리 | 앱이 import 해서 부르는 함수·클래스 묶음 | 앱 | `requests`, `pydantic` |
| 프레임워크 | 앱 코드를 끼워 넣을 자리를 정해 두고 자기가 부르는 틀 | 프레임워크 | FastAPI, LangGraph |
| SDK | 특정 플랫폼·서비스를 쓰게 하려고 만든 묶음. 클라이언트 라이브러리에 타입, 인증, 재시도, 문서, 예제, 때로는 CLI까지 | 대개 앱 | `anthropic`, `openai`, AWS `boto3` |

라이브러리와 프레임워크를 가르는 것은 제어권이다. 라이브러리는 앱이 부르고, 프레임워크는 앱을 부른다. SDK는 이 축과 상관이 없다. "이 서비스를 쓰는 데 필요한 것을 한 번에 준다"는 목적으로 붙는 이름이다. 그래서 SDK라는 이름만으로는 그 안에 엔진이 들어 있는지, 다른 곳에서 도는 엔진에 붙는 클라이언트인지 알 수 없다.

### 모델 호출 스택의 층

실제 제품에서 이 단어들이 어느 층에 붙는지 보면 구분이 쉬워진다. 모델을 한 번 부르는 경로를 아래에서 위로 적었다.

| 층 | 무엇 | 성격 |
|---|---|---|
| 1 | 모델 회사의 HTTP API (`/v1/messages`, `/v1/responses`) | 규격 |
| 2 | 모델 회사의 공식 SDK (`anthropic`, `openai`) | HTTP API 클라이언트. 라이브러리이자 SDK |
| 3 | 여러 회사를 한 모양으로 묶는 층 (LangChain 모델 클래스, LiteLLM) | 회사별 형식을 한 모양으로 맞추는 변환 층 |
| 4 | 에이전트 엔진 (루프, 도구 실행, 승인, 압축) | 라이브러리 또는 별도 프로세스 |
| 5 | 앱 (Claude Code, Codex CLI, sage) | 제품 |

2층의 공식 SDK는 사람이 직접 구현한 코드가 적다. Anthropic과 OpenAI의 Python SDK 저장소 `CONTRIBUTING.md`에는 똑같이 "Most of the SDK is generated code"라고 적혀 있다. 타입과 요청 함수는 생성기가 만들고, 사람이 고친 부분은 다음 생성 때도 유지되는 방식이다. API가 바뀌면 SDK를 다시 생성해 새 버전을 낸다. 그래서 2층 SDK는 API를 따라가는 속도가 빠르다.

3층은 반대로 사람이 관리한다. 회사마다 다른 요청·응답 형식을 한 모양으로 맞추는 것이 이 층의 일이라, 새 기능이 나오면 매번 누군가 변환 코드를 고쳐야 한다. 이 층이 공식 SDK보다 늦게 따라가는 이유가 여기에 있다. 이 저장소에서는 이 역할을 코드 안의 라이브러리가 아니라 게이트웨이 서버(llm-hub)가 맡는다. 여러 서비스가 같은 변환을 한 곳에서 쓰게 하려는 선택이다.

**"Agent SDK"는 4층에 붙은 이름인데, 제품에 따라 4층 엔진 자체이기도 하고 따로 도는 4층 엔진에 붙는 클라이언트이기도 하다.** 다음 절은 이 차이를 코드로 확인한 결과다.

## "Agent SDK"라는 이름의 뜻 2가지

같은 이름을 달고 있어도 하는 일이 다르다. 네 제품의 SDK가 무엇을 하는지 확인했다.

| 제품 | SDK가 하는 일 | 엔진 코드 공개 |
|---|---|---|
| Claude Agent SDK | 패키지는 약 1만 3천 줄. Claude Code CLI를 하위 프로세스로 띄우고 제어 프로토콜로 대화한다 | 비공개 (패키지만 MIT) |
| Codex SDK | Python SDK는 `codex app-server`를, TypeScript SDK는 `codex exec`를 하위 프로세스로 띄운다 | 공개 (Apache-2.0) |
| opencode | 엔진을 HTTP 서버로 띄우고, SDK는 `openapi.json`에서 생성한 클라이언트다 | 공개 (MIT) |
| Pi | `agent-core`가 엔진 자체다. 핵심 루프는 약 2천 줄이다. 앱이 엔진을 직접 import 한다 | 공개 |

**넷 중 셋은 SDK가 별도 프로세스로 도는 엔진에 붙는 클라이언트이고, Pi 하나만 SDK가 엔진 자체다.** 이 글에서는 앞의 셋을 프로세스 분리형(out-of-process), Pi를 라이브러리형(in-process)이라고 부른다.

### 프로세스 분리형 3개의 통신 방식

Claude Agent SDK의 핵심은 `_internal/transport/subprocess_cli.py`(v0.2.162 기준 1,228줄)다. 옵션 49개 중 30여 개를 CLI 플래그로 바꿔 CLI를 띄우고, 훅·권한 콜백·서브에이전트 같은 나머지는 시작 직후 제어 메시지로 넘긴다. 그 뒤로는 표준 입출력으로 메시지를 양방향으로 주고받는다. 패키지 안에 CLI 실행 파일이 함께 들어 있어서, SDK는 먼저 그 동봉 CLI를 찾고 없을 때만 설치된 `claude`를 쓴다. SDK를 설치하면 엔진도 같이 설치되는 구조다. 루프, 컨텍스트 압축, 프롬프트 캐싱은 전부 그 CLI 안에서 일어나고, CLI의 소스는 공개되지 않았다.

Anthropic 문서는 Agent SDK가 "Claude Code를 움직이는 것과 같은 도구, 에이전트 루프, 컨텍스트 관리"를 준다고 설명한다. 이 문장의 SDK는 1만 3천 줄짜리 패키지가 아니라 그 안에서 도는 엔진을 가리킨다. 같은 이름이 패키지와 엔진 두 가지 뜻으로 쓰여서 헷갈리기 쉽다. Cowork에 대해서는 도움말 센터가 "Claude Code를 움직이는 것과 같은 에이전트 구조"를 쓴다고만 적었다. Cowork가 Agent SDK 패키지를 쓰는지, 엔진을 어떤 방식으로 띄우는지는 공개된 코드가 없어 확인하지 못했다.

Codex는 엔진이 공개돼 있지만 SDK의 모양은 같다. 엔진을 프로세스로 띄우고 규격으로 대화한다. OpenAI가 만든 터미널 화면조차 엔진을 직접 부르지 않고 app-server를 거친다. 터미널 화면은 app-server를 같은 프로세스 안에 띄운다는 차이가 있을 뿐, 화면과 SDK가 같은 인터페이스를 쓴다.

opencode는 그 통로가 HTTP다. 엔진이 Effect의 HttpApi로 HTTP 서버를 띄우고, 터미널·데스크톱·웹 화면과 SDK가 모두 그 서버에 붙는다. SDK는 서버 규격에서 생성되므로 사람이 직접 구현한 코드가 거의 없다.

셋의 공통점은 엔진이 하나이고 그 엔진에 붙는 클라이언트가 여럿이라는 것이다. 이 구조에서 SDK를 만든다는 말은 엔진에 붙는 클라이언트를 만든다는 뜻이고, 클라이언트는 엔진이 있어야 쓸모가 있다.

### 프로세스 분리형과 라이브러리형 비교

| | 프로세스 분리형 (Claude·Codex·opencode) | 라이브러리형 (Pi) |
|---|---|---|
| 엔진 위치 | 별도 프로세스·서버 | 앱과 같은 프로세스 |
| 앱과의 통로 | 표준 입출력, JSON-RPC, HTTP | 함수 호출 |
| 여러 언어 지원 | 규격만 있으면 얇은 클라이언트로 가능 | 엔진과 같은 언어만 |
| 엔진을 고치려면 | 엔진 저장소를 고쳐야 한다(Claude는 불가) | 앱과 같은 방식으로 고친다 |
| 엔진 장애 | 프로세스가 분리돼 앱과 격리 | 앱도 같이 멈춘다 |

프로세스 분리형이 나쁜 것은 아니다. 엔진을 한 곳에서 다듬고 여러 언어의 얇은 클라이언트로 여는 데 유리하다. 그룹 SDK도 결국은 이 모양이 필요하다. 회사의 Java 팀이 Python 엔진을 쓰려면 엔진 서버와 규격이 있어야 한다. Pi도 라이브러리형 엔진과 별도로 `pi-protocol`, `pi-server`, `pi-client`라는 원격 접속용 패키지를 두었다.

문제는 순서다. 원격 인터페이스는 엔진이 생긴 다음에 만든다. 멀티모델 조건 때문에 엔진은 남의 것을 빌릴 수 없다. Claude Code 엔진은 Claude에 맞춰져 있고 닫혀 있다. 그래서 먼저 라이브러리형 엔진을 만들고, 원격 인터페이스는 엔진을 쓰는 곳이 둘 이상 생긴 뒤에 만든다.

## 공개된 엔진의 규모

엔진이 공개된 두 제품의 규모를 2026-09-25 최신본으로 확인했다. 테스트 코드는 뺐다.

| 제품 | 버전 | 언어 | 엔진 규모 | 화면 |
|---|---|---|---|---|
| Codex | `rust-v0.157.0` | Rust | `codex-core` 약 12만 줄 | TUI, exec, app-server |
| opencode | `v1.18.32` | TypeScript | `opencode` + `core` 약 11만 줄 | TUI, 데스크톱, 웹, Slack, 에디터 |

둘 다 10만 줄을 넘고, 둘 다 루프를 직접 구현했다. 밖에서 빌려 쓰는 것은 "모델에 한 번 묻고 답 받기" 정도다. opencode는 그마저 빌려 쓰던 AI SDK를 자체 코드로 바꾸는 중이다. 두 제품 모두 엔진을 외부 라이브러리에 맡기지 않았다.

두 엔진은 투자한 방향이 다르다. Codex는 안전장치에 더 투자했다. `codex-rs/sandboxing/` 아래에 Linux `bwrap`·`landlock`, macOS `seatbelt`, Windows 샌드박스가 있어 명령을 운영체제 수준에서 격리한다. 파일 편집에는 `apply_patch`라는 GPT용 형식을 도구로 둔다. opencode는 유연함과 확장에 더 투자했다. 화면이 다섯 가지이고, 플러그인으로 에이전트·훅·프롬프트를 교체할 수 있다. 엔진은 그대로 두고 플러그인만으로 하네스를 튜닝한 `oh-my-opencode` 같은 프로젝트도 있다.

이 규모는 통째로 가져오기 어렵다는 뜻이기도 하다. Codex는 Rust로 작성돼 있다. opencode는 데스크톱·웹 제품까지 한 저장소에 들어 있다. 둘 다 라이선스상 코드를 가져다 쓸 수는 있다(Apache 코드는 저작권 고지와 NOTICE를 유지해야 한다). 하지만 그룹 SDK에 필요한 것은 엔진 층이지 제품 전체가 아니다.

## 루프 구조의 공통점과 튜닝 차이

[Hermes Agent와 OpenClaw를 비교한 글](/posts/hermes-agent-vs-openclaw/)을 쓸 때 보인 경향이 이번에도 그대로였다. 루프, 도구 실행, 세션, 승인의 뼈대는 제품마다 거의 같은 모양이다.

- 모델을 부른다
- 도구 호출이 있으면 실행하고 결과를 붙여 다시 부른다
- 없으면 끝낸다
- 그 사이에 승인, 반복 감지, 컨텍스트 압축, 재시도를 끼운다

차이는 뼈대가 아니라 튜닝에서 난다. 시스템 프롬프트, 도구 설명, 압축 시점, 재시도 규칙 같은 값이다. LangChain은 모델(`gpt-5.2-codex`)을 그대로 두고 하네스만 바꿔 Terminal Bench 2.0 점수를 52.8%에서 66.5%로 올렸다고 공개했다. 같은 모델, 같은 뼈대에서 튜닝만으로 13.7%p 차이가 났다.

opencode 최신본을 열어 보면 이 튜닝이 코드로 드러난다. 모델 계열마다 다른 시스템 프롬프트 파일을 고르고, 파일 편집 도구도 GPT 계열에는 `apply_patch` 형식을 준다. 그런데 **GLM과 DeepSeek에는 전용 프롬프트가 없다.** 이 둘은 `default.txt`를 받는다.

이 부분이 멀티모델 엔진을 직접 만드는 주된 이유다. 첫 번째 조건에 적은 GLM·DeepSeek는 공개 엔진에서도 아직 튜닝되지 않은 모델이다. 엔진 코드를 직접 관리해야 모델마다 프롬프트, 도구 형식, 재시도 규칙을 바꿔 가며 측정할 수 있다. "모델이 성능을 정한다"는 말은 맞지만, 구체적으로는 모델마다 맞는 프롬프트와 도구 형식이 다르다는 뜻이다. 그 차이를 다루는 곳이 엔진이다.

## sage가 이미 가진 것

엔진을 새로 만들지 않고 sage에서 분리하는 방법을 검토할 수 있었던 것은 sage가 비서 수준에서 필요한 것을 대부분 갖고 있었기 때문이다.

| 항목 | 지금 모습 |
|---|---|
| 도구 | 68개. 끌 수 없는 것 28개, 사용자가 끌 수 있는 것 40개. 이름은 대부분 `도메인.동사` 규칙(`calendar.create`, `web.search`) |
| 승인 | 도구마다 읽기·쓰기 성질을 선언하고, 쓰기 도구는 규칙 24개로 확인과 거부를 가르고, 규칙에 없는 쓰기는 통과한다. `bash.exec`·`email.send`는 거부, 시트 편집은 사용자에게 확인 |
| 외부 도구 | DB에 등록한 MCP 서버를 사용자별 자격증명으로 붙인다 |
| 반복 방지 | 같은 도구를 같은 인자로 여러 턴에 걸쳐 반복하면 막는다. 작은 모델이 같은 검색을 되풀이하던 문제에서 나왔다 |
| 스트리밍 재개 | 답변이 스트리밍되는 도중 새로고침해도 Redis 버퍼에서 이어 받는다. 턴은 연결과 별개로 백그라운드에서 끝까지 실행된다 |
| 멀티유저 | Keycloak 로그인, 사용자별 메모리 저장소와 자격증명 |

권한 규칙을 어떻게 정했는지는 [에이전트에 도구를 붙이며 정한 권한 계약](/posts/the-tool-permission-contract-i-settled-on-for-my-agent/)에 적었다. 이 표의 대부분은 엔진으로 가지 않는다. 도구 68개와 승인 규칙 24개는 sage의 것이다. 엔진으로 가는 것은 이것들을 돌리는 틀, 즉 도구를 실행하는 순서와 승인을 요청하는 시점이다.

## 선택지 3개

| 선택지 | 장점 | 단점 |
|---|---|---|
| 공개 엔진 포크 (Codex·opencode) | 완성된 엔진을 바로 쓴다 | 10만 줄 이상을 유지보수해야 한다. 언어와 제품 구조가 그룹 SDK와 맞지 않는다 |
| 프로세스 분리형 SDK 위에 제품 | 만들 것이 가장 적다 | 엔진을 고칠 수 없다. 멀티모델 조건을 못 지킨다 |
| **운영 코드에서 엔진을 분리해 라이브러리로** | 운영 중인 루프·도구·승인이 이미 있다. 엔진을 직접 관리한다 | 엔진과 제품의 경계를 새로 정해야 한다. 옮기다 운영을 깨뜨릴 위험이 있다 |

세 번째를 골랐다. sage는 이미 운영 중이고, 루프·도구 실행·승인·스트리밍 재개가 몇 달 동안 실제 대화로 다듬어져 있다. 공개 엔진 둘은 가져오지 않고 설계를 참고하는 용도로 쓴다. 두 엔진이 루프, 압축, 재개를 왜 그렇게 구현했는지가 경계를 정하는 기준이 된다.

## 공개 엔진에서 참고하는 것

가져오지는 않지만 각 엔진에서 배울 것은 분명하다.

| 참고할 곳 | 가져올 설계 |
|---|---|
| Pi | 엔진을 라이브러리로 두고 원격 접속용 패키지(`pi-protocol`·`pi-server`·`pi-client`)는 따로 두는 구조. 핵심 루프가 약 2천 줄이라 한 번에 읽을 수 있다 |
| opencode | 모델 계열별 프롬프트·편집 도구 선택, 메시지를 part 목록으로 담는 모양, 루프 한가운데(`session/prompt.ts`의 `while (true)`)에 압축·단계 제한을 끼우는 방식 |
| Codex | 운영체제 수준 샌드박스, GPT용 편집 형식(`apply_patch`), 화면과 SDK가 같은 인터페이스(app-server)를 쓰게 한 구조 |

셋을 읽는 순서도 정했다. Pi로 루프의 최소 모양을 보고, opencode로 실제 제품이 그 루프에 무엇을 덧붙이는지 보고, Codex로 안전장치를 본다. 그룹의 여러 팀이 쓸 SDK를 설계하려면 루프, 압축, 재개가 왜 그렇게 생겼는지를 코드 없이 설명할 수 있어야 한다. 세 엔진을 읽는 목적이 그것이다.

## 엔진과 제품의 경계

sage 코드를 엔진과 제품으로 나누는 기준은 하나다. **엔진은 설정 파일, DB, Redis를 모른다.** 필요한 것은 전부 포트로 주입받는다.

| 엔진으로 가는 것 | 제품에 남는 것 |
|---|---|
| 루프 (모델 호출 ↔ 도구 실행) | 한국어 넛지 문구와 판정 키워드 |
| 도구 실행 과정 (교정·반복 감지·승인 호출·결과 분류) | 도구 68개와 그 설명, 승인 규칙 |
| 대화 기록의 모양 (블록, 메시지, 실행 이벤트) | 세션 저장소, 사용자별 격리 |
| 셸·파일 실행 환경의 인터페이스 | 작업 공간 경로, 체크포인트 |
| 모델 사실을 정책으로 바꾸는 틀 | "온프레 모델은 타임아웃 길게" 같은 규칙 |

예를 들어 sage의 루프에는 모델이 "검색해보겠습니다"라고 예고만 하고 도구를 부르지 않으면 도구 호출을 다시 요청하는 장치가 있다. 판정에 쓰는 "검색", "확인", "보겠"은 한국어 키워드다. 엔진은 멈춘 턴을 판정해 다시 요청하는 틀만 갖고, 키워드와 문구는 제품이 주입한다. 다른 제품이 생기면 그 제품에 맞는 판정을 주입하면 된다.

엔진 이름은 `agent_sdk`로 했다. 처음 붙인 이름 `sage_core`는 제품 이름이 엔진 이름에 들어 있어서 바꿨다. 이 엔진은 sage의 것이 아니라 sage 말고 다른 제품도 올릴 수 있는 틀이다.

지금 모양만 보면 `agent_sdk`는 라이브러리다. 그래도 이름에 SDK를 붙인 것은 목적 때문이다. 버전과 배포 정책, 문서, 나중에 붙일 엔진 서버와 다른 언어 클라이언트까지 한 묶음으로 내놓는 것이 목표이고, 앞에서 정리한 SDK의 뜻이 바로 그것이다. 라이브러리로 시작해서 원격 인터페이스를 더해 SDK로 넓혀 가는 순서다.

## 이전 단계 8개와 병행 트랙

엔진은 한 번에 옮기지 않는다. 운영 중인 sage를 매 단계 그대로 돌게 하면서 조금씩 옮긴다. 단계마다 따로 배포할 수 있어야 한다는 것이 규칙이다.

| 단계 | 내용 |
|---|---|
| S0 | 대화 기록을 블록 배열 모양으로 바꾸고 운영 이력 2,219행을 변환 |
| S1 | 엔진 골격과 기존 루프의 특성 테스트 44개 |
| S2 | 상태가 없는 순수 모듈 6개 이동 |
| S3 | 도구 실행 과정 |
| S4 | 루프 |
| S5 | 셸·파일 실행 환경, 실행 이벤트 저장소, 트레이서 |
| S6 | 모델 프로필 |
| S7 | 실행 이벤트를 DB 정본으로 |

지금은 S6까지 끝났고 S7이 남았다.

S1이 먼저 특성 테스트인 이유는 옮기는 동안 동작이 바뀌면 바로 알아야 하기 때문이다. 테스트가 없던 루프에 지금 동작을 그대로 고정하는 테스트를 먼저 깔고, 옮긴 뒤에도 기대값을 고치지 않고 통과하는 것을 완료 기준으로 삼았다.

엔진은 처음에 sage 저장소 안의 `agent_sdk/` 폴더에서 개발했다. 엔진이 제품 코드(`app` 패키지)를 한 줄도 import 하지 못하게 막는 테스트를 두어, 언제든 폴더째 분리할 수 있는 상태로 유지했다. S5를 마친 뒤 실제로 폴더째 옮겨 독립 저장소 `agent-sdk`로 분리했고, sage는 git 태그로 받아 쓴다. 지금은 SDK 쪽에 표준 라이브러리만 import 한다는 더 좁은 경계 테스트를 둔다. 분리 과정은 뒤의 글에서 다룬다.

엔진 로드맵 옆에는 평가 트랙 하나와 검토 중인 후보 하나가 있다.

| 트랙 | 내용 | 끝났다는 기준 |
|---|---|---|
| agent-eval | 과제 스냅샷, 채점 환경 분리, Docker 격리, 에이전트 어댑터(Claude Code·Codex·opencode) | 과제 11개 검증, 기준선 점수 확보 |
| sage_code v0 | 도구 7개, 헤드리스 실행, 최소한의 터미널 화면 | agent-eval에서 Pi·opencode와 같은 과제로 점수 비교 |

그 뒤가 멀티모델 프로필(GLM·DeepSeek 전용 프로필이 기본 프로필보다 높은 점수)과 SDK화(엔진 서버, JSON-RPC 규격, Java 클라이언트, 버전 정책)다.

하지 않기로 한 것도 적어 둔다. 터미널 화면부터 다듬기, 엔진 서버를 먼저 만들기, 공개 엔진 통째로 포크하기, 측정 없이 프롬프트 고치기. 4가지 모두 눈에 보이는 결과가 빨리 나오지만, 엔진이 없거나 측정이 없는 상태에서는 고친 것이 나아졌는지 알 수 없다.

## 결론

에이전트 엔진을 직접 만들기로 했다. 프로세스 분리형 SDK는 엔진을 고칠 수 없고, 공개 엔진은 통째로 가져오기엔 크고 제품 코드와 한 저장소에 섞여 있다. 운영 중인 비서 코드에서 엔진을 분리해 라이브러리로 만든다.

판단의 근거는 두 가지다. 루프 뼈대는 제품마다 거의 같은 모양이라 직접 구현하는 비용이 크지 않다. 반면 모델별 튜닝은 엔진 코드를 직접 관리해야만 할 수 있고, GLM·DeepSeek처럼 공개 엔진에서도 튜닝되지 않은 모델이 있다.

걱정되는 부분도 있다. 엔진을 직접 만든다는 것은 Codex와 opencode가 10만 줄 넘게 쌓은 것을 내가 다시 만들어야 한다는 뜻이다. 운영체제 수준 샌드박스, 정교한 승인, 압축, 스트리밍 재개 같은 것들이다. sage에 있는 것은 개인 비서 수준이지 코딩 에이전트 수준이 아니다. 그리고 코딩 에이전트의 성능 상한은 결국 모델이 정한다. 활성 파라미터 3B급 온프레 모델로 Claude Code를 대체하기는 어렵고, 매일 쓰려면 Claude나 GPT를 붙여야 한다. sage_code를 만들지 정하지 못한 이유도 여기에 있다. 엔진은 sage만으로도 필요하지만, 코딩 에이전트는 agent-eval 기준선을 보고 판단한다.

## 아직 확인 못 한 것

- **튜닝 효과의 크기.** GLM·DeepSeek 전용 프로필이 opencode의 기본 프롬프트보다 실제로 나은지는 같은 과제로 측정해야 한다. 이를 위한 평가 러너(agent-eval)를 따로 만들고 있다
- **LangChain 수치의 재현.** 하네스만으로 10%p 넘게 오른다는 결과는 공개 수치를 인용한 것이다. 이 환경에서 같은 폭이 나오는지는 아직 모른다
- **opencode의 샌드박스.** Codex의 운영체제 수준 샌드박스에 해당하는 것을 opencode 예전 버전에서는 찾지 못했다. 최신본에서 달라졌는지는 확인하지 않았다
- **구독 경로의 지속성.** 지금 GPT는 ChatGPT 구독 경로로 쓴다. 자체 도구에서 이 경로를 계속 쓸 수 있는지는 정책을 확인해야 한다

다음 글은 S0에서 정한 대화 기록의 모양이다. 업계의 API 형식 6가지를 같은 대화로 적어 비교하고, 메시지가 아니라 실행 이벤트를 정본으로 두기로 한 이유를 적는다.
