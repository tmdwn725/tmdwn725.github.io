## 에이전트 SDK가 하는 일

[개인 에이전트를 올리려고 설계한 서비스 구조](/posts/service-architecture-designed-for-a-personal-agent/)에서는 모델 호출이 모두 llm-hub 한 곳을 지나도록 정했다. 이 글은 그 위쪽, 모델 호출을 묶어 에이전트로 만드는 층에 대한 이야기다.

모델 API가 하는 일은 단순하다. 대화를 보내면 답을 하나 돌려준다. 답 안에 "이 도구를 이런 인자로 불러 달라"는 요청이 들어 있어도, 그 도구를 실제로 실행하는 것은 API를 부른 쪽의 일이다.

에이전트는 그 실행을 맡아서 모델 호출 여러 번을 하나의 작업으로 이어 붙인다. 모델이 도구를 요청하면 실행하고, 결과를 대화에 넣어 모델에게 다시 넘긴다. 모델이 도구 요청 없이 답만 내면 작업이 끝난다. 이 흐름을 에이전트 루프라고 부른다.

루프 자체는 몇십 줄이면 짤 수 있다. 실제로 쓰려면 그 사이에 끼워야 하는 장치가 많다.

| 기능 | 없으면 생기는 일 |
|---|---|
| 반복 횟수 제한 | 모델이 끝내지 않으면 호출과 비용이 계속 쌓인다 |
| 도구 인자 교정 | 작은 모델이 숫자를 문자열(`"42"`)로 보내는 식의 흔한 실수로 도구가 실패한다 |
| 승인 | 메일 발송이나 셸 명령 같은 위험한 도구가 확인 없이 실행된다 |
| 반복 감지 | 모델이 같은 도구를 같은 인자로 되풀이하며 헤맨다 |
| 재시도 | 일시적인 오류 하나로 턴 전체가 실패한다 |
| 중단 | 사용자가 멈춰도 서버는 끝까지 돈다 |
| 컨텍스트 초과 처리 | 대화가 길어지면 모델 호출 자체가 거부된다 |
| 실행 기록 | 무엇을 왜 실행했는지 나중에 확인할 수 없다 |
| 실행 환경 | 도구가 작업 폴더 밖의 파일을 건드린다 |

**에이전트 SDK는 이 루프와 그 사이에 끼우는 장치를 묶은 것이다.** 이 층을 하네스라고도 부른다.

개인 비서 sage는 이 기능을 거의 다 갖고 있었다. 다만 전부 앱 코드 안에 섞여 있었다. 예를 들어 루프 한가운데에 "검색해보겠습니다" 같은 한국어 예고 문장을 판정하는 키워드가 들어 있었다. 이대로는 sage 말고 다른 곳에서 이 루프를 쓸 수 없다.

## 엔진을 따로 떼어 내는 이유

이 층을 앱에서 떼어 내는 이유는 하나다. 제품마다 다시 만들지 않기 위해서다.

모델 회사들도 같은 판단을 했다. Anthropic의 Claude Agent SDK는 Claude Code를 움직이는 엔진을 다른 개발자가 쓸 수 있게 연 것이다. 문서는 Agent SDK가 "Claude Code를 움직이는 것과 같은 도구, 에이전트 루프, 컨텍스트 관리"를 준다고 설명한다. OpenAI의 Codex SDK도 Codex 엔진을 연다. 자기 제품을 만들면서 다듬은 엔진을 SDK로 내놓은 것이다.

내 쪽에서도 이 엔진을 쓸 곳이 sage 하나로 끝나지 않는다. 코딩 에이전트 sage_code를 검토하고 있고, 회사에서는 여러 계열사가 쓸 에이전트 SDK의 원형이 필요하다. 엔진이 sage 안에 섞여 있으면 둘 다 sage 코드를 복사해서 시작해야 한다.

## 기존 SDK를 쓰지 않는 이유

공개된 엔진이 있으면 가져다 쓰면 된다. 쓰지 않은 이유는 세 가지다.

### 엔진이 앱 밖에서 돈다

"Agent SDK"라는 이름을 단 네 제품을 코드로 확인했다.

| 제품 | SDK가 하는 일 | 엔진 코드 |
|---|---|---|
| Claude Agent SDK | Claude Code CLI를 별도 프로세스로 띄우고 표준 입출력으로 대화한다 | 비공개 |
| Codex SDK | `codex app-server`나 `codex exec`를 별도 프로세스로 띄운다 | 공개 (Apache-2.0) |
| opencode | 엔진을 HTTP 서버로 띄우고, SDK는 그 서버의 클라이언트다 | 공개 (MIT) |
| Pi | 앱이 엔진(`agent-core`)을 직접 import 한다 | 공개 (MIT) |

넷 중 셋은 엔진이 앱과 다른 프로그램으로 돈다. 에이전트에게 폴더 정리를 시켰을 때 떠 있는 프로세스로 보면 차이가 보인다.

```text
라이브러리형 (Pi)
python (내 앱)        <- 엔진이 앱 안에 import 돼 같이 돈다
 └─ bash: mv ...      <- 엔진이 시킨 명령

프로세스 분리형 (Claude Agent SDK)
python (내 앱)        <- SDK는 메시지만 주고받는다
 └─ claude (CLI)      <- 엔진은 별도 프로그램
     └─ bash: mv ...
```

프로세스 분리형은 엔진 하나에 터미널, 데스크톱 앱, 여러 언어의 SDK를 붙이기 좋다. 대신 쓰는 쪽은 엔진에 메시지를 보낼 수만 있고 엔진 안의 동작은 바꿀 수 없다. Claude Code는 엔진 코드가 공개되지 않아 고칠 방법도 없다.

### 모델마다 맞춰야 할 것이 다르다

루프의 뼈대는 제품마다 거의 같다. 차이는 시스템 프롬프트, 도구 설명, 도구 형식, 재시도 규칙 같은 튜닝에서 난다. LangChain은 모델(`gpt-5.2-codex`)을 그대로 두고 하네스만 바꿔 Terminal Bench 2.0 점수를 52.8%에서 66.5%로 올렸다고 공개했다.

opencode 코드에서 이 튜닝이 보인다. 모델 계열마다 다른 시스템 프롬프트 파일을 고르고, GPT 계열에는 `apply_patch`라는 편집 도구를 준다. 그런데 **GLM과 DeepSeek에는 전용 프롬프트가 없다.** 둘은 `default.txt`를 받는다.

나는 Claude, GPT, GLM, DeepSeek, 그리고 DGX Spark에서 직접 띄우는 오픈 모델을 한 엔진으로 돌려야 한다. 공개 엔진에서도 튜닝되지 않은 모델이 섞여 있으니, 모델마다 프롬프트와 도구 형식을 바꿔 가며 측정하려면 엔진 코드를 직접 관리해야 한다. 특정 회사 제품에 묶이지 않는 나만의 작업 에이전트를 만들려면 이 부분이 내 손에 있어야 한다.

### 공개 엔진은 통째로 가져오기에 크다

Codex(`rust-v0.157.0`)의 엔진 `codex-core`는 테스트를 빼고 약 12만 줄이고, opencode(`v1.18.32`)는 약 11만 줄이다. Codex는 Rust로 작성돼 있고, opencode는 데스크톱·웹 제품까지 한 저장소에 들어 있다. 필요한 것은 엔진 층인데, 가져오면 제품 전체를 함께 유지보수해야 한다.

그래서 코드는 가져오지 않고 설계만 참고한다. Codex에서는 운영체제 수준 샌드박스(Linux `bwrap`·`landlock`, macOS `seatbelt`, Windows 샌드박스)를, opencode에서는 모델별 프롬프트 선택과 플러그인 구조를, Pi에서는 엔진을 라이브러리로 두고 원격 접속 패키지(`pi-server`, `pi-client`)를 따로 두는 구조를 본다.

## 내 agent-sdk의 역할

엔진은 운영 중인 sage에서 분리해 `agent-sdk`라는 이름으로 만들었다. 엔진과 제품을 나누는 기준은 하나다. **엔진은 설정 파일, DB, Redis를 모른다.** 필요한 것은 전부 밖에서 주입받는다.

| 엔진 (agent-sdk) | 제품 (sage) |
|---|---|
| 루프, 반복 횟수 제한, 재시도, 중단 | 한국어 판정 문구와 키워드 |
| 도구 실행 과정 (인자 교정, 반복 감지, 승인 요청, 결과 분류) | 도구 68개와 그 설명, 승인 규칙 |
| 메시지·블록·실행 이벤트 타입, 실행 이벤트 저장소 규격 | 세션 저장소, 사용자별 격리, 대화 압축 |
| 셸·파일 실행 환경 인터페이스 | 작업 공간 경로 |
| 모델 사실을 정책으로 바꾸는 틀 | "온프레 모델은 타임아웃 길게" 같은 규칙 |

예를 들어 sage의 모델은 가끔 "검색해보겠습니다"라고 예고만 하고 도구를 부르지 않는다. 엔진은 이렇게 멈춘 턴을 판정해 다시 요청하는 틀만 갖고, 무엇을 예고로 볼지는 sage가 주입한다. 다른 제품은 자기 판정을 주입하면 된다. 컨텍스트 초과도 같은 방식이다. 엔진은 초과를 알리고, 대화를 어떻게 줄일지는 sage가 정한다.

agent-sdk는 약 2,950줄이고, 구성 요소는 7개다.

| 구성 요소 | 역할 |
|---|---|
| `loop` | 모델 호출과 도구 실행을 번갈아 돌리는 루프, 반복 횟수 제한, 멈춘 턴 판정 |
| `tools` | 도구 레지스트리, 도구 한 건의 실행 과정, 인자 교정, 반복 감지 |
| `model` | 모델 연결 규격, 모델 프로필, 테스트용 가짜 모델 |
| `types` | 메시지, 블록, 실행 이벤트 같은 공통 타입 |
| `env` | 셸·파일을 실행하는 환경과 작업 공간 경로 검사 |
| `store` | 추가만 하는 실행 이벤트 저장소 규격과 메시지 변환 |
| `trace` | 실행 이벤트를 받아 한 턴을 요약하는 트레이서 |

sage는 이 패키지를 git 태그로 받아 import 한다. 저장소는 따로 있지만 실행할 때는 sage 프로세스 안에서 돈다. 앞의 분류로 하면 라이브러리형이다. 엔진은 한 번에 옮기지 않았다. 지금 동작을 고정하는 테스트를 먼저 만들고, 옮긴 뒤에도 그 테스트가 기대값을 고치지 않고 통과하는 것을 기준으로 조금씩 옮겼다.

`env`는 샌드박스가 들어갈 자리이기도 하다. sage의 셸·파일 도구는 지금 이 인터페이스의 로컬 구현을 거쳐 바로 실행된다. 같은 자리에 샌드박스 구현을 끼우면 엔진 코드는 그대로 두고 도구 실행만 격리할 수 있다.

서버는 아직 만들지 않는다. 같은 Python 제품끼리는 라이브러리를 import 하는 것으로 충분하다. 회사의 Java 팀처럼 다른 언어에서 써야 하거나, 에이전트 전체를 샌드박스에 넣고 밖에서 조종해야 할 때 같은 라이브러리를 서버로 감싸 연다. 이름에 SDK를 붙인 것도 그 때문이다. 버전, 문서, 서버와 다른 언어 클라이언트까지 한 묶음으로 내놓는 것이 목표다.

## 결론

에이전트 SDK는 모델 호출을 반복하며 도구를 실행하는 층이고, 이 층을 앱에서 떼어 내야 여러 제품이 같은 엔진을 쓸 수 있다. 기존 SDK는 엔진이 앱 밖에서 돌아 고칠 수 없거나, 통째로 가져오기에 너무 크다. 그래서 운영 중인 sage에서 엔진을 분리해 라이브러리로 만들었다.

판단의 근거는 두 가지다. 루프 뼈대는 제품마다 거의 같아서 직접 구현하는 비용이 크지 않다. 반면 모델별 튜닝은 엔진 코드를 직접 관리해야만 할 수 있다.

걱정되는 부분도 있다. 엔진을 직접 만든다는 것은 Codex와 opencode가 10만 줄 넘게 쌓은 것을 다시 만들어야 한다는 뜻이다. 운영체제 수준 샌드박스, 정교한 승인, 압축 같은 것들이다. sage에 있는 것은 개인 비서 수준이지 코딩 에이전트 수준이 아니다. 그리고 코딩 에이전트의 성능 상한은 결국 모델이 정한다. 온프레 모델만으로 Claude Code를 대체하기는 어렵고, 매일 쓰려면 Claude나 GPT를 붙여야 한다. sage_code를 만들지 아직 정하지 못한 이유도 여기에 있다.
