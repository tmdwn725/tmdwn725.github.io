> DGX Spark로 LLM을 직접 굴린 기록. 3편.

## 모델 파일만 있으면 안 된다

허깅페이스에서 모델을 받으면 가중치 파일과 설정 몇 개가 전부다. 그 상태로는 아무것도 못 한다.

누군가는 이 일을 해줘야 한다.

```
문장을 토큰으로 자르고
가중치를 GPU에 올리고
들어온 요청들을 어떻게 묶어 계산할지 정하고
대화 중간 상태(KV 캐시)를 메모리에 관리하고
다음 토큰을 확률에서 뽑고
그걸 HTTP API로 내보내고
```

이걸 하는 물건을 **추론 엔진** 또는 **서빙 엔진**이라고 부른다. vLLM은 스스로를 `inference and serving engine`, SGLang은 `serving framework`라고 소개한다.

**Ollama는 엄밀히 말하면 같은 층이 아니다.** 내부에서 llama.cpp가 추론을 돌리고, Ollama는 그 위에 모델 다운로드·관리와 API 서버를 얹은 도구다. 셋을 나란히 놓는 글이 흔하지만 출발점이 다르다. 하나는 **혼자 쓰기 편하게**, 둘은 **여럿에게 서빙하려고** 만들어졌다.

그 차이가 어디서 드러나는지가 이 글의 내용이다.

## 무엇을 기준으로 봤나

같은 모델 파일을 셋 다 돌릴 수 있다. 그런데 **동시 요청이 붙는 순간부터 결과가 달라진다.** 내 용도가 채팅창 하나가 아니라 에이전트였기 때문에 이 지점이 선택 기준이 됐다.

에이전트는 한 번 물어보면 한 번 답하지 않는다. 도구를 부르고, 결과를 받아 또 부르고, 그러다 답한다. 그 사이에 예약 작업이 돌고 다른 탭에 대화가 하나 더 열려 있다. 사용자가 나 하나여도 요청은 겹친다.

```
Running: 11 reqs, GPU KV cache usage: 18.2%
```

## 세 엔진 비교

| | Ollama | vLLM | SGLang |
|---|---|---|---|
| 기반 | llama.cpp | 자체 | 자체 |
| 동시 처리 | 슬롯 방식 (0.2~, 기본 1 또는 4) | 연속 배칭 | 연속 배칭 |
| KV 캐시 | 슬롯마다 컨텍스트 예약 | 공유 블록 풀 | 공유 블록 풀 |
| 프리픽스 재사용 | 제한적 | 블록 단위 해시 | 토큰 단위 라딕스 트리 |
| 툴 콜 파서 | 모델 템플릿 의존 | 모델별 파서 옵션 | 모델별 파서 옵션 |
| 설치·모델 교체 | 매우 쉬움 | 무거움 | 무거움 |
| GB10 (aarch64) | 됨 | 됨 | 진행 중 |

## 요청을 묶는 방식

**Ollama**도 동시 요청을 받는다. 0.2부터 동시성이 들어갔고 기본으로 켜져 있다. `OLLAMA_NUM_PARALLEL`로 슬롯을 몇 개 열지 정하는데, 기본값은 가용 메모리를 보고 1이나 4를 자동으로 고른다.

방식은 슬롯이다. 요청이 오면 빈 슬롯에 들어가고, 슬롯이 차면 줄을 선다. 슬롯 안에서는 각자 독립적으로 돈다.

**vLLM과 SGLang**은 매 디코딩 단계마다 지금 돌고 있는 요청들을 **한 배치로 묶어서** 계산한다. 요청이 중간에 들어오면 다음 단계부터 배치에 합류하고, 끝난 요청은 빠진다. 다른 요청이 끝나기를 기다리지 않는다.

```
슬롯 방식        요청A ████████
                요청B ████████
                요청C          ████████   ← A가 끝나야 시작

연속 배칭        요청A ████████
                요청B ██████████
                요청C   ██████████        ← 다음 단계에 합류
```

토큰 하나 만들 때 GPU는 대부분의 시간을 가중치 읽는 데 쓴다. 배치로 묶으면 **한 번 읽어서 여러 요청을 처리**하므로 그 비용이 나눠진다. 슬롯 방식은 각자 읽는다.

## 내 서버 로그가 보여준 것

```
Running:  1 reqs   생성  31 tok/s
Running:  3 reqs   생성  62 tok/s
Running:  6 reqs   생성  90 tok/s
Running: 11 reqs   생성 110 tok/s
```

**요청이 11배가 됐는데 전체 처리량이 3.5배가 됐다.**

줄을 세우는 방식이었다면 전체 처리량이 31 근처에 머물러야 한다. 앞사람이 끝나야 뒷사람이 시작하니 합쳐도 한 개일 때와 같다.

요청당 속도는 31에서 10으로 떨어졌다. 같은 GPU를 열한 개가 나눠 쓰니 당연하다. **중요한 건 전체가 늘었다는 것이고, 그게 배치가 실제로 묶였다는 뜻이다.**

셋을 같은 조건에서 재본 건 아니다. 이 숫자는 **vLLM 에서 연속 배칭이 이렇게 동작한다는 확인**이지 엔진 간 비교 측정이 아니다.

## KV 캐시를 잡는 방식

여기가 가장 크게 갈린다. 그리고 셋의 관계가 여기서 드러난다.

```
llama.cpp         컨텍스트를 연속 메모리에 예약     → Ollama가 이걸 씀
    ↓
PagedAttention    KV 캐시를 고정 블록으로 쪼갬      → vLLM 이 도입
    ↓
RadixAttention    그 위에 프리픽스 인덱스를 얹음    → SGLang
```

**PagedAttention이 푼 건 조각화다.** 대화마다 길이가 다른데 연속된 자리를 미리 잡으면, 짧은 대화는 잡아둔 자리를 남기고 긴 대화는 들어갈 자리를 못 찾는다. 남은 메모리를 합치면 충분한데 이어진 덩어리가 없어서 거절되는 상황이 생긴다.

운영체제가 물리 메모리를 페이지로 쪼개 관리하는 것과 같은 문제이고, 같은 해법을 쓴다. 이름도 거기서 왔다.

**SGLang은 PagedAttention을 버린 게 아니라 그 위에 올렸다.** 저장은 블록으로 하되 "어디까지 겹치는가"를 찾는 인덱스를 라딕스 트리로 둔 것이다.

**Ollama는 슬롯마다 컨텍스트를 통째로 예약한다.** 슬롯 4개에 컨텍스트 8192면 실제 대화가 짧아도 4×8192 분량의 자리가 잡혀 있다.

이건 추측이 아니라 [Ollama 문서에 그대로 적혀 있다](https://docs.ollama.com/faq).

```
필요 RAM 은 OLLAMA_NUM_PARALLEL × OLLAMA_CONTEXT_LENGTH 로 늘어난다
```

**동시 처리를 늘리려면 메모리를 그만큼 더 내야 한다.** 곱셈이다.

**vLLM과 SGLang은 고정 크기 블록을 풀에 만들어두고 요청마다 필요한 만큼 빌려준다.** 대화가 짧으면 블록 몇 개만 쓰고, 길어지면 더 빌린다. 끝나면 반납한다.

<pre class="mermaid">

    direction LR
    O1["슬롯 1<br/>8192 예약<br/>(실사용 400)"]
    O2["슬롯 2<br/>8192 예약<br/>(실사용 2600)"]
    O3["슬롯 3<br/>8192 예약<br/>(비어 있음)"]
  end

내 서버에서 이게 어떻게 나오는지는 [2편](/posts/vllm-kv-cache-memory-breakdown/)에 썼다. 요약하면 KV 캐시로 6.08 GiB를 잡아두고 그게 159,296 토큰이다. 요청 열한 개가 동시에 돌 때 18.2%를 썼으니 요청당 2,600 토큰 남짓이다. **슬롯 방식이었으면 컨텍스트 65,536을 열한 번 예약해야 하고, 그건 이 메모리로 불가능하다.**

## 프리픽스를 재사용하는 방식

에이전트 요청은 앞부분이 길고 매번 거의 같다. 시스템 프롬프트, 도구 정의 수십 개, 지금까지의 대화. 그게 통째로 반복된다.

<pre class="mermaid">
graph TB
  ROOT["시스템 프롬프트 + 도구 정의<br/>여러 대화가 공유"]
  ROOT --> A["대화 A 이력"]
  ROOT --> B["대화 B 이력"]
  A --> A1["A 최신 턴"]
  B --> B1["B 최신 턴"]
</pre>

이 공유되는 앞부분을 이미 계산해뒀다면 다시 계산할 이유가 없다.

**vLLM**은 블록 단위로 해시를 떠서 같은 블록이면 재사용한다. 블록 경계에 맞아떨어져야 걸린다.

**SGLang**은 캐시를 라딕스 트리에 넣는다. 토큰 열 단위로 공통 접두어를 찾으므로 블록 경계와 무관하게 더 촘촘히 맞춘다. 겹치는 비율이 높을수록 차이가 벌어진다는 보고들이 있다.

내 서버 로그를 보면 이 숫자가 나온다.

```
Prefix cache hit rate: 55.3%
```

**절반 이상이 캐시에서 나왔다.**

프리픽스 겹침이 이 정도면 **SGLang의 라딕스 트리가 더 유리한 영역**이다. 이 한 축만 놓고 보면 SGLang을 골랐어야 한다는 계산이 나온다.

## GB10 에서는 SGLang 이 안 돌아간다

DGX Spark는 흔한 조합이 아니다.

```
aarch64      ARM 64비트. 서버 세계는 아직 x86_64가 기본이라
             파이썬 휠부터 도커 이미지까지 ARM 용이 없는 경우가 많다
GB10         Grace CPU 와 Blackwell GPU 를 한 패키지에 넣고
             메모리를 공유하는 칩
sm_121a      이 GPU 의 CUDA 아키텍처 코드
```

**세 번째가 핵심이다.** GPU 커널은 아키텍처별로 미리 컴파일해둔다. 컴파일러가 그 코드를 모르면 성능이 떨어지는 게 아니라 **빌드 자체가 안 된다.**

SGLang은 이 조합을 [아직 정식 지원하지 않는다](https://github.com/sgl-project/sglang/issues/11658). 커뮤니티 이미지와 개발 브랜치 스냅샷이 돌아다니지만 임시 우회가 들어가 있고, Triton 이 `sm_121a`를 제대로 못 받아주는 문제가 남아 있다.

이 기계에서는 그게 특히 무겁다. **이 박스는 인터넷에 직접 못 나간다.** 빌드하다 막히면 의존성 하나 받는 것도 일이 된다. 미리 만들어진 이미지가 있느냐 없느냐가 그대로 가능·불가능이 된다.

## 프리필과 디코딩이 GPU를 두고 싸운다

기동 옵션에 이게 있다.

```
--max-num-batched-tokens 8192
```

이 값을 이해하는 데 시간이 좀 걸렸다.

추론에는 성격이 다른 두 작업이 섞여 있다. **프리필**은 프롬프트 전체를 한 번에 처리해서 GPU 연산을 가득 채우고, **디코딩**은 토큰을 하나씩 뽑느라 대부분의 시간을 가중치 읽는 데 쓴다.

긴 프롬프트가 하나 들어오면 그 프리필이 GPU를 오래 붙잡는다. 그동안 다른 대화들의 디코딩이 멈춘다. **한 사람이 긴 문서를 붙여넣으면 나머지 대화가 다 같이 끊기는 것**이다.

청크 프리필은 긴 프리필을 조각내서 디코딩 사이사이에 끼워 넣는다. `--max-num-batched-tokens`가 한 번에 처리할 토큰 수를 정한다.

```
작게 (2048)    다른 대화의 토큰 간격이 매끄러워지지만
               긴 프롬프트의 첫 응답이 늦어진다

크게 (8192+)   긴 프롬프트가 빨리 처리되지만
               그동안 다른 대화의 토큰 간격이 벌어진다
```

**8192는 처리량 쪽에 기울인 값이다.** 혼자 쓰는 서버라 누가 끊기는 걸 느낄 일이 적고, 에이전트가 도구 결과로 긴 텍스트를 자주 밀어 넣기 때문이다.

로그에 이렇게 찍힌 적이 있다.

```
Avg prompt throughput: 5380.9 tokens/s, Avg generation throughput: 10.2 tokens/s
```

프리필이 초당 5,380 토큰, 생성이 10 토큰. **같은 GPU에서 두 작업의 성격이 얼마나 다른지가 이 한 줄에 보인다.**

## 툴 콜 파서 지원이 갈린다

옵션 두 개를 더 켜야 했다.

```
--enable-auto-tool-choice
--tool-call-parser qwen3_coder
```

모델은 툴 콜을 자기 형식대로 뱉는다. 그걸 OpenAI 함수 호출 형식으로 바꿔주는 파서가 없으면 그냥 텍스트로 나온다. 에이전트 입장에서는 도구를 아예 못 부르는 것과 같다.

모델마다 파서가 다르고 지원 목록도 다르다. 벤치마크 숫자보다 이 목록을 먼저 봤어야 했는데, 나는 반대로 했다.

## 언제 무엇을 고르나

| 상황 | |
|---|---|
| **VRAM에 모델이 안 들어간다** | **Ollama.** 아래 설명 |
| 혼자서 채팅창 하나 | **Ollama.** 배치 1에서는 셋이 거의 같고 설치가 비교가 안 되게 쉽다 |
| 모델을 자주 바꿔보고 싶다 | **Ollama.** vLLM은 기동에만 8분이 걸린다 |
| 동시 요청이 붙는다 | **vLLM 또는 SGLang** |
| 프리픽스 겹침이 크다 | **SGLang** 이 유리할 수 있다 |
| 하드웨어가 특이하다 | **지원되는 것.** 나머지 비교가 의미 없어진다 |

### VRAM이 모자랄 때

이게 Ollama의 진짜 존재 이유다.

llama.cpp는 모델 레이어 일부만 GPU에 올리고 나머지는 시스템 RAM에 두는 **부분 오프로드**를 지원한다. 24GB 카드에 안 들어가는 모델도 뜬다. 느리다. 초당 한 자릿수 토큰이 나온다. 그래도 **돌아간다.**

vLLM은 이 상황에서 그냥 로딩에 실패한다. 안 들어가면 안 뜬다.

`8GB 노트북에서 30B를 돌려보고 싶다`는 요구는 vLLM으로 답이 안 나온다. 이건 성능 비교의 문제가 아니라 **되느냐 안 되느냐**의 문제다.

## vLLM 을 고른 이유

프리픽스 한 축에서는 SGLang 이 유리할 수 있다. 그런데 나머지를 다 놓고 보면 그림이 달라진다.

| | |
|---|---|
| **사실상 표준** | 막히면 검색하면 나온다. 혼자 운영하는 사람에게 이게 제일 크다 |
| **모델 지원이 가장 빠르다** | 새 모델이 나오면 vLLM 지원이 먼저 붙는다 |
| **하드웨어 지원도 가장 빠르다** | GB10 이미지가 vLLM 만 있었던 게 우연이 아니다 |
| **OpenAI 호환 API 가 성숙하다** | 게이트웨이 뒤에 붙일 때 번역이 거의 없다 |

네 번째가 내 구조에서 특히 컸다. 이 서버는 게이트웨이 뒤에 프로바이더로 붙는다. **호환성이 곧 연동 비용이다.**

이득이 확실한 축 하나와, 아직 재보지도 않은 이득 하나. 저울이 기우는 방향이 분명했고 **하드웨어 지원이 그걸 확정지었다.**

정리하면 이렇게 골랐다.

```
동시 요청이 붙는다           → Ollama 탈락. 슬롯마다 메모리가 곱해진다
프리픽스가 크게 겹친다        → SGLang 이 유리할 수 있다
그런데 GB10 에서 안 돌아간다   → SGLang 탈락
남은 축을 다 합치면           → vLLM
```

**성능 벤치마크가 아니라 제약 조건이 먼저 후보를 지웠다.** 특이한 하드웨어를 쓰면 그렇게 된다. 그리고 남은 하나가 마침 생태계가 가장 넓은 쪽이라, 혼자 운영하면서 막힐 때마다 검색으로 답을 찾을 수 있었다. 그게 5개월을 굴리는 동안 옵션 목록보다 훨씬 크게 작동했다.
