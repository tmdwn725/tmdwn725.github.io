> DGX Spark로 온프렘 LLM을 굴린 기록. 2편.

## 활성 3B가 76GB를 쓴다

`nvidia-smi`를 보다가 걸렸다.

```
pid, process_name, used_gpu_memory
174376, VLLM::EngineCore, 78190 MiB
```

76GiB. 지금 올린 모델은 총 35B에 활성 3B인 MoE다. 토큰 하나 만들 때 실제로 계산에 참여하는 건 3B뿐이다. 그런데 76GB를 잡고 있다.

활성 파라미터만 메모리에 올린다고 어딘가에서 읽었던 것 같은데, 그건 내가 잘못 안 거였다.

## 기동 로그가 다 말해준다

```bash
docker logs vllm-ornith 2>&1 | head -300 | grep -E "Model loading took|Available KV cache|GPU KV cache size|Maximum concurrency"
```

```
Model loading took 65.53 GiB memory and 470.718576 seconds
Available KV cache memory: 6.08 GiB
GPU KV cache size: 159,296 tokens
Maximum concurrency for 65,536 tokens per request: 8.00x
```

첫 줄에서 끝났다. **가중치만 65.53 GiB다.**

계산이 맞는지 확인해봤다. 파라미터 35B에 bf16이면 파라미터당 2바이트, 곱하면 70GB다. GiB로 바꾸면 65.2 GiB. 로그의 65.53과 거의 같다.

활성 3B는 **속도** 얘기지 **메모리** 얘기가 아니었다. 어떤 전문가를 부를지는 토큰마다 달라지니까, 35B 전부가 메모리에 올라가 있어야 한다. 매번 다른 3B를 골라 읽을 뿐이다.

MoE가 싼 건 대역폭이지 용량이 아니다.

## 남은 건 6GB

```
Available KV cache memory: 6.08 GiB
```

가중치 65.53에 KV 캐시 6.08을 더하면 71.6 GiB다. 프로세스 전체가 76.4 GiB니까 나머지 4.8 GiB 정도는 활성화 메모리와 CUDA 런타임 몫이다.

비율로 보면 이렇다.

| | 크기 | 비중 |
|---|---|---|
| 모델 가중치 | 65.53 GiB | 92% |
| KV 캐시 | 6.08 GiB | 8% |

대화 내용을 담는 공간이 전체의 8%다.

## KV 캐시는 왜 미리 잡나

vLLM은 이 6GB를 **기동할 때 통째로 선점한다.** 요청이 하나도 없어도 잡아둔다.

PagedAttention 때문이다. KV 캐시를 고정 크기 블록으로 잘라놓고 요청마다 필요한 만큼 블록을 빌려준다. 운영체제의 페이징과 같은 발상이다.

이러려면 블록 풀이 먼저 있어야 한다. 쓸 때마다 메모리를 새로 할당하면 조각이 나고, 조각이 나면 긴 대화가 중간에 자리를 못 찾아 죽는다. 미리 잡는 게 낭비가 아니라 그 반대다.

6.08 GiB에 159,296 토큰이 들어간다고 하니 토큰당 40 KiB다. 이건 실측이라 모델 구조를 몰라도 나눗셈으로 나온다.

## 8.00x라는 숫자

```
Maximum concurrency for 65,536 tokens per request: 8.00x
```

`--max-model-len 65536`으로 띄웠으니, 모든 요청이 컨텍스트를 꽉 채운다고 가정하면 8개까지 동시에 받을 수 있다는 뜻이다.

혼자 쓰는데 8개면 충분하다고 생각하고 넘겼다. 그런데 실제 로그를 보니 다르게 돌아가고 있었다.

```
Running: 11 reqs, GPU KV cache usage: 18.2%
```

**11개가 동시에 돌았고 캐시는 18%밖에 안 찼다.**

159,296 토큰의 18.2%면 약 29,000 토큰이다. 11로 나누면 요청당 2,600 토큰 남짓. 내 대화는 65,536 근처도 안 간다.

8.00x는 최악을 가정한 값이고, 실제로는 그 몇 배가 들어간다. 컨텍스트 한도를 크게 잡아두면 이 숫자가 겁을 주는데, 겁먹을 필요가 없었다.

## fp8을 켠 이유

띄울 때 이 옵션을 넣어뒀다.

```
--kv-cache-dtype fp8
```

당시엔 남들이 쓰길래 따라 켠 쪽에 가까웠다. 지금 숫자를 보니 켜야만 했던 거였다.

KV 캐시에 6GB밖에 없는데 여기에 컨텍스트 65,536을 넣으려면 토큰당 크기를 줄이는 수밖에 없다. fp8은 원소당 1바이트라 fp16의 절반이다. 같은 6GB에 두 배가 들어간다.

fp8을 안 켰으면 159,296이 아니라 8만 토큰쯤이었을 거고, 최대 동시 처리도 8.00x가 아니라 4x였을 것이다.

## 그래서 0.62

`--gpu-memory-utilization`을 0.62로 잡아뒀다. 통합메모리 119GB 중 62%만 vLLM에 주는 설정이다.

나머지를 남긴 이유가 있다. 이 박스에는 AlphaFold2와 ProteinMPNN도 떠 있다. 둘은 평소 GPU를 전혀 안 잡고 있다가 요청이 오면 서브프로세스를 띄워서 쓴다. 그 순간 쓸 자리가 없으면 계산이 죽는다.

0.62를 올리면 KV 캐시가 커지고 동시 처리가 늘어난다. 하지만 늘려봐야 지금도 18%밖에 안 쓴다. **놀고 있는 공간을 더 늘리려고 다른 도구를 죽일 이유가 없다.**

취향으로 고른 숫자가 아니라 여기서 나온 값이다.

## 부수적으로 알게 된 것

```
Model loading took 65.53 GiB memory and 470.718576 seconds
```

기동에 **8분** 걸린다. 65GB를 디스크에서 읽어 올리는 시간이다.

컨테이너를 재시작하면 8분간 채팅이 안 된다는 뜻이다. 설정 하나 바꿔보려고 가볍게 재시작할 수 있는 게 아니다. 이걸 모르고 낮에 옵션을 바꿨다가 한참을 기다린 적이 있다.

## 확인하는 법

`nvidia-smi`를 그냥 치면 이렇게 나온다.

```
Memory-Usage: Not Supported
```

처음엔 드라이버가 고장난 줄 알았다. GB10은 CPU와 GPU가 메모리를 공유하는 통합 구조라 전통적인 VRAM 사용량 개념이 안 맞는다. 그래서 프로세스별로 보는 쪽으로 바꿨다.

```bash
nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv
```
