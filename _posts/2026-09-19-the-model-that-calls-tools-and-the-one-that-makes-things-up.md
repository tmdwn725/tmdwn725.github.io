[추론이 메모리와 속도를 쓰는 방식을 본 글](/posts/how-local-llm-inference-actually-works/)을 이렇게 끝냈다.

```
가중치를 4비트로 내리면    얼마나 빨라지고 도구 호출이 얼마나 나빠지나
MTP 를 켜면              얼마나 빨라지나
메모리 비율을 올리면       바이오 도구가 버티나
컨텍스트를 줄이면         실제로 뭐가 막히나
```

이 중 둘을 측정했다. 하는 김에 모델도 바꿨다.

## 서빙 엔진 업데이트

쓰던 vLLM 이 0.17, 3월 빌드였다. 새로 보려던 모델들은 그보다 높은 버전을 요구했다.

DGX Spark 는 인터넷이 없어 모델도 이미지도 프록시를 태워야 한다. 모델 가중치는 컨테이너에 환경변수를 주면 되지만, `docker pull` 은 dockerd 데몬이 하므로 데몬 쪽에 설정해야 한다.

```
/etc/systemd/system/docker.service.d/http-proxy.conf

[Service]
Environment="HTTP_PROXY=http://<프록시>:8888"
Environment="HTTPS_PROXY=http://<프록시>:8888"
Environment="NO_PROXY=localhost,127.0.0.1,172.16.0.0/24"
```

### vLLM 버전과 KV 캐시

엔진만 올리고 모델은 그대로 뒀다. `--gpu-memory-utilization` 도 0.62 그대로다.

| | 0.17 | 0.27.1 |
|---|---|---|
| KV 캐시 | 5.46 GiB / 142,528 토큰 | 6.9 GiB / **594,997 토큰** |
| 64K 요청 동시성 | 7.18x | 9.08x |

**같은 비율을 줬는데 받은 게 달라졌다.** 하이브리드 어텐션의 KV 회계 방식이 그 사이 바뀐 것 같다. 버전을 올릴 때 설정값의 의미가 유지된다고 가정하면 안 되겠다.

덤도 있었다. 전날 "이 엔진의 새 API 는 사고 과정 on/off 를 무시한다" 고 결론 내고 문서에 "항상 켜짐으로 선언한다" 고 적어뒀는데, 버전을 올리니 **둘 다 정상 동작했다.** 구버전 버그였다. 스트리밍에서도 사고 과정 델타 193개와 본문 델타 8개가 완전히 갈라져 나와서, 본문에 섞여 나오는 태그를 청소하던 코드를 지울 수 있게 됐다.

## 최신 오픈 모델 검토

8월에 공개된 것들 대부분이 이 기계에 안 들어간다.

| 모델 | 총 / 활성 | 왜 탈락 |
|---|---|---|
| GLM-5.3-Flash | 320B / 18B | 4비트로도 안 들어감 |
| MiniMax M3 | 428B / 23B | 〃 |
| MiMo-V2.5 | 310B / 15B | 〃 |
| Qwen3.8-Flash-Next | 125B / 6B | 4비트 판이 125 GiB. KV 자리가 없다 |

Flash-Next 가 아쉬웠다. 활성 6B 라 속도는 좋을 텐데 51B 짜리 n-gram 임베딩 테이블이 통째로 상주한다. 그 테이블을 NVMe 에서 읽게 패치하면 75 GiB 로 내려가지만, 매 토큰 디스크를 긁는 구조라 상시 돌리기엔 부담이다.

### 모델 3종 제원

| | Ornith 1.0 | Ornith 1.5 | Qwen3.8-27B |
|---|---|---|---|
| 저장소 | `deepreinforce-ai/Ornith-1.0-35B` | `ornith-ai/Ornith-1.5-35B-A3B` | `Qwen/Qwen3.8-27B` |
| 구조 | MoE 35B / 활성 3B | MoE 35B / 활성 3B | **dense 27B** |
| 어텐션 | 하이브리드 (Mamba 계열 + full) | 〃 | 하이브리드 (Gated DeltaNet + full 16층) |
| KV head / head_dim | 2 / 256 | 2 / 256 | 4 / 256 |
| 초안 헤드 | 없음 | 없음 | **모델 파일에 포함** |
| 이미지 입력 | - | - | vision encoder 27층 |
| 공개 | 2026-06-25 | 2026-08-19 | 2026-08-14 |
| 라이선스 | MIT | MIT | Apache 2.0 |

앞의 둘은 **같은 크기·같은 활성 파라미터의 두 세대**다. 달라지는 건 학습이지 구조가 아니다. 세 번째만 형태가 다르다.

Qwen3.8-27B 를 다시 본 이유가 있다. 전에 27B dense 를 올렸다가 느려서 접었고, 원인이 대역폭이라는 것도 지난 글에서 확인했다. dense 27B 는 매 토큰 54 GB 를 읽어야 해 273GB/s 로는 초당 5회가 상한이다. 활성 3B MoE 는 6 GB 만 읽으니 45회다.

**그런데 이 모델은 초안 헤드를 갖고 있다.** `config.json` 에 `mtp_num_hidden_layers: 1` 이 있다. 초안을 찍는 층 하나가 모델 파일에 같이 들어 있어서, 초안 모델을 따로 받지 않아도 옵션 한 줄로 켜진다.

초안을 여러 개 찍어 한 번에 검증하면 매 토큰 가중치를 읽는 횟수가 줄어든다. 대역폭 산수를 뒤집을 유일한 장치라 다시 올려봤다.

### 가중치 크기

같은 모델도 어떤 판을 받느냐에 따라 디스크에서부터 다르다.

```
Ornith 1.0   bf16     66 GB    35B × 2바이트
Ornith 1.5   bf16     67 GB    35B × 2바이트
Qwen3.8-27B  bf16     52 GB    27B × 2바이트
             ↓ --quantization fp8 (엔진이 올리면서 변환)
             fp8      31 GB
             ↓ 4비트 판을 따로 받음
             nvfp4    23 GB
```

MoE 쪽은 **35B 전부가 메모리에 있어야 한다.** 매 토큰 3B 만 읽을 뿐 나머지 32B 가 사라지는 게 아니다.

이 숫자가 곧 GPU 메모리에 올라가는 양이다. 파일에 있는 그대로 올라가고, 그 위에 KV 캐시와 실행 중 임시 버퍼가 얹힌다.

```
Qwen3.8-27B nvfp4
  23 GB      가중치 (파일 크기 그대로)
+ 18.93 GiB  KV 캐시
+ α          활성화, CUDA graph, 런타임
= --gpu-memory-utilization 0.40 이 예약한 몫
```

가중치를 줄이면 같은 예약 안에서 KV 로 갈 자리가 그만큼 늘어난다.

4비트 판은 `RadixArk/Qwen3.8-27B-NVFP4-BF16-LMHead` 를 받았다. 이름대로 **본체는 4비트로 누르고 출력층만 BF16 으로 남긴 것**이고, 엔진은 `modelopt_mixed` 로 인식한다. 출력층은 다음 토큰을 고르는 마지막 자리라 도구 이름을 정확히 찍어야 하는 작업에서는 여기를 지키는 게 중요할 수 있다고 봤다.

### 기동 후 메모리

같은 엔진, 같은 기계다.

| | 메모리 비율 | KV 캐시 | KV 토큰 | 64K 동시성 | 가중치 로딩 |
|---|---|---|---|---|---|
| Ornith 1.0 (bf16) | 0.62 | 6.9 GiB | 594,997 | 9.08x | 9.0분 |
| Ornith 1.5 (bf16) | 0.62 | 2.95 GiB | 253,520 | 3.87x | 3.7분 |
| Qwen3.8 (fp8) | 0.50 | 25.78 GiB | 580,461 | 8.86x | 7.3분 |
| Qwen3.8 (nvfp4) | **0.40** | 18.93 GiB | 425,984 | 6.50x | **2.8분** |

**총 가중치가 작은 쪽이 KV 로 쓸 자리를 남긴다.** 27B 를 4비트로 내리니 메모리 비율을 0.40 까지 낮추고도 KV 를 18.93 GiB 받았다. MoE 두 개보다 여유롭다. 활성 파라미터는 매 토큰 읽는 양을 정하고, 총 가중치는 자리를 정한다. **둘은 다른 문제였다.**

Ornith 1.5 의 KV 가 1.0 의 절반도 안 되는 건 가중치 1 GB 차이 때문이 아니라 뒤에 나오는 `--max-num-seqs` 를 낮춘 탓이다. 여기서도 같은 비율에 받는 게 달라졌다.

## MTP 켜기

지난 글에서 이 항목을 보고 "MTP 층이 있는데 안 쓰고 있다" 고 적었다. 이번에 켰다.

초안 헤드가 토큰 몇 개를 먼저 찍고, 본 모델이 **한 번의 forward 로 검증**한다. 동의한 토큰만 채택하고 틀린 지점부터는 본 모델이 이어간다. 출력 분포가 본 모델 단독과 수학적으로 같아서 **틀리면 속도만 손해지 품질은 안 변한다.**

초안 3개, 400 토큰씩, 단일 요청, 사고 과정은 끈 채로 측정했다.

| | 산문 | 코드 |
|---|---|---|
| fp8 + MTP | 11.8 tok/s (청크당 2.0) | 16.3 tok/s (청크당 2.8) |
| nvfp4 + MTP | 14.0 tok/s (청크당 2.0) | 17.8 tok/s (청크당 2.6) |

fp8 단독 이론치가 8 정도니 1.5~2배다. **코드가 산문보다 수락률이 높다.** 반복 패턴이 많을수록 초안이 잘 맞는다.

4비트에서 19% / 9% 밖에 안 오른 건 예상 밖이었다. 가중치를 31 GB 에서 23 GB 로 줄였으니 산수로는 더 나와야 한다. GB10 은 4비트 연산을 하드웨어로 하지 않고 커널이 풀어서 계산하는데, 그 비용이 대역폭 이득을 상당 부분 먹는 것으로 보인다. **파일에 적힌 자료형과 실제 계산되는 자료형이 다르다**는 걸 잊고 있었다.

## 평가 기준 6개

벤치마크 점수는 안 봤다. 매일 실제로 시키는 일로 골랐고, 모든 모델에 **같은 문장을 같은 순서로** 물었다.

```
① 관심종목 29개 현재가        여러 도구를 연달아 부르는가
② 파이썬 문법 예시            도구를 안 불러야 통과
③ 펩타이드 구조 예측          바이오 도구를 부르는가
④ 마이너스 종목 재무 분석      잔고 → 선별 → 재무조회 → 판단
⑤ 대역폭으로 tok/s 계산       정답 있음
⑥ KV 캐시 크기 계산           정답 있음
```

통과 기준은 하나다. **부를 자리에서 부르고, 부르지 말아야 할 자리에서 안 부르고, 지어내지 않는다.** ⑤⑥ 은 정답이 정해져 있어 숫자로 채점한다.

채점은 게이트웨이 로그를 봤다. 화면에 뭐라고 썼는지가 아니라 **어느 도구를 몇 번 불렀는지**가 DB 에 남는다. ①의 "도구가 실패했다" 는 답이 거짓인 것도 이렇게 드러났다.

| 기호 | 뜻 |
|---|---|
| ○ | 통과 |
| △ | 통과했지만 흠이 있다 |
| × | 실패 |
| ★ | 기대 이상 |

| | ① | ② | **③** | ④ | ⑤ | ⑥ |
|---|---|---|---|---|---|---|
| Ornith 1.0 | × | △ | **×** | × | × | ○ |
| Ornith 1.5 | ○ | ○ | **×** | ○ | ○ | × |
| Qwen3.8-27B fp8 | ○ | ○ | **★** | ○ | ○ | ○ |
| Qwen3.8-27B nvfp4 | ★ | ○ | **★** | ○ | ○ | ○ |

### 계산 문제 채점

⑤⑥ 은 채점이 명확해서 어디서 틀렸는지가 그대로 보인다.

| | 정답 | Ornith 1.0 | Ornith 1.5 | Qwen3.8-27B |
|---|---|---|---|---|
| ⑤ 27B dense bf16 | 5.06 tok/s | 4.87 | 5.05 | 5.06 |
| ⑤ 35B MoE 활성 3B | 45.5 tok/s | **3.93** | 45.5 | 45.5 |
| ⑥ KV fp8 | 8.59 GB | 8.0 GiB | **4.0 GB** | 8.59 GB |
| ⑥ KV bf16 | 17.18 GB | 16.0 GiB | **8.0 GB** | 17.18 GB |

Ornith 1.0 의 MoE 오답이 흥미롭다. **45.5 를 제대로 구해놓고** "GPU 는 결국 전체 가중치를 읽어야 한다" 며 스스로 기각했다. 활성 파라미터만 읽는다는 게 MoE 의 전제인데 그걸 뒤집은 것이다.

1.5 의 `4.0 / 8.0` 은 K 와 V 중 하나만 센 값이다. 다만 **같은 모델에 온도만 바꿔 한 번 더 물었을 때는 맞혔다.** 한 칸 차이는 소음으로 봐야 한다는 뜻이다.

GiB 와 GB 는 둘 다 맞는 것으로 봤다. 8.589 GB 가 곧 8 GiB 다.

### 세대 차이

Ornith 1.0 은 관심종목 29개 중 9개만 부르고 이렇게 답했다.

> 해외 주식 20개는 KIS 도구가 반응시간 초과로 일부 실패했으므로…

로그에는 **해외 종목 호출 시도 자체가 없었다.** 하지도 않은 일이 실패했다고 핑계를 지어냈다.

보유종목 분석은 더 나빴다. 잔고 조회 도구를 부르지도 않고 앞 대화에 남아 있던 관심종목을 가져다 "LG전자 -51,800원" 같은 손익을 만들어냈다. 내 실제 보유 종목은 전부 ETF 다.

1.5 는 이걸 다 고쳤다. 29개를 전부 부르고, 해외가 0 을 돌려주자 "-" 로 표기했다. 보유종목도 잔고 → 마이너스 5개 선별 → 재무 조회까지 가고 **"이건 ETF 라 개별 기업 재무제표가 없다"** 는 것까지 스스로 알아챘다. 같은 크기, 같은 구조, 두 달 차이다.

### 셋 다 못 넘은 문제

③ 이다. 펩타이드 서열을 주고 구조를 예측해달라고 하면 도구를 부르는 대신 **결과를 지어냈다.**

Ornith 1.5 가 만들어낸 답이다.

```
평균 pLDDT    82.4
최대 pLDDT    96.8
90+ (매우 높음): 5 residues - C-terminal 부근
70-90 (높음):   9 residues - 핵심 구조

PDB 형식의 예측 구조를 확인하세요: /tmp/structure_6a9d1f.pdb
```

없는 파일 경로까지 붙였다. 도구 호출 기록은 0 건이다. 1.0 도, 1.5 도, 온도를 바꿔 다시 물어도 세 번 다 이랬다.

**Qwen3.8-27B 는 도구를 불렀다.** 수십 밀리초 만에 `All connection attempts failed` 가 돌아왔고(그 서버는 평소 꺼둔다), 모델은 서열과 실패 원인, "pLDDT 를 아직 확인하지 못했습니다" 까지 그대로 보고했다.

이게 이번 비교의 결론이다. 벤치 점수도 tok/s 도 아니고, **모르는 걸 도구에 물어보러 가느냐 아는 척하느냐.**

### 도구를 막으면 다 지어낸다

Qwen3.8 에게 "그 도구 없이 네가 판단해서 해줘" 라고 명시적으로 추측을 시켰더니 이 모델도 똑같이 지어냈다. 서열을 21잔기에서 19잔기로 잘못 읽고, 인슐린 A 사슬을 항체 유래 펩타이드라고 단정하고, 잔기 번호를 1부터 100까지 나열하는 쓰레기를 출력했다.

차이는 **지식이 아니라 행동**이다. 도구를 막으면 셋 다 같은 수준으로 지어낸다. 다만 Qwen3.8 은 막히기 전에 가보려 했다.

## 4비트로 내리면 도구 호출이 나빠지나

12일 전에 적은 질문이고 이번에 가장 확인하고 싶었던 것이다.

걱정할 근거가 있었다. NVIDIA 는 4비트 판이 일반 벤치에서 손실 1% 미만이라고 한다. 그런데 올해 나온 연구들은 **에이전트와 도구 호출에서는 다르게 깨진다**고 말한다.

```
Qwen3.5-9B          77.3 → 70.4
Gemma4-26B-A4B      66.1 → 56.0
```

10점씩 빠진다. 내 여섯 문제로 치면 한두 문제가 뒤집힐 크기다.

설계는 **같은 모델, 같은 초안 설정, 양자화만 다르게.** fp8 은 손실이 거의 없어 기준선이 되고, 둘의 차이가 그대로 4비트 몫이 된다.

원래는 DFlash 라는 다른 초안 방식을 쓰려 했다. 이쪽은 초안 모델을 따로 받아야 해서 3.6 GB 를 내려받았는데, 엔진이 거부했다.

```
ValidationError: Model architectures ['DFlash2DraftModel'] are not supported for now.
```

지원 목록에 `DFlashDraftModel` 은 있고 `DFlash2DraftModel` 만 없다. **v1 은 알고 v2 는 모른다.** 참고한 레시피가 "nightly 빌드 필요" 라고 적어둔 게 이 얘기였다. 덕분에 초안 방식이 MTP 로 통일되면서 **양자화만 격리된** 더 깨끗한 비교가 됐다.

| | fp8 + MTP | nvfp4 + MTP |
|---|---|---|
| 통과 | 6/6 | **6/6** |
| ③ 도구 호출 | 불렀다 | **불렀다** |
| 호출당 평균 | 25.0초 | **18.6초** |
| 가장 오래 걸린 호출 | 67.3초 | 40.9초 |
| 평균 출력 토큰 | 308 | 306 |

**나빠지지 않았다.** 도구를 부르는 행동도, 계산 문제 정답도, 답변 길이도 그대로고 오히려 26% 빨라졌다.

①에서는 더 나아갔다. fp8 판은 해외 종목을 못 가져오자 "이 도구는 국내 6자리 종목코드만 지원합니다" 하고 멈췄는데, 4비트 판은 **웹 검색으로 갈아타서** 20종목 시세를 가져왔다. 출처 날짜가 8월 19일부터 9월 19일까지 제각각이고 한 종목은 못 찾았는데, 그걸 "확인 실패 - 검색 결과가 유효하지 않음" 으로 적었다. 막히니 다른 길을 찾았고, 가져온 값이 언제 것인지까지 적었다.

다만 **"4비트 절벽이 없다" 가 아니라 "이 워크로드에서는 안 밟혔다"** 가 정확한 표현이다. 연구가 든 사례는 9B 와 활성 4B 짜리였다. 27B dense 는 파라미터가 많아 4비트 격자에 담을 여유가 더 있고, 나는 출력층을 BF16 으로 남긴 판을 골랐다. 출력층을 지킨 게 효과였는지는 순수 4비트 판과 비교해야 알 수 있는데 그건 안 해봤다.

## 속도와 통과율

여섯 문제를 도는 동안 게이트웨이에 쌓인 로그를 그대로 집계했다. 도구 121개가 실려 입력이 매 호출 32~38K 토큰이고, **첫 토큰까지의 시간이 전체를 지배한다.**

| | 통과 | 호출당 평균 | 최대 | 평균 출력 토큰 |
|---|---|---|---|---|
| Ornith 1.0 | 1/6 | **11.4초** | - | 498 |
| Ornith 1.5 | 4/6 | 15.4초 | 37초 | 419 |
| Qwen3.8-27B fp8 | 6/6 | 25.0초 | 67초 | 308 |
| **Qwen3.8-27B nvfp4** | **6/6** | 18.6초 | 41초 | **306** |

fp8 로만 봤을 때는 "가장 정확한 게 가장 느리다" 였다. 4비트로 내리니 18.6초가 되어 Ornith 1.5 의 15.4초와 3초 차이가 됐다. **4/6 과 6/6 사이의 3초라면 살 만한 값이다.**

출력 토큰이 가장 적다는 것도 눈에 걸린다. 통과율이 제일 높은데 말수는 제일 적다. Ornith 1.0 은 틀린 계산을 498 토큰으로 늘어놓고, Qwen3.8 은 맞는 답에 "실제로는 라우팅과 스케줄링 오버헤드로 이보다 낮다" 한 줄을 붙이고 끝낸다.

## 측정 중 발견한 버그 4개

들여다보지 않았으면 몰랐을 것들이다.

**게이트웨이의 모델 파라미터가 죽은 값이었다.** 요청 스키마의 `temperature` 기본값이 `1.0` 이라 "요청값 우선, 없으면 DB 기본값" 로직에서 요청값이 항상 이겼다. 관리 화면에서 모델별 온도를 설정해도 적용된 적이 없다. 기본값을 `None` 으로 바꿔 고쳤다. 이 버그 때문에 Ornith 1.0 회차는 온도 1.0 으로 측정됐고, Ornith 1.5 는 고친 뒤 온도 0.7 로 다시 물어 그 값을 표에 실었다.

**도구 인자 복구 플래그가 소음이었다.** 깨진 JSON 을 복구하는 함수가 멀쩡한 JSON 에도 "복구했음" 을 돌려줬다. "모델이 얼마나 자주 깨진 인자를 내나" 라는 지표가 처음부터 무의미했다.

**채팅 경로가 모델별 엔드포인트를 안 읽었다.** 오버라이드 필드가 임베딩과 음성 경로에만 적용돼 있었다.

**새 모델을 등록하고도 못 썼다.** API 키마다 허용 모델 목록이 따로 있다.

## 인프라 함정 2개

**`--max-num-seqs` 를 낮춰야 하는 모델이 있다.** Ornith 1.5 를 기본값 256 으로 띄우니 이렇게 죽었다.

```
ValueError: max_num_seqs (256) exceeds available Mamba cache blocks (219).
```

하이브리드 모델은 디코드 시퀀스마다 Mamba 캐시 블록이 하나씩 필요한데, 가중치가 조금 커지면서 블록이 모자랐다. 혼자 쓰는 기계라 32 로 낮춰도 잃는 게 없다.

여기에 `--restart unless-stopped` 가 겹치면 고약하다. **5분짜리 로딩을 무한 반복하는데, 죽는 지점이 로딩 끝이라 로그만 보면 정상처럼 보인다.**

## 결론

**Qwen3.8-27B 를 4비트로, MTP 를 켜서 쓰기로 했다.**

여섯 문제를 다 통과한 유일한 구성이고 속도는 Ornith 1.5 와 3초 차이다. 무엇보다 **도구를 부른다.** 모르는 걸 물어보러 가는 모델과 그럴듯하게 지어내는 모델의 차이는, 개인 비서로 쓰는 입장에서 다른 어떤 지표보다 크다. pLDDT 82.4 를 그대로 믿고 다음 작업으로 넘어갔다면 나는 그게 거짓인 줄도 몰랐을 것이다.

지금 이렇게 돌고 있다.

```
vllm serve RadixArk/Qwen3.8-27B-NVFP4-BF16-LMHead
  --max-model-len 65536
  --max-num-seqs 32
  --gpu-memory-utilization 0.40
  --kv-cache-dtype fp8
  --enable-prefix-caching
  --max-num-batched-tokens 8192
  --speculative-config '{"method":"mtp","num_speculative_tokens":3}'
  --reasoning-parser qwen3
  --tool-call-parser qwen3_xml --enable-auto-tool-choice
```

덤으로 자리가 생겼다. 가중치가 66 GB 에서 23 GB 로 줄었으니 **40 GB 이상이 빈다.** 몇 달 전에 자리가 없어 내려둔 임베딩 모델과 음성 인식 모델을 되살릴 수 있다. 4비트의 진짜 이득은 속도가 아니라 이쪽일지도 모르겠다.

한 가지는 덜 내키는 채로 남는다. **Ornith 는 활성 3B 로 이 속도를 낸다.** 27B dense 는 MTP 를 덧대고 4비트까지 내려서야 비슷해졌다. Ornith 계열에 4비트 판과 초안 헤드가 붙으면 다시 뒤집힐 수 있다.

## 아직 확인 못 한 것

지난 글의 네 줄 중 둘이 남았다. 여기에 이번에 새로 생긴 것들을 더한다.

```
메모리 비율을 올리면       바이오 도구가 버티나        (아직)
컨텍스트를 줄이면         실제로 뭐가 막히나          (아직)
출력층을 BF16 으로 남긴 게 실제로 효과였나
도구 스키마 32K 프롬프트에서 초안 수락률이 얼마나 떨어지나
이 기계 전용으로 나온 초안 모델을 쓰면 얼마나 더 빨라지나
```

한 문제당 한 번씩만 물었다. Ornith 1.5 는 온도만 바꿔 한 번 더 물었더니 ⑥ 의 답이 뒤집혔으니, 한 칸 차이는 소음으로 봐야 한다. 여러 회차에서 일관되게 나온 것만 믿을 만하다. ③ 이 그렇다. 다섯 번을 물어 Ornith 는 세 번 다 지어냈고 Qwen3.8 은 두 번 다 도구를 불렀다.
