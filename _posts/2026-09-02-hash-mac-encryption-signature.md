## 게이트웨이가 보관하는 비밀

게이트웨이를 만들면 남의 API 키를 대신 들고 있어야 한다. 사용자별 프로바이더 키, 외부 서버 자격증명, 게이트웨이를 부르는 쪽의 인증 정보 같은 것들이다.

이걸 어떻게 저장할지 정해야 했는데, 찾아보니 방식 이름만 수십 개가 나왔다. AES, RSA, SHA-256, bcrypt, HMAC, Ed25519, PBKDF2 가 다 같은 목록에 있는데 서로 하는 일이 달랐다.

넷으로 묶으니 정리됐다.

| 도구 | 되돌릴 수 있나 | 무엇을 막나 | 키 |
|---|---|---|---|
| **해시** | 못 되돌린다 | 원문 노출, 변조 | 없음 |
| **MAC** | 못 되돌린다 | 위조 | 비밀키 하나 |
| **대칭 암호화** | 되돌린다 | 내용 노출 | 비밀키 하나 |
| **비대칭** | 되돌린다 | 위조, 부인 | 공개키·개인키 |

**넷은 막는 대상이 다르다.** 내용을 숨기는 건 암호화뿐이고, 만든 쪽을 증명하는 건 비대칭 서명뿐이다.

## 해시

### 잠그기만 하고 못 푼다

입력을 넣으면 고정 길이 결과가 나온다. 같은 입력이면 항상 같은 결과이고, 결과에서 입력을 되돌릴 수는 없다.

```
"안녕"     →  SHA-256  →  6b23c0d5f35d1b11…   (256비트, 항상 같은 길이)
"안녕!"    →  SHA-256  →  a3f52d1c8e4b0977…
```

한 글자만 바뀌어도 결과가 완전히 달라진다. **되돌릴 수 없다는 게 이 도구의 쓸모다.**

```
저장할 때   비밀번호를 해시해서 넣는다
확인할 때   들어온 비밀번호를 해시해서 저장된 것과 비교한다
```

원문을 갖고 있지 않으면서 대조는 할 수 있다. DB 가 통째로 유출돼도 원문은 없다. 파일이 중간에 바뀌었는지 확인할 때도 같은 방식이다.

### 대표 알고리즘

```
SHA-256 · SHA-512    지금 표준. SHA-2 계열
SHA-3                구조가 다른 후속. 아직 SHA-2 로 충분하다
BLAKE3               훨씬 빠름. 무결성 확인에 좋다
MD5 · SHA-1          깨졌다. 서로 다른 입력이 같은 해시를 내게 만들 수 있다
```

MD5 와 SHA-1 은 **충돌**을 만들 수 있다는 게 증명됐다. 두 개의 다른 파일이 같은 해시를 갖게 만들 수 있으니 무결성 확인에 못 쓴다.

### 비밀번호에는 느린 해시

해시라고 다 같지 않다. **SHA-256 은 너무 빠르다.**

빠른 게 장점인 용도도 있지만 비밀번호에서는 약점이 된다. 공격자가 DB 를 털었으면 후보 비밀번호를 하나씩 해시해서 맞춰보는데, GPU 로 초당 수십억 번을 돌린다.

그래서 비밀번호에는 **일부러 느린 해시**를 쓴다.

```
bcrypt     오래 검증됨. 입력 길이 제한(72바이트)이 있다
scrypt     메모리도 많이 쓰게 만든다. GPU 로 병렬화하기 어렵다
Argon2     지금 권장. 시간·메모리·병렬도를 따로 조절한다
```

한 번 계산에 수십에서 수백 밀리초가 걸리게 맞춘다. 사용자는 로그인할 때 한 번만 겪으니 0.1초가 문제되지 않는데, 공격자는 수십억 번을 돌려야 하니 그 0.1초가 벽이 된다.

### salt

같은 비밀번호를 쓰는 사람이 여럿이면 해시도 같아진다. 하나를 뚫으면 나머지가 같이 뚫린다.

그래서 사용자마다 다른 무작위 값을 섞는다. 이게 **salt** 다.

```
salt 없음   "1234" → 항상 같은 해시      미리 계산해두면 재사용 가능
salt 있음   "1234" + 사용자별 무작위값    사용자마다 다른 해시
```

미리 계산해둔 대조표(레인보우 테이블)를 못 쓰게 만드는 게 목적이다. salt 는 비밀이 아니라서 해시 옆에 같이 저장한다.

## MAC

### 해시에 비밀키를 섞는다

해시로는 **누가 만들었는지**를 알 수 없다. 아무나 계산할 수 있으니, 공격자가 자기 메시지를 만들고 그 해시를 붙여도 통과한다.

MAC 은 여기에 비밀키를 섞어서 **키를 아는 쪽만 만들 수 있는 값**으로 만든다.

<pre class="mermaid">
graph LR
  M["메시지"] --> H["HMAC"]
  K["비밀키"] --> H
  H --> S["서명값"]
  M --> SEND["메시지 + 서명값<br/>같이 보낸다"]
  S --> SEND
  SEND --> V["받는 쪽에서<br/>같은 키로 다시 계산"]
  V --> C{"같은가"}
  C -->|"예"| OK["진짜"]
  C -->|"아니오"| NO["버린다"]
</pre>

웹훅을 받을 때 이걸 쓴다. 외부에서 내 서버로 POST 를 날리는 구조라 아무나 흉내낼 수 있는데, 서명이 맞아야 진짜로 인정한다. 중간에 본문이 바뀌어도 서명이 안 맞는다.

내용을 숨기지는 않는다. **MAC 은 암호화가 아니다.**

### 키와 메시지를 그냥 붙이면 안 된다

비밀키를 섞는다면 `SHA-256(키 + 메시지)` 로 해도 될 것 같은데 이건 취약하다.

SHA-2 같은 해시는 **중간 상태를 이어받아 계속 계산할 수 있는 구조**다. 그래서 공격자가 원문과 서명만 보고도 `메시지 + 덧붙인 내용` 에 대한 올바른 서명을 만들어낼 수 있다. 키를 몰라도 된다. 이걸 길이 확장 공격이라고 한다.

HMAC 은 키를 안팎 두 번 나눠 넣는 구조라 이게 막힌다.

```
HMAC(K, m) = H( (K⊕opad) ‖ H( (K⊕ipad) ‖ m ) )
```

바깥 해시가 한 번 더 감싸서 중간 상태를 이어붙일 수 없다. **직접 조합하지 말고 HMAC 을 쓰는 이유다.**

### 검증할 때 시간이 샌다

서명을 대조할 때 `==` 를 쓰면 문제가 생긴다. 문자열 비교는 **다른 바이트를 만나는 순간 멈춘다.**

```
첫 바이트부터 다름     아주 빨리 거짓
앞 열 바이트가 맞음    조금 늦게 거짓
```

공격자가 서명을 조금씩 바꿔 보내면서 응답 시간을 재면 어디까지 맞았는지 알아낼 수 있다. 한 바이트씩 정답을 찾아나가는 공격이다.

그래서 **끝까지 다 비교하는 함수**를 쓴다. 파이썬이면 `hmac.compare_digest` 다. 항상 같은 시간이 걸려서 시간으로는 아무것도 알 수 없다.

### JWT 의 HS256 이 이것이다

토큰에 서명할 때 HMAC 을 쓰는 방식이 `HS256` 이다.

```
HS256    HMAC-SHA256.  발급자와 검증자가 같은 비밀키를 나눠 갖는다
```

**나눠 갖는다는 게 문제가 될 수 있다.** 검증하려면 키를 줘야 하는데, 그 키로 토큰을 만들 수도 있다. 검증하는 쪽이 여럿이면 그중 하나만 뚫려도 위조 토큰이 나온다.

이 문제를 푸는 게 비대칭 서명이다.

## 대칭 암호화

### 같은 키로 잠그고 푼다

```
평문 + 키   →  암호문
암호문 + 키 →  평문
```

해시와 다른 점은 **되돌릴 수 있다**는 것이다. 프로바이더 API 키처럼 나중에 원문이 필요한 값은 해시하면 안 된다. 실제로 호출할 때 써야 한다.

```
되돌려야 하나?
   예      API 키, 외부 서비스 토큰     →  암호화
   아니오  비밀번호, 게이트웨이 인증 키  →  해시
```

**저장 설계는 이 질문에서 시작한다.** 전부 암호화해버리면 되돌릴 필요 없는 값까지 복호화 가능한 상태로 들고 있게 된다.

### 블록 암호와 운용 모드

AES 는 **16바이트씩** 잠근다. 그보다 긴 데이터는 토막을 내서 여러 번 잠가야 한다. **토막을 어떤 순서로 어떻게 엮느냐가 여러 가지**고, 이걸 운용 모드라고 한다.

```
ECB    토막마다 따로 잠근다
       같은 평문 토막이 항상 같은 암호문이 된다  →  쓰면 안 된다

CBC    앞 토막의 암호문을 다음 토막에 섞는다
       맨 앞에 무작위 IV 가 필요하다

CTR    카운터를 암호화해서 평문과 XOR 한다
       토막 경계 없이 흐르듯 처리된다

GCM    CTR 에 무결성 검사를 붙였다  →  지금 권장
```

ECB 가 왜 위험한지는 반복되는 데이터를 넣어보면 드러난다.

```
평문     AAAAAAAAAAAAAAAA BBBBBBBBBBBBBBBB AAAAAAAAAAAAAAAA
ECB      3f9a…             c17e…             3f9a…
                                              ↑ 첫 토막과 같다
```

**내용을 몰라도 어디가 반복되는지가 보인다.** 이미지를 ECB 로 암호화하면 형태가 그대로 남는 게 이 때문이다.

CBC 와 CTR 은 앞 토막이나 카운터를 섞어서 이걸 막는다. 대신 **같은 키로 같은 IV 를 두 번 쓰면 안 된다.** 재사용하면 같은 평문이 다시 같은 암호문이 돼서 ECB 와 똑같아진다.

### 암호화만으로는 변조를 못 막는다

암호문을 공격자가 조작해도 복호화 자체는 된다. 대개는 알아볼 수 없는 값이 나오지만, 운이 나쁘면 그럴듯한 값이 나오고 시스템은 그걸 정상으로 받아들인다.

그래서 실무에서는 **암호화와 MAC 을 같이 쓴다.**

```
잠그고    평문을 암호화한다
서명하고  암호문에 MAC 을 붙인다
확인은    MAC 을 먼저 검증하고, 통과해야 복호화한다
```

이 조합을 미리 묶어둔 것들이 있고 **인증된 암호화**라고 부른다.

```
AES-GCM               AES 의 CTR 모드에 인증을 묶었다. 하드웨어 가속이 있다
ChaCha20-Poly1305     AES 가속이 없는 환경에서 빠르다
Fernet                AES-128-CBC + HMAC-SHA256. 파이썬에서 쓰기 쉽다
```

**직접 조합하지 말고 이런 걸 쓰는 게 안전하다.** 순서를 잘못 잡으면 취약해진다. 암호화를 먼저 하고 그 결과에 MAC 을 붙이는 순서가 맞다.

## 비대칭

### 키를 둘로 나눈다

MAC 은 양쪽이 같은 키를 갖는다. 그래서 못 하는 일이 둘 있다.

```
키를 미리 나눠 가져야 한다      처음 만나는 상대와는 못 쓴다
누가 만들었는지 증명이 안 된다   둘 다 같은 키를 가지니 서로 부인할 수 있다
```

비대칭은 키를 **개인키와 공개키** 둘로 나눠서 이걸 푼다.

<pre class="mermaid">
graph TB
  subgraph SYM["대칭 · 키 하나"]
    direction LR
    A1["A"] --- K1["같은 키"] --- B1["B"]
  end
  subgraph ASYM["비대칭 · 키 둘"]
    direction LR
    A2["A<br/>개인키 보관"] -->|"서명"| MSG["메시지 + 서명"]
    MSG -->|"검증"| B2["B<br/>공개키만 있으면 됨"]
  end
</pre>

```
서명   메시지 + 개인키           →  서명값       개인키를 가진 쪽만 가능
검증   메시지 + 서명값 + 공개키   →  참 / 거짓    공개키는 아무나 가져도 됨
```

공개키는 이름 그대로 공개해도 된다. **검증하는 쪽이 비밀을 하나도 몰라도 된다는 게 핵심이다.**

### 대표 알고리즘

```
RSA        오래된 표준. 키가 길다(2048비트 이상). 느리다
           서명과 암호화 둘 다 된다

ECDSA      타원곡선. 짧은 키로 같은 강도. RSA 보다 빠르다
Ed25519    타원곡선. 지금 권장. 구현 실수가 나기 어렵게 설계됐다
           서명 전용

ECDH · X25519   키 교환용. 서명이 아니라 공통 비밀을 만드는 데 쓴다
```

**비대칭으로 큰 데이터를 직접 암호화하지 않는다.** 너무 느려서 둘을 섞어 쓴다.

```
1  비대칭으로 대칭키를 안전하게 나눠 갖거나 교환한다
2  실제 데이터는 그 대칭키로 암호화한다
```

TLS 가 이 구조다. 연결을 맺을 때만 비대칭을 쓰고, 그다음 통신은 전부 대칭이다. 서명할 때도 데이터를 통째로 서명하지 않고 **해시를 서명한다.**

### JWT 의 RS256 과 HS256

HS256 에서 키를 나눠 갖는 문제가 여기서 풀린다.

| | HS256 | RS256 |
|---|---|---|
| 방식 | HMAC-SHA256 | RSA 서명 |
| 키 | 비밀키 하나를 나눠 갖는다 | 발급자는 개인키, 검증자는 공개키 |
| 검증자가 토큰을 만들 수 있나 | **만들 수 있다** | 못 만든다 |
| 키 배포 | 안전한 경로로 전달해야 한다 | 공개키라 그냥 뿌려도 된다 |

**검증하는 쪽이 여럿이면 RS256 이 맞다.** 게이트웨이 뒤에 여러 서비스가 붙어서 각자 토큰을 검증한다면, HS256 은 그 전부에게 발급 권한을 주는 셈이 된다.

`ES256`(ECDSA)과 `EdDSA`(Ed25519)도 같은 비대칭 계열이고 더 짧고 빠르다.

인증 서버가 개인키로 서명하면 게이트웨이는 **공개키만 받아두고** 검증한다. 인증 서버에 매번 물어보지 않아도 되고, 게이트웨이가 비밀을 들고 있을 필요도 없다.

## 이름들이 어디에 속하나

| 분류 | 대표 이름 | 쓰는 자리 |
|---|---|---|
| 해시 | **SHA-256**, SHA-3, BLAKE3 | 무결성 확인, 대조 |
| 느린 해시 | bcrypt, scrypt, **Argon2** | 비밀번호 저장 |
| MAC | **HMAC**(-SHA256), CMAC | 웹훅 검증, HS256 토큰 |
| 대칭 암호화 | **AES**, ChaCha20 | 자격증명 저장 |
| 인증된 암호화 | **AES-GCM**, ChaCha20-Poly1305, Fernet | 위 둘을 묶은 것 |
| 비대칭 서명 | **Ed25519**, ECDSA, RSA | JWT RS256, 인증서 |
| 키 교환 | **X25519**, ECDH | TLS 연결 수립 |
| 키 유도 | **PBKDF2**, HKDF, scrypt | 시크릿에서 실제 키를 만들 때 |

굵은 것이 지금 새로 고른다면 무난한 선택이다. 나머지는 기존 시스템에서 자주 마주친다.

헷갈리기 쉬운 짝이 넷 있다.

```
SHA-256 과 bcrypt    둘 다 해시인데 속도 목표가 반대다
HMAC 과 서명         둘 다 위조를 막는데 키가 하나냐 둘이냐가 다르다
AES 와 AES-GCM       뒤쪽은 AES 에 무결성 검사를 묶은 것이다
PBKDF2 와 bcrypt     앞은 키를 만들고 뒤는 대조용이다
```

마지막이 특히 헷갈렸다. 비밀번호를 저장할 때는 bcrypt 로 해시하고, 시크릿에서 암호화 키를 뽑을 때는 PBKDF2 로 유도한다. **둘 다 반복 계산으로 느리게 만들지만 결과를 쓰는 데가 다르다.**

## 무엇을 어디에 쓰나

```
비밀번호 저장            Argon2 또는 bcrypt + salt
게이트웨이 API 키 검증    SHA-256 해시        되돌릴 필요가 없다
프로바이더 API 키 저장    AES-GCM             나중에 원문이 필요하다
웹훅 진위 확인           HMAC-SHA256         키를 나눠 가진 사이
토큰 서명 (검증자 하나)   HS256               간단하다
토큰 서명 (검증자 여럿)   RS256 · EdDSA       공개키만 뿌리면 된다
전송 구간               TLS                  키 교환은 X25519
```

## 정리

```
해시     못 되돌린다. 대조와 무결성에 쓴다
         비밀번호에는 느린 해시와 salt 를 쓴다

MAC      비밀키를 아는 쪽만 만들 수 있다. 위조와 변조를 막는다
         키와 메시지를 직접 붙이지 말고 HMAC 을 쓴다
         비교는 시간이 일정한 함수로 한다

대칭     되돌린다. 내용을 숨긴다
         운용 모드가 여럿인데 ECB 는 쓰지 않는다
         변조는 못 막으므로 인증된 암호화를 쓴다

비대칭   키를 개인키와 공개키로 나눈다
         키를 미리 나눠 갖지 않아도 되고 만든 쪽을 부인할 수 없다
         느려서 데이터를 직접 암호화하지 않고 대칭키를 나르는 데 쓴다
```

다음은 이 도구들을 실제로 조합하는 단계다. **암호화 키를 어디에 두고 어떻게 바꿀지**가 남았다.
