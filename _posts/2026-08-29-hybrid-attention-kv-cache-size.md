## 토큰당 40 KiB 는 어디서 나오나

내 GPU 서버의 vLLM 컨테이너는 기동할 때 로그를 길게 남긴다.

```bash
docker logs vllm-ornith
```

거기 이런 두 줄이 있다.

```
Available KV cache memory: 6.08 GiB
GPU KV cache size: 159,296 tokens
```

같은 것을 다른 단위로 말한다. KV 캐시에 쓸 수 있는 공간이 6.08 GiB 고, 거기 토큰 159,296 개가 들어간다. `size` 인데 단위가 바이트가 아니라 개수다.

```
6.08 GiB ÷ 159,296 = 약 40 KiB
```

**토큰 하나가 40 KiB 를 차지한다.** 대화가 길어지면 이만큼씩 쌓인다.

[앞선 글](/posts/vllm-kv-cache-memory-breakdown/)은 여기서 멈췄다. 나눗셈만 한 것이다. 정작 vLLM 은 반대로 계산한다. 모델 구조를 보고 토큰당 크기를 먼저 구한 다음, 공간을 나눠 159,296 을 낸다.

그 토큰당 크기가 어디서 나오는지 파봤다.

## 어텐션이 저장하는 것

### Q · K · V 가 하는 일

모델은 답을 한 번에 뱉지 않는다. 토큰을 하나씩 만들고, 매번 지금까지의 모든 토큰을 참고한다.

참고하는 방식이 어텐션이다. 도서관에서 자료를 찾는 것과 구조가 같다.

```
Query   검색어      "나는 지금 무엇을 찾고 있는가"
Key     책 제목     "나는 이런 내용을 가진 토큰이다"
Value   책 내용     "나를 참고하면 이 정보를 준다"
```

셋은 같은 토큰에서 나온다. 토큰이 벡터로 바뀌면 서로 다른 행렬 세 개를 곱해 Q·K·V 를 만든다. 한 토큰이 검색하는 쪽도 되고 검색당하는 쪽도 되니 역할별로 따로 뽑는다.

```
영희가  사과를  집었다.  그것은  ___
                          ↑
                    지금 만들 토큰
```

`그것은` 다음에 올 말을 만들려면 **`그것`이 무엇을 가리키는지** 알아야 한다.

```
Q   "그것"이 가리키는 대상을 찾는다
    ↓ 앞의 토큰들과 하나씩 맞춰본다

K   "영희가"   →  사람. 잘 안 맞음
K   "사과를"   →  사물. 잘 맞음
K   "집었다"   →  동작. 잘 안 맞음
```

`사과를` 의 K 가 가장 잘 맞으니 그 토큰의 V 를 가장 많이 가져온다. 그렇게 모은 정보로 다음 토큰을 만든다. `빨갰다` 같은 게 나올 것이다.

<pre class="mermaid">
graph LR
  Q["'그것은'<br/>Query"]
  K1["'영희가'<br/>K · V"]
  K2["'사과를'<br/>K · V"]
  K3["'집었다'<br/>K · V"]
  K1 -. "약하게" .-> Q
  K2 == "강하게" ==> Q
  K3 -. "약하게" .-> Q
  Q --> OUT["다음 토큰"]
</pre>

한 곳만 고르는 게 아니라 전부에서 가중치만큼 가져온다. 잘 맞는 것에서 많이, 안 맞는 것에서 조금.

### K 와 V 만 캐시하는 이유

여기서 비대칭이 생긴다. **Q 는 지금 만들 토큰 것 하나면 되고, K 와 V 는 지금까지의 모든 토큰 것이 필요하다.**

토큰 1000개 대화에서 1001번째를 만든다고 하자. 캐시가 없으면 매번 앞의 전부를 다시 계산해야 한다.

```
캐시 없음   1001번째  →  토큰 1~1000 의 K·V 를 전부 다시 계산
            1002번째  →  토큰 1~1001 의 K·V 를 전부 다시 계산

캐시 있음   1001번째  →  저장해둔 걸 읽고 1001 것만 계산해 붙인다
            1002번째  →  저장해둔 걸 읽고 1002 것만 계산해 붙인다
```

앞 토큰들의 K 와 V 는 한 번 계산하면 바뀌지 않는다. **계산을 메모리와 맞바꾼 것**이고, 그 메모리가 KV 캐시다.

Q 는 지금 만드는 토큰 것만 쓰이고 다음 턴에는 쓸모가 없다. 그래서 저장하지 않는다.

### 헤드 16개에 KV 헤드 2개 (GQA)

한 레이어의 어텐션은 여러 갈래로 나뉘어 동시에 돈다. 이 갈래 하나가 **헤드**다. 도서관으로 치면 16명이 각자 다른 관심사로 같은 문장을 뒤진다.

```
헤드 1    문법 관계를 찾는다
헤드 2    지시어가 가리키는 대상을 찾는다
헤드 3    멀리 있는 단어와의 연결을 찾는다
```

처음 나온 어텐션은 헤드마다 Q·K·V 를 전부 따로 뒀다.

```
헤드 1     Q1 · K1 · V1
헤드 2     Q2 · K2 · V2
...
헤드 16    Q16 · K16 · V16
```

이게 **MHA**(Multi-Head Attention) 다. 헤드마다 자기 관점에 맞게 K 를 만드니 표현력은 가장 좋다.

문제는 **캐시에 쌓이는 게 K·V 뿐**이라는 것이다. K·V 가 16세트면 캐시도 16배다.

그래서 나온 게 **GQA**(Grouped-Query Attention) 다.

> Q 는 헤드 16개 그대로 두고, **K·V 만 2세트로 줄여서 헤드 8개가 한 세트씩 나눠 쓴다.**

```
헤드 1~8      Q1 ~ Q8     →   K1 · V1 을 공유
헤드 9~16     Q9 ~ Q16    →   K2 · V2 를 공유
```

이 K·V 세트 수를 **KV 헤드**라고 부른다. `config.json` 의 `num_key_value_heads` 가 이 값이고, 이 모델은 2다.

GQA 를 제안한 논문에 셋을 한 장에 그린 그림이 있다.

![MHA · GQA · MQA 비교](/assets/img/posts/gqa-mha-mqa.png)
_아래 파란 것이 Q, 위 두 줄이 K 와 V 다. 왼쪽 Multi-head 는 Q 마다 K·V 가 따로 있고, 오른쪽 Multi-query 는 전부가 하나를 공유한다. 가운데 Grouped-query 가 그 사이다._

> 출처: [GQA: Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints](https://arxiv.org/abs/2305.13245), Ainslie et al. (2023), Figure 2. [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/) · 흰 여백만 더함

그림은 Q 8개에 K·V 4개(2대 1)로 그렸다. **비율만 다르고 구조는 같다.** 이 모델은 Q 16개에 K·V 2개라 8대 1이다.

같은 K·V 를 봐도 Q 가 다르면 다른 것을 찾아온다. 8명이 같은 도서관에서 각자 다른 주제를 뒤지는 것과 같아서, 헤드 16개라는 다양성은 상당 부분 유지된다.

손해는 있다. 헤드 8개가 같은 K 를 공유하니 누군가는 자기 관심사에 덜 맞는 분류를 받는다. 그 손해로 캐시를 8분의 1로 줄이는 거래다.

극단으로 밀어 KV 헤드를 1개만 두면 **MQA**(Multi-Query Attention) 다. 캐시는 가장 적지만 손해가 커진다.

| | Q 헤드 | KV 헤드 | 캐시 | 표현력 |
|---|---|---|---|---|
| **MHA** | 16 | 16 | 가장 큼 | 가장 좋음 |
| **GQA 8:1** | 16 | **2** | **1/8** | 약간 손해 |
| **MQA** | 16 | 1 | 1/16 | 손해 큼 |

셋 다 Q 헤드는 16개다. 줄이는 것도 캐시에 쌓이는 것도 KV 헤드 쪽뿐이다. 8대 1은 요즘 흔한 비율이고 이 모델이 그 값이다.

## 토큰당 크기 계산

### 레이어 · KV 헤드 · 헤드 차원 · 자료형

토큰 하나가 저장해야 하는 숫자의 개수를 세면 크기가 나온다.

K 와 V 는 숫자 하나가 아니라 벡터다. 그 길이가 헤드 차원이고 이 모델은 256이다. 여기에 K·V 한 쌍, KV 헤드 2세트를 곱한다.

레이어마다 어텐션이 독립적이라 40번 더 곱한다. 1번 레이어는 원래 토큰을 보지만 2번은 1번이 변환한 결과를 본다. 같은 토큰이라도 레이어마다 다른 K·V 가 나오니, 나중에 참조하려면 40개분을 다 들고 있어야 한다.

마지막이 숫자 하나를 몇 바이트로 저장하느냐다. 기동 옵션에 `--kv-cache-dtype fp8` 을 줬으니 1바이트다. 원래 bf16 이면 2바이트인데 절반으로 줄여 담은 것이고, 이렇게 더 적은 비트로 담는 것을 **양자화**라고 한다.

| 단계 | 계산 | 누적 |
|---|---|---|
| 벡터 하나 | `head_dim` 256 | 숫자 256개 |
| K 와 V 한 쌍 | × 2 | 512개 |
| KV 헤드 2개 | × 2 | 1,024개 |
| 레이어 40개 | × 40 | **40,960개** |
| fp8 로 저장 | × 1바이트 | **40,960 바이트 = 40 KiB** |

```
토큰당 KV = 2 × 레이어 수 × KV 헤드 수 × 헤드 차원 × 자료형 바이트
            ↑     ↑          ↑           ↑
          K,V  레이어 수   KV 헤드 수    헤드 차원
```

### config.json 값으로 검산

위 값들은 모델을 받으면 같이 오는 `config.json` 에 적혀 있다.

```
num_hidden_layers      40
num_attention_heads    16
num_key_value_heads     2
head_dim              256
```

```
계산   2 × 40 × 2 × 256 × 1  =  40,960 바이트  =  40 KiB
측정   6.08 GiB ÷ 159,296    =  40.02 KiB
```

**맞았다.** 여기까지 쓰고 글을 끝낼 생각이었다.

## 레이어 40개 중 10개만 full attention 이었다

### linear attention 은 무엇을 저장하나

`config.json` 을 더 내려보다가 이걸 봤다.

```
layer_types              linear_attention 3개, full_attention 1개 반복
full_attention_interval  4
```

**레이어 40개가 다 같은 어텐션이 아니었다.** 4개마다 하나만 지금까지 설명한 어텐션이고, 나머지 셋은 `linear attention` 이라는 다른 방식이다.

```
레이어  1   2   3   4    5   6   7   8         37  38  39  40
     ·   ·   ·   ■    ·   ·   ·   ■   ···    ·   ·   ·   ■

■  full attention      10개    지금까지 설명한 그것
·  linear attention    30개    다른 방식
```

**차이는 요약을 하느냐다.**

```
full attention     이전 토큰들을 원본 그대로 남긴다
                   → 볼 때마다 전부 훑어서 필요한 것을 고른다

linear attention   이전 토큰들을 하나로 요약해서 남긴다
                   → 새 토큰이 오면 요약을 갱신한다
```

오는 사람을 기록한다고 하자. 같은 일을 두 방식으로 할 수 있다.

full attention 은 **방명록**이다. 온 사람을 한 줄씩 그대로 적는다. 원본이 남으니 나중에 아무 줄이나 정확히 다시 볼 수 있다. 대신 **사람이 늘면 장수가 늘어난다.**

linear attention 은 **화이트보드**다. 온 사람을 그대로 적는 게 아니라 "지금까지 누가 왔는지" 를 **요약해서 한 판에 유지한다.** 새 사람이 오면 그 요약을 고쳐 쓴다. 판 크기가 정해져 있으니 **아무리 많이 와도 넓어지지 않고, 대신 눌려 들어간 개별 정보는 돌아오지 않는다.**

```
full attention     토큰 1,000개  →  방명록 1,000줄   토큰 수에 비례
linear attention   토큰 1,000개  →  판 하나 그대로   토큰 수와 무관
```

**요약을 미리 하느냐 나중에 하느냐의 차이이기도 하다.** full attention 도 결국 여러 토큰에서 조금씩 가져와 하나로 합치지만, 그건 **읽을 때** 그때그때 한다. 원본이 남아 있으니 다음 토큰은 다른 조합으로 다시 합칠 수 있다. linear attention 은 **쓸 때** 미리 합쳐버려서 되돌릴 수 없다.

그래서 "3번째 토큰"을 콕 집어 볼 수 없다. 그 대가로 메모리를 아낀다.

판이 작다는 뜻은 아니다. **작은 게 아니라 안 자라는 것뿐이다.** 얼마나 큰지는 뒤에서 나온다.

### full 만 쓰거나 linear 만 쓰면

메모리만 다른 게 아니다. **계산량이 다르고, 이름도 거기서 왔다.**

full attention 은 새 토큰마다 앞의 토큰을 전부 훑는다. 1,000번째 토큰은 1,000개를 보고 2,000번째는 2,000개를 본다. 문장 전체로 치면 **토큰 수의 제곱**에 비례한다.

linear attention 은 새 토큰이 와도 판 하나를 갱신할 뿐이라 **토큰마다 드는 일이 일정하다.** 전체로는 토큰 수에 비례한다. linear 라는 이름이 여기서 나왔다.

| | full attention | linear attention |
|---|---|---|
| 이전 토큰 | 원본 그대로 남긴다 | 요약해서 하나로 합친다 |
| 토큰당 계산량 | 지금까지 토큰 수에 비례 | 일정 |
| 문장 전체 계산량 | 토큰 수의 **제곱** | 토큰 수에 **비례** |
| 저장 | 토큰마다 원본 K·V | 요약된 고정 크기 상태 |
| 특정 위치 조회 | 정확히 된다 | 안 된다 (요약에 눌림) |

그러면 전부 linear 로 하면 되지 않나 싶은데 마지막 줄이 걸린다. **"아까 그 숫자 뭐였지" 를 못 한다.** 긴 문서에서 특정 대목을 다시 짚는 일이 안 되면 쓸모가 크게 준다.

반대로 전부 full 로 하면 정확하지만 길이가 늘수록 계산과 메모리가 같이 터진다.

**그래서 섞는다.** 4개 중 3개는 싼 linear 로 흘려보내고 하나는 full 로 둬서, **정확히 조회할 수 있는 지점**을 주기적으로 만든다. `full_attention_interval: 4` 가 그 간격이다.

### Mamba 상태와 블록 크기 2,096 토큰

그러면 K·V 를 쌓는 건 full attention 레이어 10개뿐이니 계산이 이렇게 되어야 한다.

```
2 × 10 × 2 × 256 × 1 = 10,240 바이트 = 10 KiB
```

측정값의 4분의 1이다. 40 을 곱했는데 K·V 를 쌓는 레이어는 10개인데도 답이 맞았다. 남는 30 KiB 가 무엇인지부터 봐야 했다.

기동 로그를 다시 뒤졌더니 못 보고 지나친 줄들이 있었다.

```
Mamba cache mode is set to 'align' for Qwen3_5MoeForConditionalGeneration
Setting attention block size to 2096 tokens
  to ensure that attention page size is >= mamba page size
```

`Mamba` 는 SSM(State Space Model) 계열 아키텍처의 이름이다. 앞의 토큰을 전부 들고 있는 대신 **고정 크기 상태 하나에 압축해 토큰마다 갱신한다.** 앞에서 말한 메모가 이것이다.

이 모델의 linear attention 은 정확히는 [Gated DeltaNet](https://sebastianraschka.com/llm-architecture-gallery/hybrid-attention/) 이다. Mamba 와 계보는 다르지만 **고정 상태를 들고 간다는 성질이 같아서**, vLLM 은 이 부류를 통틀어 Mamba 로 부르고 같은 캐시 기계로 관리한다. Qwen 모델인데 로그에 Mamba 가 찍히는 이유다.

그래서 vLLM 은 full attention 의 KV 캐시와 linear attention 의 상태를 같은 메모리 풀에 넣는다.

둘은 크기 단위가 다르다. KV 는 토큰마다 자잘하게 쌓이고 Mamba 상태는 대화당 한 덩어리로 크다. 같은 풀에 넣으려면 페이지 크기를 맞춰야 한다.

여기서 **블록**이 나온다. vLLM 은 KV 캐시를 요청마다 통째로 떼어주지 않고, 고정 크기 조각으로 잘라두고 필요한 만큼 빌려준다. 그 조각이 블록이고, 이 방식을 PagedAttention 이라고 부른다. [3편](/posts/llm-serving-engine-comparison/)에 썼다.

**블록 크기는 보통 16 토큰이다.** 그런데 이 모델은 그렇지 않았다.

```
보통 vLLM 블록 크기    16 토큰
이 모델              2,096 토큰
```

131배다. full attention 쪽 블록을 Mamba 쪽에 맞춰 키운 것이고, 숫자도 떨어진다.

```
159,296 ÷ 2,096 = 76 블록
```

추측이 아니라 [vLLM 이 문서에 적어둔 동작](https://vllm.ai/blog/2025-09-11-qwen3-next)이다.

> full attention 레이어의 논리 블록 크기를 자동으로 조정해서,
> full attention 과 linear attention 의 상태가 같은 크기의 물리 메모리를 쓰게 한다.

즉 "토큰당 40 KiB" 는 full attention 만의 비용이 아니다. Mamba 상태까지 합친 총량을 토큰 수로 나눈 값이다.

```
토큰당 40 KiB
  ├─ KV 캐시 (full attention 10개)   10 KiB
  └─ Mamba 상태 (linear 30개) 의 몫   30 KiB
```

### 레이어 40개 전부에 같은 크기 페이지를 잡는다

블록 하나에서 레이어 하나가 차지하는 자리를 계산해봤다.

```
2,096 토큰 × 2(K,V) × 2(KV 헤드) × 256 × 1바이트 = 2.05 MiB
```

`align` 이 하는 일이 **linear 레이어에도 이 크기를 똑같이 주는 것**이다. 그래야 한 풀에서 아무 자리나 꺼내 쓸 수 있다. 그러면 블록 하나가 레이어 40개분 자리를 잡는다.

| | 블록당 | × 76블록 |
|---|---|---|
| full attention 10개만 잡는다면 | 20.5 MiB | 1.52 GiB |
| 레이어 40개 전부 잡는다면 | 81.9 MiB | **6.08 GiB** |

로그의 6.08 GiB 다. 블록 수도 딱 떨어진다.

```
159,296 ÷ 2,096 = 76 블록
```

비유로 돌리면 **화이트보드 한 판이 방명록 2,096줄과 같은 자리를 차지하도록** vLLM 이 맞춰놓은 것이다. 판이 작아서 싼 게 아니라, 줄 수가 늘어도 그 자리가 안 늘어나서 싸다.

**그러니 ×40 은 맞는 계산이었다.** 다만 뜻이 내가 생각한 것과 달랐다. 레이어 40개가 전부 K·V 를 쌓아서가 아니라, **vLLM 이 40개 전부에 같은 크기 자리를 잡아두기 때문이다.** 나머지 30개는 그 자리에 토큰마다 쌓는 대신 고정 상태를 넣는다.

### 동시 처리 8.00x 의 근거

로그에 이런 줄이 있다.

```
Maximum concurrency for 65,536 tokens per request: 8.00x
```

컨텍스트를 꽉 채운 요청을 여덟 개까지 동시에 받는다는 뜻이다. 그런데 명목대로 나누면 안 맞는다.

```
159,296 ÷ 65,536 = 2.43
```

차이는 **자리를 빌리는 방식**이다. full attention 레이어는 토큰이 늘면 블록을 더 빌리지만, linear attention 레이어는 대화가 길어져도 판 하나면 된다. 요청 하나가 실제로 쓰는 자리를 세보면 이렇다.

```
풀 전체       76 블록 × 40 레이어       =  3,040 자리

요청 하나 (65,536 토큰)
  full        32 블록 × 10 레이어       =    320 자리   ← 길이에 비례
  linear      30 레이어 × 상태 2개      =     60 자리   ← 길이와 무관
                                          ---------
                                             380 자리

3,040 ÷ 380 = 8.00
```

**로그의 8.00x 와 정확히 같다.**

linear 레이어가 상태를 2개 쓰는 건 Gated DeltaNet 이 **conv 상태와 순환 상태를 따로 들고 가기 때문**으로 보인다. 1개로 잡으면 8.69 가 나와서 안 맞는다.

> 여기부터는 추론이다. 로그가 직접 말해주는 건 블록 크기 2,096 까지고, **레이어 40개 전부에 같은 페이지를 잡는다는 것과 linear 상태가 2개라는 것은 숫자가 맞아떨어지는 걸로 세운 가설이다.** 아래 숫자들도 그 위에 서 있다. vLLM 코드를 열어야 확정된다.

같은 계산을 길이별로 해보면 이렇게 나온다.

<pre class="mermaid">
xychart-beta
  title "요청 하나가 잡는 자리 (MiB)"
  x-axis "컨텍스트 길이" [8K, 16K, 32K, 65K]
  y-axis "MiB" 0 --> 700
  bar [82, 164, 328, 655]
  line [123, 123, 123, 123]
</pre>

막대가 full attention 레이어의 KV 캐시고, 선이 linear attention 레이어의 상태다. **full 쪽은 길이를 따라 오르고 linear 쪽은 123 MiB 에서 움직이지 않는다.** 8K 에서는 linear 쪽이 더 크고, 12K 언저리에서 뒤집힌다.

| 컨텍스트 | full attention | linear attention | 합 | linear 비중 |
|---|---|---|---|---|
| 8K | 82 | 123 | 205 | **60%** |
| 16K | 164 | 123 | 287 | 43% |
| 32K | 328 | 123 | 450 | 27% |
| 65K | 655 | 123 | 778 | **16%** |

짧은 대화에서는 linear 쪽이 자리의 60% 를 먹는다. **하이브리드가 이득인 건 컨텍스트가 길 때뿐이다.**

명목 회계는 이 123 MiB 를 토큰마다 나눠 붙인다. 그래서 **긴 요청일수록 실제보다 비싸게 매겨지고**, 실제 동시 처리량은 그만큼 늘어난다.

## GQA · fp8 · 하이브리드가 내준 것

셋 다 메모리를 줄이지만 **공짜로 줄이지는 않는다.** 절약이 아니라 맞바꾸기다.

**토큰당 자리를 직접 줄인 건 둘이다.**

| | 줄인 만큼 | 내준 것 | 정하는 쪽 |
|---|---|---|---|
| GQA 8:1 | 캐시 **8분의 1** | Q 헤드마다 자기 K·V 를 갖던 표현력 | 모델 · `num_key_value_heads` |
| fp8 **양자화** | 캐시 **절반** | 수치 정밀도 | 나 · `--kv-cache-dtype` |

곱셈이라 겹치면 16배다. 이 둘이 없었으면 토큰당 40 KiB 가 640 KiB 였고, 6.08 GiB 에 **토큰 1만 개도 못 담는다.** 컨텍스트 65,536 짜리 대화는 하나도 온전히 못 받는다.

**하이브리드는 줄이는 대상이 다르다.** 앞에서 본 대로 vLLM 은 레이어 40개 전부에 같은 크기 페이지를 잡으므로, 풀에 담기는 토큰 수는 하이브리드여도 안 바뀐다. 159,296 그대로다.

달라지는 건 요청 하나가 자리를 얼마나 붙잡느냐다.

| 65,536 토큰 요청 하나 | 잡는 자리 | 동시 처리 |
|---|---|---|
| 전부 full attention 이라면 | 1,280 | 2.38x |
| 하이브리드 | 380 | **8.00x** |

| | 줄인 만큼 | 내준 것 | 정하는 쪽 |
|---|---|---|---|
| 하이브리드 4:1 | 동시 처리 **3.4배**, 계산량 제곱 → 비례 | 임의 위치를 정확히 조회하는 능력 | 모델 · `layer_types` |

**용량이 아니라 동시 처리량을 산다.** GQA·fp8 과 같은 종류가 아니라서 곱해서 합치면 안 된다.

가중치만으로 65.53 GiB 를 먹어서 KV 에 6 GiB 밖에 안 남는 기계다. GQA 와 fp8 이 없었으면 긴 대화를 하나도 못 받고, 하이브리드가 없었으면 두 개 남짓밖에 못 받는다.

그래서 **다른 모델을 올리면 토큰당 40 KiB 는 안 나온다.** 계산하는 방법만 같고 값은 전부 바뀐다. 블록이 2,096 인 것도 하이브리드라서지, 아닌 모델은 기본 16 토큰이고 그 로그 줄 자체가 안 나온다.

## 확인한 것과 남은 것

이 글은 "계산이 맞았다" 로 끝날 예정이었다. `config.json` 을 끝까지 읽고 나서야 **왜 맞았는지는 다른 이야기**라는 걸 알았다.

```
✓  KV 캐시가 왜 필요한가                      계산을 메모리와 맞바꾼 것
✓  크기가 무엇으로 정해지는가                  레이어 · KV 헤드 · 헤드 차원 · 자료형
✓  이 모델은 하이브리드다                      레이어 40개 중 10개만 full attention, 나머지는 Gated DeltaNet
✓  블록이 2,096 토큰인 이유                    Mamba 페이지에 맞춤
?  왜 ×40 이 맞았는가                          레이어 40개 전부에 같은 자리를 잡는 듯
?  8.00x 는 어디서 나오는가                    3,040 ÷ 380 이면 떨어짐
?  linear 레이어의 상태가 정말 2개인가          숫자는 맞는데 코드로는 미확인
```

아래 셋은 **로그가 말해준 게 아니라 산술이 맞아떨어져서 세운 가설이다.** 6.08 GiB 도 8.00x 도 소수점까지 재현되니 우연은 아닐 텐데, 확정하려면 vLLM 코드를 열어야 한다. 다음 편에서 볼 생각이다.

하나는 확실해졌다. **모델을 고를 때 파라미터 수만 보면 안 된다.** **같은 GPU 에 같은 vLLM 을 올려도 `layer_types` 와 `num_key_value_heads` 가 받을 수 있는 대화 수를 몇 배씩 바꾼다.** 다음에 모델을 고를 때는 config 를 먼저 열 생각이다.
