## KV 캐시에 쌓이는 것

대화를 하면 GPU 메모리에 숫자가 쌓인다. 그게 무엇인지부터 짚는다.

입력한 글은 먼저 토큰으로 쪼개진다.

```
"영희가 사과를 집었다"   →   [영희가] [사과를] [집었다]
```

토큰 하나가 모델을 통과하면 그 토큰을 나타내는 숫자 뭉치가 만들어진다. 이름이 K 와 V 다. 다음 토큰을 만들 때 앞의 토큰들을 다시 참고해야 하므로, 이걸 버리지 않고 GPU 메모리에 쌓아둔다. **그 쌓아둔 것이 KV 캐시다.**

버리면 매번 처음부터 다시 계산해야 하는데 그게 훨씬 비싸다. 그 대신 대화가 길어질수록 메모리가 는다.

```
대화   1,000 토큰   →   40 MB
대화  65,000 토큰   →   2.5 GB
```

토큰 하나가 얼마를 남기느냐가 이 글의 주제다. 내 서버는 40 KiB 인데 그 값이 어디서 오는지 본다.

## 로그가 말하는 토큰당 40 KiB

내 GPU 서버의 vLLM 컨테이너는 기동할 때 로그를 길게 남긴다.

```bash
docker logs vllm-ornith
```

```
Available KV cache memory: 6.08 GiB
GPU KV cache size: 159,296 tokens
```

KV 캐시에 쓸 수 있는 공간이 6.08 GiB 고, 거기 토큰 159,296 개가 들어간다. `size` 인데 단위가 바이트가 아니라 개수다.

```
6.08 GiB ÷ 159,296 = 약 40 KiB
```

**토큰 하나가 40 KiB 를 차지한다.** 대화가 길어지면 이만큼씩 쌓인다.

[GPU 메모리 배분을 본 글](/posts/vllm-kv-cache-memory-breakdown/)은 여기서 멈췄다. 나눗셈만 한 것이다. 정작 vLLM 은 반대로 계산한다. 모델 구조를 보고 토큰당 크기를 먼저 구한 다음, 공간을 나눠 159,296 을 낸다.

**결론부터 적으면 이 40 KiB 는 모델 구조만으로 나오는 값이 아니다.** 공식대로 계산하면 40 KiB 가 맞는데, 정작 이 모델에서 토큰마다 K·V 를 쌓는 레이어는 40개 중 10개뿐이다.

이 순서로 확인한다.

```
1  KV 크기를 정하는 것        Q·K·V · GQA · 레이어 · 자료형
2  공식대로 계산하고 검산      40 KiB, 측정값과 맞는다
3  그런데 맞을 리 없는 계산    full attention 이 10개뿐이다
```

## attention 이 저장하는 것

모델은 같은 구조를 여러 겹 쌓아 만든다. 그 한 겹이 **레이어**고, 토큰은 40겹을 순서대로 통과하면서 조금씩 다듬어진다. 겹마다 attention 이 한 번씩 돈다.

```
attention    앞 토큰들을 참조해서 다음 토큰을 만드는 동작
   │  이 동작에 앞 토큰들의 K·V 가 필요하다
K · V        앞 토큰들이 남긴 재료
   │  매번 다시 계산하면 느리니 저장해둔다
KV 캐시      그 재료를 담아둔 GPU 메모리
   │  얼마나 담아야 하나
KV 헤드      K·V 가 몇 세트인가. 캐시 크기를 정하는 수
```

아래 세 소절이 이 순서다.

### Q · K · V 가 하는 일

모델은 답을 한 번에 뱉지 않는다. 토큰을 하나씩 만들고, 매번 지금까지의 모든 토큰을 참고한다.

참고하는 방식이 attention 이다. 이름은 key-value 저장소에서 왔다. 키를 주면 값을 꺼내주는 그 구조다.

```
key-value store   키를 주면          값을 준다
attention         Q 를 주면   K 와 맞춰서   V 를 준다
```

도서관에 놓으면 이렇다.

```
Query   검색어      "나는 지금 무엇을 찾고 있는가"
Key     책 제목     "나는 이런 내용을 가진 토큰이다"
Value   책 내용     "나를 참고하면 이 정보를 준다"
```

Q 는 **이 토큰이 자기 뜻을 정하려고 앞에서 무엇을 찾아야 하는가**다. 문장 하나를 넣어도 모델 안에서는 토큰마다 따로 생긴다.

```
입력      "영희가 사과를 집었다. 그것은"
토큰      [영희가] [사과를] [집었다] [그것은]

`집었다` 의 Q    누가 집었지, 뭘 집었지
`그것은` 의 Q    내가 가리키는 게 뭐지
```

셋은 같은 토큰에서 나온다. 한 토큰이 검색하는 쪽도 되고 검색당하는 쪽도 되니, 토큰 벡터에 행렬 세 개를 각각 곱해 역할별로 뽑는다.

```
토큰 벡터  × W_Q  →  Q       W = 가중치 행렬
           × W_K  →  K       학습으로 정해진 숫자표
           × W_V  →  V       모델 파일에 들어 있다
```

```
영희가  사과를  집었다.  그것은  ___
                          ↑
                    지금 만들 토큰
```

`그것은` 다음에 올 말을 만들려면 **`그것`이 무엇을 가리키는지** 알아야 한다.

```
Q   "그것"이 가리키는 대상을 찾는다
    ↓ 앞의 토큰들과 하나씩 맞춰본다

K   "영희가"   →  사람. 잘 안 맞음
K   "사과를"   →  사물. 잘 맞음
K   "집었다"   →  동작. 잘 안 맞음
```

`사과를` 의 K 가 가장 잘 맞으니 그 토큰의 V 를 가장 많이 가져온다. 그렇게 모은 정보로 다음 토큰을 만든다. `빨갰다` 같은 게 나올 것이다.

<pre class="mermaid">
graph LR
  Q["'그것은'<br/>Query"]
  K1["'영희가'<br/>K · V"]
  K2["'사과를'<br/>K · V"]
  K3["'집었다'<br/>K · V"]
  K1 -. "약하게" .-> Q
  K2 == "강하게" ==> Q
  K3 -. "약하게" .-> Q
  Q --> OUT["다음 토큰"]
</pre>

한 곳만 고르는 게 아니라 전부에서 가중치만큼 가져온다. 잘 맞는 것에서 많이, 안 맞는 것에서 조금.

### K 와 V 만 캐시하는 이유

토큰 하나를 만들 때 앞의 토큰들은 **K 와 V 로만 참여한다.** 새 토큰이 Q 를 들고 앞의 K 들과 맞춰본 뒤 V 를 가져오니, 계산 어디에도 앞 토큰의 Q 는 등장하지 않는다. 앞 토큰의 Q 는 그 토큰을 만들 때 한 번 쓰이고 끝났다.

그래서 **K 와 V 만 쌓인다.** 토큰 1000개 대화에서 1001번째를 만든다고 하자. 캐시가 없으면 매번 앞의 전부를 다시 계산해야 한다.

```
캐시 없음   1001번째  →  토큰 1~1000 의 K·V 를 전부 다시 계산
            1002번째  →  토큰 1~1001 의 K·V 를 전부 다시 계산

캐시 있음   1001번째  →  저장해둔 걸 읽고 1001 것만 계산해 붙인다
            1002번째  →  저장해둔 걸 읽고 1002 것만 계산해 붙인다
```

앞 토큰들의 K 와 V 는 한 번 계산하면 바뀌지 않는다. **계산을 메모리와 맞바꾼 것**이고, 그 메모리가 KV 캐시다.

가중치와는 성질이 다르다. **가중치는 한 번 올려두고 모두가 같이 쓰지만, K·V 는 내 토큰에서 나오니 대화마다 따로 쌓인다.** [GPU 메모리 배분을 본 글](/posts/vllm-kv-cache-memory-breakdown/)에서 메모리가 `가중치 65.53 GiB` 와 `KV 캐시 6.08 GiB` 로 갈렸던 게 이 차이다.

### 헤드 16개에 KV 헤드 2개 (GQA)

한 레이어의 attention 은 여러 갈래로 나뉘어 동시에 돈다. 이 갈래 하나가 **헤드**다. 도서관으로 치면 16명이 각자 다른 관심사로 같은 문장을 뒤진다.

```
헤드 1    문법 관계를 찾는다
헤드 2    지시어가 가리키는 대상을 찾는다
헤드 3    멀리 있는 단어와의 연결을 찾는다
```

처음 나온 attention 은 헤드마다 Q·K·V 를 전부 따로 뒀다.

```
헤드 1     Q1 · K1 · V1
헤드 2     Q2 · K2 · V2
...
헤드 16    Q16 · K16 · V16
```

이게 **MHA**(Multi-Head Attention) 다. 헤드마다 자기 관점에 맞게 K 를 만드니 표현력은 가장 좋다.

**캐시 크기를 정하는 건 K·V 개수뿐이다.** Q 는 헤드가 몇 개든 쌓이지 않는다. MHA 는 K·V 가 16세트라 캐시도 16배가 된다. 줄이려면 K·V 쪽을 건드려야 한다.

그래서 나온 게 **GQA**(Grouped-Query Attention) 다.

> Q 는 헤드 16개 그대로 두고, **K·V 만 2세트로 줄여서 헤드 8개가 한 세트씩 나눠 쓴다.**

```
헤드 1~8      Q1 ~ Q8     →   K1 · V1 을 공유
헤드 9~16     Q9 ~ Q16    →   K2 · V2 를 공유
```

이 K·V 세트 수를 **KV 헤드**라고 부른다. `config.json` 의 `num_key_value_heads` 가 이 값이고, 이 모델은 2다.

GQA 를 제안한 논문에 셋을 한 장에 그린 그림이 있다.

![MHA · GQA · MQA 비교](/assets/img/posts/gqa-mha-mqa.png)
_아래 파란 것이 Q, 위 두 줄이 K 와 V 다. 왼쪽 Multi-head 는 Q 마다 K·V 가 따로 있고, 오른쪽 Multi-query 는 전부가 하나를 공유한다. 가운데 Grouped-query 가 그 사이다._

> 출처: [GQA: Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints](https://arxiv.org/abs/2305.13245), Ainslie et al. (2023), Figure 2. [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/) · 흰 여백만 더함

그림은 Q 8개에 K·V 4개(2대 1)로 그렸다. **비율만 다르고 구조는 같다.** 이 모델은 Q 16개에 K·V 2개라 8대 1이다.

같은 K·V 를 봐도 Q 가 다르면 다른 것을 찾아온다. 8명이 같은 도서관에서 각자 다른 주제를 뒤지는 것과 같아서, 헤드 16개라는 다양성은 상당 부분 유지된다.

손해는 있다. 헤드 8개가 같은 K 를 공유하니 누군가는 자기 관심사에 덜 맞는 분류를 받는다. 그 손해로 캐시를 8분의 1로 줄이는 거래다.

극단으로 밀어 KV 헤드를 1개만 두면 **MQA**(Multi-Query Attention) 다. 캐시는 가장 적지만 손해가 커진다.

| | Q 헤드 | KV 헤드 | 캐시 | 표현력 |
|---|---|---|---|---|
| **MHA** | 16 | 16 | 가장 큼 | 가장 좋음 |
| **GQA 8:1** | 16 | **2** | **1/8** | 약간 손해 |
| **MQA** | 16 | 1 | 1/16 | 손해 큼 |

셋 다 Q 헤드는 16개다. 줄이는 것도 캐시에 쌓이는 것도 KV 헤드 쪽뿐이다. 8대 1은 요즘 흔한 비율이고 이 모델이 그 값이다.

## 토큰당 크기 계산

토큰 하나가 40개 레이어를 지나는 동안 무엇이 남고 무엇이 버려지는지부터 보면 계산이 쉽다.

레이어 하나 안에서는 이렇게 돈다.

<pre class="mermaid">
graph LR
  V["토큰 벡터"] --> Q1["Q1"]
  V --> Q2["Q2"]
  V --> QD["⋯"]
  V --> Q16["Q16"]
  Q1 --> M["16개 결과를<br/>이어붙임"]
  Q2 --> M
  QD --> M
  Q16 --> M
  M --> OUT["벡터 1개<br/>다음 레이어로"]
  V -.-> KV["K · V<br/>캐시에 남긴다"]
</pre>

**16갈래가 동시에 돌고 그 층 끝에서 합쳐진다.** 다음 레이어로 넘어가는 건 벡터 하나고, Q 16개는 거기서 버려진다. 캐시에 남는 건 K·V 뿐이다.

```
레이어 1개 · 토큰 1개
  남긴다   K · V   1 KiB
  버린다   Q       16개

× 40 레이어
  남은 것   40 KiB      ← 이게 KV 캐시
  버린 것   Q 640개
```

**헤드 16개는 계산량에만 들어가고 메모리에는 안 들어간다.** 캐시에 남는 건 K·V 뿐이고, 그건 KV 헤드 2개로 정해진다.

### 레이어 · KV 헤드 · 헤드 차원 · 자료형

토큰 하나가 저장해야 하는 숫자의 개수를 세면 크기가 나온다.

K 와 V 는 숫자 하나가 아니라 벡터다. 그 길이가 헤드 차원이고 이 모델은 256이다. 여기에 K·V 한 쌍, KV 헤드 2세트를 곱한다.

**같은 토큰이라도 레이어마다 다른 K·V 가 나온다.** 그래서 40번 더 곱한다.

이유가 둘이다. 레이어마다 **자기 `W_K` · `W_V` 를 따로** 갖고, 받는 입력도 다르다. 1번은 원래 토큰 벡터를 받지만 2번은 1번이 바꿔놓은 결과를 받는다.

```
1번 레이어    원래 토큰 벡터를 받는다      K: "과일 명사" 쪽
20번 레이어   앞에서 다듬어진 벡터를 받는다  K: "영희가 집은 대상" 쪽
```

20번 레이어가 1번의 K 를 빌려 쓸 수 없다. 다른 기준으로 만들어진 값이라서다.

Q 도 마찬가지다. **앞 층의 결과가 다음 층의 질문을 만든다.** 40번 같은 걸 묻는 게 아니라, 층마다 맥락을 덧붙이며 다듬어간다. 그래서 레이어는 건너뛸 수 없고 순서대로 통과해야 한다.

마지막이 숫자 하나를 몇 바이트로 저장하느냐다. 기동 옵션에 `--kv-cache-dtype fp8` 을 줬으니 1바이트다. 원래 bf16 이면 2바이트인데 절반으로 줄여 담은 것이고, 이렇게 더 적은 비트로 담는 것을 **양자화**라고 한다.

| 단계 | 계산 | 누적 |
|---|---|---|
| 벡터 하나 | `head_dim` 256 | 숫자 256개 |
| K 와 V 한 쌍 | × 2 | 512개 |
| KV 헤드 2개 | × 2 | 1,024개 |
| 레이어 40개 | × 40 | **40,960개** |
| fp8 로 저장 | × 1바이트 | **40,960 바이트 = 40 KiB** |

중간의 `1,024개` 가 **레이어 하나가 토큰 하나에 남기는 양**이다. fp8 이면 1,024 바이트, 곧 1 KiB 다. 여기에 레이어 수를 곱한 게 40 KiB 다.

```
토큰당 KV = 2 × 레이어 수 × KV 헤드 수 × 헤드 차원 × 자료형 바이트
            ↑     ↑          ↑           ↑
          K,V  레이어 수   KV 헤드 수    헤드 차원
```

### config.json 값으로 검산

위 값들은 모델을 받으면 같이 오는 `config.json` 에 적혀 있다.

```
num_hidden_layers      40
num_attention_heads    16
num_key_value_heads     2
head_dim              256
```

```
계산   2 × 40 × 2 × 256 × 1  =  40,960 바이트  =  40 KiB
측정   6.08 GiB ÷ 159,296    =  40.02 KiB
```

**맞았다.** 여기까지 쓰고 글을 끝낼 생각이었다.

## 레이어 40개 중 10개만 full attention

### linear attention 의 저장 방식

`config.json` 을 더 내려보다가 이걸 봤다.

```
layer_types              linear_attention 3개, full_attention 1개 반복
full_attention_interval  4
```

**레이어 40개가 다 같은 attention 이 아니었다.** 4개마다 하나만 지금까지 설명한 그것이고, 나머지 셋은 `linear attention` 이라는 다른 방식이다.

```
레이어  1   2   3   4    5   6   7   8         37  38  39  40
     ·   ·   ·   ■    ·   ·   ·   ■   ···    ·   ·   ·   ■

■  full attention      10개    지금까지 설명한 그것
·  linear attention    30개    다른 방식
```

**차이는 요약을 하느냐다.**

```
full attention     이전 토큰들을 원본 그대로 남긴다
                   → 볼 때마다 전부 훑어서 필요한 것을 고른다

linear attention   이전 토큰들을 하나로 요약해서 남긴다
                   → 새 토큰이 오면 요약을 갱신한다
```

오는 사람을 기록한다고 하자. 같은 일을 두 방식으로 할 수 있다.

full attention 은 **방명록**이다. 온 사람을 한 줄씩 그대로 적는다. 원본이 남으니 나중에 아무 줄이나 정확히 다시 볼 수 있고, 대신 사람이 늘면 장수가 늘어난다.

linear attention 은 **화이트보드**다. 온 사람을 그대로 적는 게 아니라 "지금까지 누가 왔는지" 를 요약해서 한 판에 유지한다. 새 사람이 오면 그 요약을 고쳐 쓴다. 판 크기가 정해져 있으니 아무리 많이 와도 넓어지지 않고, 대신 눌려 들어간 개별 정보는 돌아오지 않는다.

판은 레이어마다 하나씩 따로다. **linear 레이어가 30개면 판도 30개**고, 서로 내용을 주고받지 않는다. 3번 레이어가 요약한 걸 5번이 이어받는 게 아니라, 5번은 자기 입력으로 자기 요약을 새로 만든다.

```
full attention     토큰 1,000개  →  방명록 1,000줄   토큰 수에 비례
linear attention   토큰 1,000개  →  판 하나 그대로   토큰 수와 무관
```

**요약을 미리 하느냐 나중에 하느냐의 차이이기도 하다.** full attention 도 결국 여러 토큰에서 조금씩 가져와 하나로 합치지만, 그건 읽을 때 그때그때 한다. 원본이 남아 있으니 다음 토큰은 다른 조합으로 다시 합칠 수 있다. linear attention 은 쓸 때 미리 합쳐버려서 되돌릴 수 없다.

그래서 "3번째 토큰"을 콕 집어 볼 수 없다. 그 대가로 메모리를 아낀다.

**판이 작은 게 아니라 안 자라는 것뿐이다.** 얼마나 큰지는 뒤에서 나온다.

### full attention 과 linear attention 비교

메모리만 다른 게 아니다. **계산량이 다르고, 이름도 거기서 왔다.**

full attention 은 새 토큰마다 앞의 토큰을 전부 훑는다. 1,000번째 토큰은 1,000개를 보고 2,000번째는 2,000개를 본다. 문장 전체로 치면 **토큰 수의 제곱**에 비례한다.

linear attention 은 새 토큰이 와도 판 하나를 갱신할 뿐이라 **토큰마다 드는 일이 일정하다.** 전체로는 토큰 수에 비례한다. linear 라는 이름이 여기서 나왔다.

| | full attention | linear attention |
|---|---|---|
| 이전 토큰 | 원본 그대로 남긴다 | 요약해서 하나로 합친다 |
| 토큰당 계산량 | 지금까지 토큰 수에 비례 | 일정 |
| 문장 전체 계산량 | 토큰 수의 **제곱** | 토큰 수에 **비례** |
| 저장 | 토큰마다 원본 K·V | 요약된 고정 크기 상태 |
| 특정 위치 조회 | 정확히 된다 | 안 된다 (요약에 눌림) |

그러면 전부 linear 로 하면 되지 않나 싶은데 마지막 줄이 걸린다. **"아까 그 숫자 뭐였지" 를 못 한다.** 긴 문서에서 특정 대목을 다시 짚는 일이 안 되면 쓸모가 크게 준다.

반대로 전부 full 로 하면 정확하지만 길이가 늘수록 계산과 메모리가 같이 터진다.

**그래서 섞는다.** 4개 중 3개는 linear 로 싸게 처리하고 하나만 full 로 둔다. `full_attention_interval: 4` 가 그 간격이다.

linear 레이어를 셋 지나도 정확한 조회가 가능한 건, **토큰마다 자기 벡터가 레이어를 타고 끝까지 흐르기 때문**이다. linear 레이어가 요약하는 건 다른 토큰을 참조하는 방식이지 토큰 자체가 아니다. 그래서 4번째 레이어에 오면 앞의 모든 토큰을 다시 정확히 짚을 수 있다.

### 40 KiB 와 실제 증가분 10 KiB

K·V 를 토큰마다 쌓는 건 full attention 레이어 10개뿐이니 계산이 이렇게 되어야 한다.

```
2 × 10 × 2 × 256 × 1 = 10,240 바이트 = 10 KiB
```

**측정값의 4분의 1이다.** 대화가 길어질 때 실제로 토큰마다 늘어나는 양은 10 KiB 다. 나머지 30 개 레이어는 길이와 무관한 고정 크기 상태를 가진다.

그런데 앞의 `2 × 40 × 2 × 256 × 1` 도 측정값과 맞았다. 둘 다 맞을 수는 없다.

```
공식대로        40 KiB     로그의 6.08 GiB ÷ 159,296 과 일치
실제 증가분     10 KiB     K·V 를 쌓는 레이어만 세면
```

**그러니 로그의 40 KiB 는 모델이 무엇을 저장하느냐가 아니라, vLLM 이 그 자리를 어떻게 잡느냐에서 나온 값이다.** 여기서부터는 모델 구조가 아니라 엔진 이야기라 [따로 정리했다](/posts/vllm-kv-cache-startup/).

## GQA · fp8 · hybrid 가 내준 것

셋 다 메모리를 줄이지만 **공짜로 줄이지는 않는다.** 절약이 아니라 맞바꾸기다.

**토큰당 자리를 직접 줄인 건 둘이다.**

| | 줄인 만큼 | 내준 것 | 정하는 쪽 |
|---|---|---|---|
| GQA 8:1 | 캐시 **8분의 1** | Q 헤드마다 자기 K·V 를 갖던 표현력 | 모델 · `num_key_value_heads` |
| fp8 **양자화** | 캐시 **절반** | 수치 정밀도 | 나 · `--kv-cache-dtype` |

곱셈이라 겹치면 16배다. 길이에 따라 늘어나는 양이 지금은 토큰당 10 KiB 인데 이 둘이 없었으면 **160 KiB** 다. 컨텍스트 65,536 짜리 대화 하나가 10 GiB 를 먹는다는 뜻이고, KV 에 6.08 GiB 밖에 없는 기계에서는 하나도 온전히 못 받는다.

**hybrid 는 줄이는 대상이 다르다.**

| | 줄인 만큼 | 내준 것 | 정하는 쪽 |
|---|---|---|---|
| hybrid 4:1 | 길이에 비례하는 증가분을 **4분의 1** 로, 계산량을 제곱에서 비례로 | 임의 위치를 정확히 조회하는 능력 | 모델 · `layer_types` |

GQA·fp8 은 토큰 하나의 크기를 줄이고, hybrid 는 **길이를 따라 자라는 부분**을 줄인다. 종류가 달라서 곱해서 합치면 안 된다.

그래서 **다른 모델을 올리면 토큰당 크기가 달라진다.** 계산하는 방법만 같고 값은 전부 바뀐다.

## 정리

```
KV 캐시가 왜 필요한가        앞 토큰의 K·V 는 안 바뀐다. 계산을 메모리와 맞바꾼 것

일반 공식                    2 × 레이어 수 × KV 헤드 수 × 헤드 차원 × 자료형 바이트
레이어 40개를 넣으면          40 KiB      vLLM 로그와 일치
실제 증가분                   10 KiB      full attention 10개 × 1 KiB
남은 차이                     vLLM 의 그룹·블록 할당에서 생긴다

모델이 정하는 값             레이어 40 · KV 헤드 2 · 헤드 차원 256 · layer_types
내가 정하는 값               --kv-cache-dtype fp8
```

`남은 차이` 는 모델이 아니라 엔진 이야기라 [따로 정리했다](/posts/vllm-kv-cache-startup/).

**같은 GPU 에 같은 vLLM 을 올려도 `layer_types` 와 `num_key_value_heads` 가 받을 수 있는 대화 수를 몇 배씩 바꾼다.** 파라미터 수만 보고 고를 게 아니었다.
