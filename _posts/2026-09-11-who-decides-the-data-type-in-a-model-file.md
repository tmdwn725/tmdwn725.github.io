## 앞 글이 남긴 질문

[내 서버 설정을 하나씩 따져본 글](/posts/how-local-llm-inference-actually-works/)에서 자료형이 이렇게 갈려 있다는 걸 확인했다.

```
가중치     bf16    안 정했다. 모델 파일이 그렇다
KV 캐시    fp8     내가 옵션으로 정했다
```

**그럼 그 파일은 누가 bf16 으로 정했나.** 학습한 쪽이 정했을 텐데, 왜 하필 bf16 인가. 그리고 추론에서는 fp8 이나 4비트로 내려도 되는데 학습은 왜 안 그러나.

파고들어보니 답이 단순했다. **값을 쌓아두는 자리만 fp32 로 지키고, 나머지는 낮은 비트로 내린다.**

## 학습은 계산과 저장을 나눈다

### 혼합 정밀도

학습을 bf16 으로 한다는 말이 **전부를 bf16 으로 한다는 뜻이 아니다.** 가중치를 두 개 갖고 있다.

```
마스터 가중치    fp32    진짜 값. 업데이트가 여기 쌓인다
계산용 사본      bf16    마스터를 반올림한 것. 계산은 여기서 한다
옵티마이저 상태   fp32    모멘텀 같은 것
```

**둘이 같은 값은 아니다.** bf16 사본은 fp32 마스터를 반올림한 것이라 이미 조금 어긋나 있다. 계산할 때만 쓰고 버리는 것도 그래서다.

매 스텝마다 마스터를 bf16 으로 복사해 계산하고, 나온 결과로 **fp32 마스터를 고친다.** 이걸 mixed precision, 혼합 정밀도라고 부른다.

메모리가 더 드는데도 이렇게 한다. 이유가 있다.

### 가중치 · 활성값 · 그래디언트

학습에서 도는 숫자가 세 종류다. **셋의 크기가 크게 달라서 이게 자료형 선택을 강제한다.**

| | 무엇 | 보통 크기 | 언제 바뀌나 |
|---|---|---|---|
| 가중치 | 모델이 기억하는 값 | 0.01 ~ 1 | 매 스텝 조금씩 |
| 활성값 | 계산 도중의 중간 결과 | 0.1 ~ 100 | 매번 새로 계산 |
| 그래디언트 | 가중치를 어디로 옮길지 가리키는 값 | 0.000001 ~ 0.01 | 매번 새로 계산 |

**그래디언트**는 우리말로 기울기다. "이 가중치를 키우면 오차가 늘어나나 줄어드나" 를 나타낸다. 양수면 줄여야 하고 음수면 키워야 하며, 크기는 얼마나 민감하게 반응하는지를 뜻한다.

가중치를 고치는 계산이 이렇게 생겼다.

```
새 가중치 = 기존 가중치 - (학습률 × 그래디언트)
```

**학습률**은 보폭이다. 크면 답을 뛰어넘고 작으면 하염없이 느려진다.

### 왜 마스터를 fp32 로 두나

위 표에서 보이듯 **그래디언트가 가중치보다 천 배에서 백만 배 작다.** 크기가 한참 다른 두 수를 빼는 계산이라 자료형이 버텨주지 못하면 결과가 안 움직인다.

```
가중치      0.4823
업데이트    0.0000001
```

앞 글에서 fp16 이 작은 값을 아예 0 으로 적어버린다고 했는데, **bf16 은 그 문제가 없다.** 범위가 넓어서 `0.0000001` 을 멀쩡히 저장한다.

그런데 더하는 순간 막힌다.

```
bf16 이 0.48 근처에서 쓰는 눈금   0.00195
더할 값                          0.0000001

0.4823 + 0.0000001 = 0.4823      같은 칸에 떨어진다
```

**bf16 은 그 작은 값을 저장할 수는 있는데, 큰 값에 더한 결과를 다른 값으로 저장할 수가 없다.** 눈금 사이에 들어가서 반올림되면 원래 자리로 돌아온다.

fp32 는 같은 구간에서 눈금이 훨씬 촘촘하다.

```
fp32 가 0.48 근처에서 쓰는 눈금   0.00000003

0.4823 + 0.0000001 = 0.4823001   옮겨간다
```

### bf16 도 못 하는 일

여기가 앞 글과 이어지는 지점이다. **같은 "값이 사라진다" 인데 원인이 다르다.**

```
fp16   범위가 좁아서 값 자체를 0 으로 적는다        →  범위 문제
bf16   값은 적는데 더한 결과가 제자리로 돌아온다     →  정밀도 문제
```

앞 글에서 bf16 이 범위를 지키려고 정밀도를 내줬다고 했다. **그 대가를 여기서 치른다.** 가수 7비트로는 누적이 안 된다.

그래서 계산은 bf16 으로 하고 누적은 fp32 에 맡긴다. 둘을 나눈 게 아니라 **각자 잘하는 걸 시킨 것이다.**

## 학습이 정밀도를 내려온 순서

### fp32 단독에서 fp8 까지

대략 이렇게 왔다.

| 시기 | 주류 |
|---|---|
| ~2018 | fp32 단독 |
| 2018~2020 | fp16 + loss scaling |
| 2020~2024 | bf16 + fp32 마스터 |
| 2024~ | fp8 부분 도입 |

fp16 시절에 loss scaling 이 필요했던 건 앞 글에 썼다. bf16 이 나오면서 그 장치가 필요 없어졌고, 지금은 fp8 이 들어오는 중이다.

**다만 fp8 도 전부를 fp8 로 하는 게 아니다.** 층이 하나 더 생겼을 뿐 구조는 같다.

```
fp32   마스터 가중치, 옵티마이저      누적 담당. 안 내린다
bf16   임베딩, 정규화, 출력층        민감한 층
fp8    행렬 곱셈 대부분             연산량의 대부분
```

**누적하는 곳은 여전히 fp32 다.** 비트를 아무리 내려도 이 자리는 안 내려간다. 앞에서 본 계산이 그 이유다.

### 순전파와 역전파가 다른 형식을 쓴다

fp8 에 변형이 둘 있다고 했는데, 학습에서는 그 둘을 **같은 학습 안에서 나눠 쓴다.**

```
E4M3   지수 4 · 가수 3    순전파  가중치와 활성값
E5M2   지수 5 · 가수 2    역전파  그래디언트
```

앞 표의 크기 차이가 그대로 나타난다. 순전파가 다루는 가중치와 활성값은 `0.01 ~ 100` 안에 있어서 범위가 남는다. 그래서 가수를 하나 더 가진 쪽을 쓴다.

그래디언트는 다르다. 아주 작아지기도 하고 튀기도 한다. **범위가 모자라면 0 이 되거나 무한대가 되니** 지수를 하나 더 준 쪽을 쓴다.

8비트에서는 정밀도와 범위를 한 형식으로 타협할 수가 없어서 용도별로 갈랐다.

## 하드웨어가 형식을 정한다

### 회로가 없으면 흉내만 낸다

여기가 실제로 순서를 정한다. **좋은 형식이 이기는 게 아니라 칩이 지원하는 형식이 이긴다.**

자료형은 소프트웨어로도 흉내 낼 수 있다. 다만 곱셈 회로가 그 형식을 직접 못 받으면, 매번 풀었다가 계산하고 다시 접어야 해서 **오히려 느려진다.** 메모리는 줄어도 속도는 손해다.

### 회로가 들어온 순서

```
bf16   Google TPU 가 먼저, NVIDIA 는 Ampere(2020) 부터
fp8    NVIDIA Hopper(2022, H100)
fp4    NVIDIA Blackwell
```

bf16 이 표준이 된 것도 학계가 설득당해서가 아니라 **칩에 회로가 들어갔기 때문이다.** fp8 이 뜬 것도 같다.

이게 내 기계 얘기와 바로 이어진다. **GB10 은 Blackwell 이라 4비트 연산 회로가 있다.** 그래서 4비트 모델이 진짜로 빨라진다. 회로가 없는 칩에서는 파일만 작아지고 속도는 안 나온다.

### MX 포맷

4비트에서 범위를 어떻게 확보하느냐를 업계가 같이 정리한 게 MX 포맷이다. NVIDIA, AMD, Intel, Microsoft 등이 함께 표준으로 만들었다.

```
값 32개를 한 묶음으로 두고 배율 하나를 공유한다
개별 값은 4비트나 6비트만 쓴다
```

앞 글에서 양자화 배율이 loss scaling 과 같은 발상이라고 했는데, **그걸 묶음 단위로 자동화한 것이다.** NVFP4 가 이 계열이다.

## 추론은 다른 문제를 푼다

### 누적이 없다

학습에서 fp32 를 못 버리는 이유가 누적이었다. **추론에는 그게 없다.**

```
학습    가중치를 계속 고친다        →  작은 변화가 쌓여야 한다
추론    가중치가 안 변한다          →  쌓을 게 없다
```

한 번 계산하고 다음 층으로 넘기면 끝이다. 그래서 학습보다 훨씬 아래로 내려갈 수 있다.

```
bf16 · fp16     품질 최우선
fp8             대규모 서비스의 주류
int4            개인 GPU 에서 큰 모델 돌릴 때
int2 이하        연구 단계. 품질이 무너진다
```

### 같은 메모리면 정밀도보다 파라미터 수

추론에서 널리 쓰이는 경험칙이 있다. **같은 메모리를 쓴다면 정밀한 작은 모델보다 거친 큰 모델이 낫다는 것이다.**

```
70B 를 4비트로     약 35 GB
13B 를 16비트로    약 26 GB
```

둘을 비교하면 대체로 앞이 낫다고들 한다. 파라미터가 많은 쪽이 담고 있는 게 많고, 양자화로 잃는 건 생각보다 적다는 얘기다.

측정된 법칙은 아니고 경험적인 판단이다. 4비트 아래로 내려가면 뒤집힌다. 그래도 모델을 고를 때 첫 기준으로는 쓸 만하다.

**내 경우에 대입하면 이렇게 된다.**

```
Ornith-1.5 를 4비트로   23.4 GB
같은 모델을 bf16 으로    71.9 GB
```

같은 모델이라 이 원칙이 그대로 적용되지는 않는다. 다만 남는 자리에 무엇을 넣을지가 달라진다. 4비트로 내리면 GPU 예산에서 40 GiB 넘게 비고, 그건 KV 캐시로 가서 대화 길이와 동시 처리 수가 된다.

## 예산과 배분

앞 글에서는 정밀도와 범위 둘로만 봤는데, 그 위에 하나가 더 있다.

```
비트 수    예산.  줄이면 메모리와 속도를 얻는다
 ├ 지수    그 예산에서 범위에 얼마를 줄까
 └ 가수    그 예산에서 정밀도에 얼마를 줄까
```

셋이 대등하게 맞바꾸는 게 아니다. **비트 수가 먼저 예산을 정하고, 지수와 가수가 그 안에서 나눠 갖는다.**

그래서 선택이 두 단계다.

```
① 몇 비트를 쓸까         16 → 8 → 4.  메모리와 속도를 얻고 품질을 내준다
② 그 비트를 어떻게 나눌까   범위 쪽이냐 정밀도 쪽이냐
```

지금까지 나온 형식이 전부 이 두 선택의 조합이다.

| | ① 비트 | ② 배분 |
|---|---|---|
| fp32 | 32 | 둘 다 넉넉하다 |
| fp16 | 16 | 정밀도 쪽 |
| bf16 | 16 | 범위 쪽 |
| fp8 E4M3 | 8 | 정밀도 쪽 |
| fp8 E5M2 | 8 | 범위 쪽 |
| NVFP4 | 4 | 정밀도 쪽. 범위는 묶음 배율이 맡는다 |

**같은 줄에 있는 둘은 비용이 같다.** fp16 과 bf16 은 둘 다 2바이트라 메모리도 속도도 차이가 없고, 배분만 다르다. 앞에서 fp16 을 bf16 으로 바꿀 이유가 없다고 한 게 이 얘기다.

맨 아랫줄이 요즘 방향이다. **예산을 극단으로 줄이고, 형식이 감당 못 하는 범위는 배율로 밖에서 메운다.**

## 그래서 내가 정할 수 있는 것

처음 질문으로 돌아오면 답이 이렇다.

```
가중치가 bf16 인 이유
  ← 학습 팀이 bf16 으로 학습하고 저장했다
     ← 누적은 fp32 에 맡기고 계산만 내릴 수 있어서
        ← 칩에 bf16 회로가 있어서
```

**내가 고른 게 하나도 없다.** 모델 파일을 받는 순간 이미 정해져 있었다.

내가 실제로 정한 건 `--kv-cache-dtype fp8` 하나뿐이었다. 그게 가능했던 건 KV 캐시가 학습에 없는 물건이라 파일에 안 담겨 오기 때문이다.

그리고 하나 더 고를 수 있다. **어떤 파일을 받을지.** 같은 모델의 4비트 판을 받으면 그건 내가 고른 게 된다. 다만 그 4비트가 진짜로 빨라지려면 칩에 회로가 있어야 하고, 그건 또 내가 GPU 를 살 때 정해진 것이다.

파고들수록 내가 정하는 자리가 좁아진다. 대신 **왜 그 값인지는 이제 설명할 수 있다.**
