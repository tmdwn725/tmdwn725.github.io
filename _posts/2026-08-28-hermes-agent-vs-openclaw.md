> DGX Spark로 LLM을 직접 굴린 기록. 4편.

## 왜 뜯어봤나

[GPU를 산 이유](/posts/why-dgx-spark/)가 개인 비서였다. 메일과 일정과 파일을 통째로 만지는 에이전트를 만들려면 모델이 내 쪽에 있어야 했다.

일단은 이미 나와 있는 에이전트를 써보기로 했다. 그중 하나가 내 용도에 맞으면 그냥 쓰면 되니까. 그래서 개인용 AI 에이전트로 가장 알려진 두 개를 골라 한 달쯤 굴려보고 분석 문서를 썼다.

**Hermes Agent** (Nous Research). 파이썬으로 만들어졌고 자가 개선을 내세운다.

**OpenClaw** (OpenClaw Foundation). 타입스크립트로 만들어졌고 게이트웨이를 중심에 둔다. 네이티브 앱까지 공식 지원한다.

결론부터 쓰면 둘 다 안 썼다. 부실해서가 아니라 그 반대에 가까웠다.

> 아래 비교는 hermes-agent 0.14 대와 openclaw 2026.5 스냅샷을 뜯어보고 정리한 것이다. 둘 다 빠르게 움직이는 프로젝트라 지금은 달라진 게 있다. 예를 들어 hermes 는 그 뒤로 0.20 대가 되면서 데스크톱 앱이 붙었다. 구조와 철학은 유지되지만 개별 항목은 지금 시점에서 다시 확인하는 게 좋다.

## 같은 그림, 다른 철학

둘 다 큰 그림은 같다. **게이트웨이 중심의 다중 채널 + 다중 LLM 프로바이더 + 확장 가능한 도구 플랫폼.** 그런데 한 줄 정의가 다르다.

```
openclaw       "Gateway is the control plane"
               한 프로세스가 API·WebSocket·세션 오케스트레이션·채널·운영·보안을 다 관장

hermes-agent   "self-improving AI agent"
               자가 개선 루프가 코드 경로로 실재하고, RL 학습 데이터 생산까지 의도
```

이 차이가 아래 모든 결정으로 내려온다.

## 스택부터 갈린다

| | openclaw | hermes-agent |
|---|---|---|
| 언어 | TypeScript (ESM), `any` 지양 | Python 3.11+ |
| 런타임 | Node 22+ (Bun 지원) | Python 3.11+ |
| 패키지 | pnpm monorepo | uv 권장, pip 호환 |
| 데스크톱·모바일 | SwiftUI (macOS/iOS), Kotlin (Android) | Electron 데스크톱 (macOS/Windows/Linux) |
| 테스트 | Vitest, 커버리지 라인 70% / 분기 55% | `tests/` 1,197 파일 |

**둘 다 앱이 있는데 방향이 다르다.** openclaw 는 각 플랫폼의 네이티브 기술로 만든다. macOS 메뉴바 앱이 중심이고 iOS·Android 가 따라온다. hermes 는 Electron 으로 데스크톱 세 종(macOS·Windows·Linux)을 한 번에 덮는다. **모바일까지 가느냐, 데스크톱을 넓게 덮느냐의 차이다.** 여기에 hermes 는 웹 UI 와 터미널 UI 도 같이 둔다.

의존성 정책도 다르다. hermes는 **모든 직접 의존성을 정확한 버전으로 고정**한다. 2026년 5월 공급망 공격이 그 정책을 직접 트리거했다고 문서에 적혀 있다.

## 도구 권한이 가장 크게 갈린다

여기가 두 프로젝트의 성격을 제일 잘 보여준다.

**openclaw는 정책 파이프라인을 깐다.**

```
profile → allow/deny → owner-only → group → subagent
       → message provider → model provider → sandbox → fs policy
```

여덟 단계를 통과해야 도구가 실행된다. 그룹별로, 채널별로, 모델 프로바이더별로 정책을 나눌 수 있다. 운영 환경을 상정한 설계다.

**hermes는 기본이 허용이다.** 대신 격리를 조합으로 만든다. 터미널 백엔드 선택, 승인 흐름, 게이트웨이 인증, 스킬 가드를 겹쳐 쓴다. 도구는 `tools/registry.py` 하나에 자가 등록하고, `check_fn` 과 `requires_env` 로 런타임에 노출 여부만 정한다.

```
openclaw   막는 걸 설계로 푼다
hermes     열어두고 조합으로 감싼다
```

## hermes 의 가장 큰 강점은 자가 개선이다

hermes 를 다른 에이전트와 구분 짓는 건 자가 개선이다. 슬로건이 아니라 코드로 있다.

```
curator.py             87KB   쌓인 메모리를 주기적으로 정리
background_review.py   59KB   세션이 끝난 뒤 되돌아보는 루프
insights.py            52KB   누적 데이터에서 패턴 추출
memory_manager.py      52KB   메모리 저장·병합 관리
```

**네 파일 합쳐 250KB 다.** 설정 항목 몇 개가 아니라 각각이 독립된 서브시스템이다.

에이전트를 오래 쓰면 반드시 만나는 문제가 있다. **메모리가 쌓이면 프롬프트에 다 못 넣는다.** 그러면 최신 기억이 잘려나가고, 어제 알려준 걸 오늘 모른다. 누군가는 이걸 정리해줘야 하는데 대부분의 에이전트는 그 자리가 비어 있다.

hermes 는 그 자리를 채워뒀다. 게다가 대화 궤적을 **강화학습 데이터로 생산하는 것**까지 핵심 기능으로 둔다. 배치 러너와 궤적 압축기가 따로 있다. 만든 쪽이 차세대 툴 콜링 모델 학습 데이터를 뽑으려는 의도가 코드에 드러난다.

openclaw 도 궤적을 남기지만 운영 분석용이다. **"에이전트가 스스로 나아진다"를 코드 경로로 만든 건 hermes 쪽이다.**

## 격리와 다중 에이전트

| | openclaw | hermes-agent |
|---|---|---|
| 샌드박스 | Docker / SSH. 기본 보수적 (network none, capDrop ALL, readOnly root) | **7개 백엔드** Local / Docker / SSH / Singularity / Modal / Daytona / Vercel Sandbox |
| 서브에이전트 | **푸시 기반.** 자식 완료 이벤트가 부모에 push, 부모는 폴링 안 함 | **동기 블로킹.** 자식이 끝날 때까지 스레드풀에서 대기 |
| 다중 코디네이션 | Task / TaskFlow 레지스트리 (별도 영속) | **칸반 DB 공유 상태.** 워커가 별도 프로세스로 뜨고 카드 ID를 환경변수로 받음 |

hermes의 7개 백엔드 중 Modal과 Daytona는 서버리스다. **작업을 클라우드에 띄웠다가 내릴 수 있다.** 로컬 GPU가 없어도 무거운 작업을 돌린다는 뜻이다.

## 컨텍스트 압축에서 본 디테일

hermes 쪽에서 눈에 남은 설정이 있다.

```
compression.threshold  = 0.50    컨텍스트 절반 차면 압축
target_ratio           = 0.20    5분의 1로 줄인다
protect_last_n         = 20      최근 20턴은 건드리지 않는다
protect_first_n        = 3       초반 3턴도 보존
```

그리고 요약문에서 **"Next Steps" 대신 "Remaining Work" 라는 표현을 쓴다.** 이유가 적혀 있다. 요약 안의 "다음 단계"를 모델이 **지금 수행하라는 지시로 오해**하기 때문이다.

**단어 하나를 바꿔서 오작동을 막는다.** 이런 건 실제로 당해보지 않으면 안 나온다.

## 규모

| | openclaw | hermes-agent |
|---|---|---|
| 확장 | extensions 152 | plugins 19 |
| 스킬 | 51 | 82 + 옵션 115 |
| 도구 | 플러그인에 분산 | 136 파일 |
| 메시징 채널 | 23 | 22 + 플러그인 6 |
| LLM 프로바이더 | 50+ | 30+ |
| 훅 | 메시지·플러그인·워크스페이스 계열 | 17종 |
| 다국어 | 문서 zh-CN | **17개 로케일, 한국어 포함** |

**확장을 세는 단위가 다르다.** openclaw 는 기능 하나가 extension 하나로 나가고, hermes 는 도구를 파일 단위로 두고 플러그인은 묶음으로 쓴다. 숫자만 비교하면 오해가 생긴다.

**hermes는 공식 한국어 지원이 있다.** 로케일과 문서 사이트 둘 다.

## 어디에 붙일 수 있나

둘 다 채널이 스무 개가 넘는다. 그런데 목록을 나란히 놓으면 성격이 갈린다.

**둘 다 있는 것**

```
Telegram · Discord · Slack · Signal · WhatsApp
Matrix · Mattermost · Feishu · Webhook
```

**OpenClaw 에만 있는 것**

```
iMessage · Google Meet · Zoom · Teams 회의 · voice-call
Twitch · Nostr · Tlon · IRC
Nextcloud Talk · Synology Chat · LINE · Zalo
```

**Hermes Agent 에만 있는 것**

```
Home Assistant · Email · SMS · API Server
DingTalk · WeCom · Weixin · QQ · Yuanbao · BlueBubbles
MS Graph Webhook
```

여기서 방향이 보인다.

**OpenClaw 는 사람이 있는 곳에 붙는다.** 메신저에 화상회의(Meet·Zoom·Teams)와 음성 통화가 붙고, 트위치와 분산 SNS 까지 있다. 셀프호스팅 메신저(Nextcloud Talk·Synology Chat)도 챙긴다. **대화가 오가는 자리에 에이전트를 데려다 놓는다는 그림이다.**

**Hermes Agent 는 일이 일어나는 곳에 붙는다.** 이메일과 문자가 1급 채널이고, 홈 어시스턴트로 집안 기기를 부르고, API 서버와 웹훅이 따로 있다. 그리고 중국 기업 메신저(DingTalk·WeCom·Weixin·QQ)가 한 세트로 들어가 있다. **사람이 없어도 흘러가는 일에 에이전트를 끼워 넣는 그림이다.**

같은 "채널 스무 개"인데 고른 스무 개가 다르다.

## 나는 텔레그램으로 썼다

그중 내가 실제로 쓴 건 텔레그램 하나였다.

이유는 단순하다. **밖에 있을 때 집에 있는 기계에 명령을 보내려면 이미 깔려 있는 앱이 제일 낫다.** 웹 UI 를 따로 열 필요가 없고 알림도 그냥 온다.

### 봇 만들기

텔레그램은 봇을 만드는 절차가 텔레그램 안에서 끝난다. **BotFather** 라는 공식 봇이 그 역할을 한다.

```
1. 텔레그램에서 @BotFather 를 검색해 대화를 연다
2. /newbot 이라고 보낸다
3. 봇 이름을 정한다 (표시되는 이름)
4. 봇 아이디를 정한다 (반드시 bot 으로 끝나야 한다)
5. 토큰을 받는다
```

받는 토큰은 이렇게 생겼다.

```
8123456789:AAH7f-XxxxxxxxxxxxxxxxxxxxxxxxxxxxX
```

**이게 봇의 비밀번호다.** 이 문자열을 아는 사람은 누구나 그 봇으로 메시지를 보내고 받을 수 있다. 절대 공개 저장소에 커밋하면 안 된다.

다음으로 **내 텔레그램 user ID** 가 필요하다. `@userinfobot` 에게 아무 메시지나 보내면 숫자로 알려준다.

### 설정

OpenClaw 는 설정 파일에 이렇게 들어간다.

```json
{
  "channels": {
    "telegram": {
      "enabled": true,
      "botToken": "<받은 토큰>",
      "dmPolicy": "allowlist",
      "allowFrom": ["<내 user ID>"]
    }
  }
}
```

**`allowFrom` 을 빼먹으면 안 된다.** 봇 아이디는 검색으로 찾을 수 있다. allowlist 가 없으면 아무나 그 봇에게 말을 걸 수 있고, 그 말이 내 컴퓨터에서 실행된다.

### 페어링

두 프로젝트 다 이걸 알고 있어서 **페어링 절차**를 따로 뒀다. 모르는 사람이 첫 메시지를 보내면 바로 통과시키지 않고, 코드를 발급해서 운영자 승인을 받는다.

Hermes Agent 쪽 정책은 이렇게 구체적이다.

```
8자리 코드, 헷갈리는 0 · O · 1 · I 제외
유효 시간 1시간
사용자당 10분에 1회만 발급
5회 실패하면 1시간 잠금
코드는 로그에 안 남긴다
```

**여기까지 신경 쓴 걸 보고 이 프로젝트를 좀 다시 봤다.** 개인용 도구인데 인증 잠금 정책이 상용 서비스 수준이다.

실제로 쓰면서 제일 조심하게 된 건 다른 데 있었다. 위험한 명령을 실행하기 전에 승인을 묻는데, **그 승인 버튼이 텔레그램 안에 뜬다.** 모바일에서 알림 확인하다가 습관적으로 누르면 그대로 실행된다. 승인 모드를 어떻게 둘지 한참 고민했다.

## 언제 무엇을 고르나

### OpenClaw 가 맞는 경우

```
· macOS · iOS · Android 네이티브 앱 경험이 필요하다
· TypeScript / Node 생태계로 가야 한다
· 그룹 · 채널 · 프로바이더별로 도구 정책을 나눠야 한다
· 서브에이전트를 비동기로 굴려야 한다
· 캔버스 같은 인터랙티브 산출물을 렌더링해야 한다
```

**예시 하나. 회의 녹취와 자동 요약.**

Google Meet 을 채널로 붙이고 전사 백엔드를 켜두면, 회의가 끝났을 때 요약본이 정해둔 곳으로 온다. 실시간 전사와 회의록 생성이 별도 모듈로 들어 있어서 조립이 아니라 설정이다. Hermes Agent 로 하려면 직접 붙여야 한다.

**예시 둘. 정기 보안 점검.**

봇 설정과 게이트웨이 권한이 안전한지 점검하는 명령이 내장돼 있다.

```bash
openclaw security audit --deep
```

이걸 주 1회 예약해두고 결과를 메신저로 받는 식으로 쓸 수 있다. 채널을 여러 개 열어둘수록 이런 점검이 필요해진다.

### Hermes Agent 가 맞는 경우

```
· 파이썬 생태계다
· 자가 개선 루프가 핵심 가치다
· 학습 데이터(RL 궤적)를 직접 생산해야 한다
· 클라우드 샌드박스에 작업을 띄워야 한다
· 칸반 기반 다중 워커 코디네이션이 필요하다
· 외부 메모리 백엔드를 갈아끼워야 한다
· 한국어 문서가 필요하다
```

**예시 하나. 커밋마다 자동 코드 리뷰.**

훅이 17종이라 세션 시작·종료, 도구 호출 전후, LLM 호출 전후 어디에나 끼어들 수 있다. 로컬 저장소에 커밋이 생기면 훅이 잡아서 리뷰를 돌리고 결과를 메신저나 파일로 보내는 흐름을 설정으로 짤 수 있다.

**예시 둘. 큰 작업을 여러 워커가 나눠서.**

"이 모놀리스를 서비스 단위로 쪼개라" 같은 작업은 한 세션에서 끝나지 않는다. Hermes Agent 는 칸반 보드를 데이터베이스로 두고, 워커를 별도 프로세스로 띄워서 카드를 하나씩 집어가게 한다.

```bash
hermes kanban init
```

작업이 며칠에 걸쳐도 상태가 보드에 남는다. OpenClaw 도 태스크 레지스트리로 비슷한 걸 할 수 있는데, 워커를 여러 개 붙이는 그림은 Hermes Agent 쪽이 직관적이다.

## 그런데 둘 다 안 썼다

비교를 끝내고 나서 직접 만들기로 했다. 이유가 둘이다.

**첫째, 내가 쓰는 게 일부였다.**

채널이 스물세 개인데 나는 하나만 쓴다. 플러그인이 백서른 개인데 손대는 건 몇 개다. 네이티브 앱도, 강화학습 궤적도, 칸반 워커도 안 쓴다.

기능이 많은 게 문제가 아니다. **안 쓰는 기능이 이해해야 할 표면적을 늘린다.** 뭔가 이상하게 동작할 때 원인 후보가 그만큼 많아진다.

**둘째, 막혔을 때 열어보기가 어려웠다.**

hermes 의 대화 루프 파일을 지금 세어보면 8,071줄이다. 그중 함수 하나가 이렇다.

```
run_conversation()      1,252줄
_perform_api_call()     5,166줄
```

**API 호출 한 번을 감싸는 함수가 5천 줄이다.** 초기화 파일도 2,928줄이다. 여기서 뭔가 이상하게 동작하면 어디를 봐야 할지 감을 잡는 것부터 일이 된다.

openclaw 는 반대 방향으로 어렵다. 도구 하나를 실행하려면 여덟 단계 정책을 통과하는데, 막혔을 때 그 여덟 곳을 다 봐야 한다. 코드가 잘게 나뉘어 있어서 한 파일은 짧은데 흐름을 따라가는 게 길다.

**둘 다 그럴 만해서 그렇게 된 코드다.** 채널 스물세 개와 프로바이더 오십 개를 감당하려면 그만큼 복잡해진다. 다만 나는 채널 하나와 사용자 한 명을 감당하면 된다.

## 가져온 것

직접 만들되 좋은 건 그대로 가져왔다. 발명할 이유가 없다.

**시스템 프롬프트 3티어.** hermes가 프롬프트를 세 층으로 나눈다.

```
stable     정체성 · 도구 사용 지침 · 세션 시작에 1회
context    호출자 메시지 · 작업 디렉토리에서 찾은 규칙 파일
volatile   매 턴 바뀌는 것 (현재 시각 등)
```

캐싱과 직결된다. stable은 안 바뀌니 프롬프트 캐시가 먹고, volatile만 매번 새로 붙는다. **내 프롬프트 디렉토리도 지금 이 세 파일이다.**

**메모리 큐레이터.** 쌓인 메모리를 주기적으로 정리하는 역할. 안 하면 프롬프트에 다 못 넣고 최신 메모리가 잘려나간다.

**도구 스키마 정리기.** 로컬 모델은 JSON Schema를 문법으로 컴파일해서 출력을 제약하는데, 표현 못 하는 구조가 있으면 요청 전체를 거절한다. hermes는 이걸 445줄짜리 모듈로 다룬다. 내 코드에는 이렇게 적혀 있다.

```
Adapted from Hermes tools/schema_sanitizer.py (445 lines)
→ trimmed to the rules Sage / agent-flow actually trip over
```

**445줄에서 실제로 걸린 다섯 가지만 남겼다.** 지금 184줄이다.

**실행 전 승인.** openclaw는 승인 기록을 파일로 남긴다. 한 번 허용한 건 다시 안 묻는다.

## 경량화는 기능을 줄이는 게 아니다

버린 것이 가져온 것보다 훨씬 많다. 음성 입출력, 채널 스물두 개, 서브에이전트 위임, 샌드박스 백엔드 일곱 개, 캔버스, 워크스페이스 증명, 강화학습 궤적.

**텔레그램도 결국 안 붙였다.** 잘 쓰긴 했는데 봇 토큰과 allowlist를 관리해야 하고, 알림이 개인 메신저에 섞인다. 그래서 웹 앱을 홈 화면에 올리고 푸시 알림을 받는 쪽으로 갔다. 채널 하나를 고르는 것도 결국 무엇을 관리할 것인가의 문제였다.

**전부 언젠가 필요할 수도 있는 것들이다.** 그런데 지금 필요하지 않고, 지금 필요하지 않은 걸 넣어두면 고칠 때 발목을 잡는다.

설정도 그렇다. hermes 설정 파일은 444줄인데 내가 건드린 건 열 줄 남짓이었다. **남이 쓸 걸 상정하면 설정이 늘어나는데, 사용자가 나뿐이면 대부분은 코드로 정해도 된다.**

두 개를 먼저 써본 게 맞았다고 생각한다. 바로 만들었으면 승인 흐름이나 메모리 정리 같은 걸 **필요해진 다음에 급하게 붙였을 것이다.** 이미 잘 만든 물건이 그걸 어떻게 다루는지 보고 나서 시작하니 구조를 처음부터 잡을 수 있었다.
