## 블록이라는 단위

[토큰당 KV 크기를 계산한 글](/posts/hybrid-attention-kv-cache-size/)에서 본 대로, 대화를 하면 토큰마다 K·V 라는 숫자 뭉치가 GPU 메모리에 쌓인다. 내 서버는 토큰당 40 KiB 고, KV 캐시용으로 6.08 GB 를 잡아뒀다.

**vLLM 은 이 6.08 GB 를 통째로 다루지 않고 고정 크기 조각으로 잘라 쓴다.** 그 조각이 블록이다. 요청이 오면 블록을 빌려주고 끝나면 회수한다.

이 구조가 두 군데에서 드러난다.

```
1  기동 로그가 찍는 숫자가 실제 용량과 다르다
2  같은 앞부분을 다시 계산하지 않을 수 있다   prefix caching
```

첫째는 로그를 읽을 때 걸린다. 용량을 말해주는 줄이 둘 있는데 서로 안 맞는다.

```
GPU KV cache size: 159,296 tokens
Maximum concurrency for 65,536 tokens per request: 8.00x
```

둘째 줄부터 읽으면 이렇다.

```
Maximum concurrency for 65,536 tokens per request: 8.00x
                       ────────────────────────   ─────
                       요청 하나가 이만큼 쓴다면    이런 요청을 8개까지
```

`65,536` 은 내가 준 `--max-model-len` 이다. **컨텍스트를 꽉 채운 요청 기준으로 동시에 몇 개까지 받는지**를 vLLM 이 계산해 찍어준다.

그런데 첫 줄로 같은 걸 구하면 다른 답이 나온다. 159,296 토큰까지 담을 수 있다니, 65,536 짜리 요청은 두 개하고 조금 더다.

```
159,296 ÷ 65,536 = 2.43
```

**3.3배 어긋난다.** 블록을 어떻게 세느냐에서 나오는 차이고, 아래에서 푼다.

둘째는 옵션 하나로 켜고 끄는 기능이다. 블록 단위로 쪼개뒀으니 **앞부분이 같은 요청끼리 조각을 돌려쓸 수 있다.** 이게 얼마나 이득인지, 그리고 프롬프트를 어떻게 짜야 걸리는지가 뒤쪽 내용이다.

## 블록 구조와 로그의 숫자

### 번호표와 물리 주소 계산

대화마다 길이가 다른데 연속된 메모리를 미리 잡아두면 자리가 남거나 모자란다. 짧은 대화가 남긴 틈에 긴 대화가 못 들어가는 **조각화**가 생긴다.

vLLM 은 KV 캐시를 **고정 크기 조각**으로 잘라두고 요청마다 필요한 만큼 빌려준다. 운영체제가 물리 메모리를 페이지로 관리하는 것과 같은 발상이고, 이름도 거기서 왔다. 이 조각을 **블록**이라고 부른다.

요청이 들고 있는 건 실제 메모리가 아니라 **번호표**다.

```
요청 A   [ 7 ][12 ][ 3 ]
요청 B   [ 7 ][15 ][ 9 ]
           ↑
        물리 블록 번호. 순서만 맞으면 흩어져 있어도 된다
```

**논리적으로 이어진 대화가 물리적으로는 흩어져 있어도 된다.** 이게 연속 메모리 요구를 깬 지점이고, 조각화가 사라지는 이유다.

내 서버는 블록 하나가 2,096 토큰이다. 대화가 5,000 토큰까지 왔다고 하면 이렇게 담긴다.

```
블록 0    토큰     0 ~ 2,095
블록 1    토큰 2,096 ~ 4,191
블록 2    토큰 4,192 ~ 6,287     ← 5,000번째 토큰은 여기
```

5,000번째는 블록 2 안에서 4,192 부터 세어 808번째 자리다. **여기까지가 내 기준 번호**고, 번호표를 거쳐야 실제 위치가 나온다.

```
번호표에서 블록 2 를 찾으면    물리 블록 9번
9 × 2,096 + 808 = 19,672      GPU 메모리의 실제 자리
```

**내 대화의 2번 블록이 물리적으로 9번이든 40번이든 계산이 성립한다.** 논리 번호와 물리 번호를 분리한 덕이다.

### GPU KV cache size 의 계산식

먼저 6.08 GB 가 몇 조각으로 잘렸는지 본다. 조각 하나는 **그룹에 든 레이어 10개분을 통째로 덮는다.**

```
조각 하나   레이어 1개분 2.05 MiB × 10 레이어  =  20.5 MiB
조각 개수   6.08 GB ÷ 20.5 MiB                =  304개
```

그리고 **그룹**이 있다. 레이어를 종류별로 묶은 것인데, 내 모델은 `linear × 3 + full × 1` 패턴이 열 번 반복돼서 vLLM 이 **레이어 10개씩 그룹 4개**로 나눈다.

```
그룹 1   레이어  4, 8, 12 … 40     full attention 10개
그룹 2   레이어  1, 5,  9 … 37     linear 10개
그룹 3   레이어  2, 6, 10 … 38     linear 10개
그룹 4   레이어  3, 7, 11 … 39     linear 10개
```

**네 그룹은 다른 대화를 담는 게 아니라 같은 토큰의 다른 레이어를 담는다.** 토큰이 40개 레이어를 다 통과하니 대화 하나가 네 그룹을 전부 쓴다.

```
토큰 5,000개짜리 대화 하나

  그룹 1   블록 3개
  그룹 2   블록 2개      같은 대화를 넷이 나눠 담는다
  그룹 3   블록 2개
  그룹 4   블록 2개
```

여기서 갈리는 게 있다. **블록 하나에 무엇이 들었는지가 그룹마다 다르다.**

```
그룹 1 의 블록      토큰 2,096개분의 K·V      →  토큰으로 셀 수 있다
linear 그룹 블록    길이와 무관한 고정 상태    →  토큰으로 셀 게 없다
```

그러니 **대화가 몇 토큰까지 가느냐는 그룹 1이 블록을 몇 개 받느냐로만 정해진다.** 나머지 셋은 몇 블록을 쓰든 대화 길이를 늘려주지 않는다.

로그는 여기서 **넷이 똑같이 나눠 쓴다고 가정한다.**

```
그룹 1 이 받는 몫    304 ÷ 4        =      76 블록
토큰으로 환산        76 × 2,096     = 159,296 토큰
```

코드가 그대로다.

```python
num_tokens = num_blocks // len(kv_cache_groups) * block_size
```

그룹이 하나뿐인 보통 모델에서는 나누기 1이라 이게 곧 실제 용량이다. hybrid 에서는 가정이 틀린다. **linear 그룹은 대화가 길어져도 2블록이면 되기 때문이다.**

```
             로그의 가정      실제 필요
그룹 1         76 블록         32 블록    컨텍스트 65,536 기준
그룹 2         76 블록          2 블록
그룹 3         76 블록          2 블록
그룹 4         76 블록          2 블록
                              38 블록
```

**linear 쪽에 74개씩 놀리는 셈으로 세고 있다.** 실제로 세면 이렇게 나온다.

```
304 ÷ 38 = 8.00
```

로그의 `8.00x` 다. 둘 중 하나가 틀린 게 아니라 **세는 방법이 다르다.**

```
159,296 ÷ 65,536 = 2.43   넷이 균등하게 나눈다고 가정한 값
304 ÷ 38         = 8.00   실제로 필요한 블록으로 센 값
```

**둘이 다른 걸 센다.**

```
GPU KV cache size     블록을 그룹 수로 균등하게 나눠 토큰으로 환산
                      그룹마다 실제 몇 개 필요한지는 안 본다

Maximum concurrency   요청 하나가 그룹별로 실제 몇 블록 잡는지 세서 나눈다
```

> hybrid 모델에서 용량을 볼 때는 `GPU KV cache size` 가 아니라 `Maximum concurrency` 를 본다. 그룹별 실제 필요량을 반영한 쪽이라서다.

## prefix caching 의 동작

### 요청 사이의 K·V 재사용

지금까지 본 KV 캐시는 **요청 하나 안에서** 쓰는 것이다. 토큰을 하나 만들 때마다 앞 토큰들의 K·V 를 다시 계산하지 않으려고 들고 있는 거고, 이건 끄고 켤 수 있는 게 아니다. 없으면 아예 못 쓴다.

`--enable-prefix-caching` 이 켜는 건 다른 쪽이다. **요청과 요청 사이**에서 재사용하는 것이다.

```
끄면    요청 1   프롬프트 3만 토큰 프리필 → 답 생성 → 끝나면 K·V 버림
        요청 2   앞부분이 같아도 처음부터 다시 3만 토큰 프리필

켜면    요청 1   프리필 → 답 생성 → 끝나도 블록을 안 지운다
        요청 2   앞부분을 찾아서 그만큼 프리필을 건너뛴다
```

**요청이 끝났을 때 그 블록을 버리느냐 남기느냐**가 차이다.

이게 이득인 건 **답을 만들기 전에 프롬프트 전체를 한 번 통과시켜야 하기 때문**이다. 3만 토큰이 들어오면 3만 개를 다 밀어넣어 K·V 를 만들고 나서야 첫 글자가 나온다. 이 구간을 프리필이라고 하고, 내 서버 로그의 `Avg prompt throughput` 이 그 속도다. 앞부분이 캐시에 있으면 **그만큼을 건너뛰고 첫 응답이 빨라진다.**

구현은 **같은 블록을 여러 요청이 가리키게 하는 것**이다. 앞에서 본 번호표가 이미 그 모양이었다.

```
요청 A   [ 7 ][12 ][ 3 ]
요청 B   [ 7 ][15 ][ 9 ]
           ↑     ↑
      같은 블록   여기서 갈린다. 뒤는 전부 새로 계산
      ref_cnt 2
```

### ref_cnt 와 블록 반납

여럿이 같이 쓰면 **언제 치워도 되는지**가 문제가 된다. A 가 끝났다고 블록 7 을 비워버리면 아직 쓰고 있는 B 의 데이터가 날아간다.

그래서 블록마다 **지금 몇 요청이 쓰고 있는지 세는 숫자**를 둔다. 코드에서 `ref_cnt` 다.

```
A 가 블록 7 을 쓰기 시작    ref_cnt  0 → 1
B 도 블록 7 을 쓰기 시작    ref_cnt  1 → 2
A 가 끝남                   ref_cnt  2 → 1     아직 안 치운다
B 도 끝남                   ref_cnt  1 → 0     이제 빈 블록으로 돌려놓는다
```

**0 이 되어야 반납된다.** 다만 반납이 삭제는 아니다.

```
반납됨      빈 블록 줄 뒤로 간다. 내용과 해시는 그대로 남는다
            이때도 해시로 찾을 수 있다 → 캐시 적중
덮어쓰임    자리가 모자라 다른 요청이 가져갈 때. 그때 해시가 지워진다
```

**줄 뒤에 있는 동안은 캐시로 살아 있다.** 오래된 것부터 밀려나니 자주 쓰는 앞부분은 계속 남는다. 여기가 prefix caching 의 본체다.

### 해시 체인

왜 앞에서부터만 걸리나. 블록을 찾는 해시가 자기 내용만 쓰지 않기 때문이다.

```python
def hash_block_tokens(hash_function, parent_block_hash, curr_block_token_ids, extra_keys)
```

**앞 블록의 해시가 인자로 들어간다.** 세 번째 블록이 같으려면 첫 번째와 두 번째도 같아야 하고, **한 번 갈라지면 그 뒤는 내용이 우연히 같아도 다른 값이 나온다.** prefix 라는 이름이 여기서 나왔다.

### 캐시되는 최소 단위

캐시에 넣는 조건이 하나 더 있다.

```python
# We only hash full blocks
num_full_blocks = num_tokens // self.block_size
```

**블록이 꽉 찼을 때만 캐시에 넣는다.** 아직 채워지는 중인 마지막 블록은 뒤에 토큰이 더 붙을 수 있어서 내용이 확정되지 않았고, 확정 안 된 걸 해시해두면 다음에 찾을 때 안 맞는다.

프롬프트 5,000 토큰이면 이렇게 갈린다.

```
블록 0    토큰     0 ~ 2,095    꽉 참   →  캐시됨
블록 1    토큰 2,096 ~ 4,191    꽉 참   →  캐시됨
블록 2    토큰 4,192 ~ 4,999    808개만 →  캐시 안 됨
```

**앞에서부터 꽉 찬 블록까지만 캐시된다.** 5,000 토큰 프롬프트면 4,191번째 토큰까지가 남고, 나머지 808개는 다음 요청에서 또 계산한다.

자투리는 블록 크기만큼 커질 수 있다. 블록이 16 이면 최대 15 토큰을 버리지만 2,096 이면 최대 2,095 를 버린다.

```
블록 16       500 토큰 프롬프트  →  31 블록 캐시됨, 4 토큰 버림
블록 2,096    500 토큰 프롬프트  →   0 블록 캐시됨, 전부 버림
```

### 실측 적중률 55.6%

내 서버는 2,096 이다. 여기까지 보고 **웬만한 프롬프트는 블록 하나도 못 채우겠다 싶었다.** 그러면 옵션을 켜둔 의미가 없다.

실측은 반대였다.

```
Prefix cache hit rate: 55.6%
```

프롬프트가 짧을 거라고 본 게 틀렸다. 로그의 `Avg prompt throughput` 은 10초 창 평균이라, 요청 하나가 도는 구간의 값에 10을 곱하면 그 프롬프트의 대략적인 크기가 나온다.

```
5,380 tok/s × 10s = 53,800 토큰
1,968 tok/s × 10s = 19,600 토큰
  941 tok/s × 10s =  9,400 토큰
```

**개인 비서라도 프롬프트는 수천에서 수만 토큰이다.** 도구 정의와 메모리와 대화 이력이 매 요청마다 통째로 붙기 때문이다. 2,096 은 쉽게 넘는다.

| 프롬프트 | 캐시되는 블록 | 최대 적중률 | 버리는 나머지 |
|---|---|---|---|
| 1,500 | 0 | **0%** | 1,500 |
| 3,000 | 1 | 70% | 904 |
| 10,000 | 4 | 84% | 1,616 |
| 30,000 | 14 | **98%** | 656 |

**블록이 커서 생기는 손해는 나머지 몫이고, 프롬프트가 길수록 그 비중이 줄어든다.** 실측 55.6% 는 짧은 요청과 긴 요청이 섞인 결과다.

여기까지가 캐시가 **언제** 걸리는지다. 그러면 걸리게 하려면 프롬프트를 어떻게 짜야 하나.

## 캐싱이 잘 걸리는 프롬프트 구조

에이전트는 한 번 물어보면 한 번 답하고 끝나지 않는다. 도구를 부르고, 결과를 받아 또 부르고, 그러다 답한다. **매 턴마다 앞의 것을 통째로 다시 보낸다.**

```
턴 1   [시스템][도구 정의][질문]
턴 2   [시스템][도구 정의][질문][도구 호출][결과]
턴 3   [시스템][도구 정의][질문][도구 호출][결과][도구 호출][결과]
```

앞부분이 계속 같으니 **캐싱이 가장 잘 걸리는 모양**이다.

이건 자기 서버만의 얘기가 아니다. Anthropic 과 OpenAI 가 파는 **prompt caching** 이 같은 메커니즘이다. 이름과 파는 방식만 다르다.

| | prefix caching | prompt caching |
|---|---|---|
| 쓰는 곳 | vLLM · SGLang 같은 엔진 | Anthropic · OpenAI API |
| 원리 | 앞부분 K·V 재사용 | 같음 |
| 켜는 법 | 옵션 하나로 자동 | OpenAI 자동, Anthropic 은 직접 표시 |
| 유효기간 | 없음. 밀려날 때까지 | 5분 (1시간 옵션) |
| 이득 | 프리필 시간 | 읽기가 정가의 10%, 쓰기는 25% 할증 |

**최소 단위가 있는 것도 같다.** 내 서버가 블록 2,096 토큰인 것처럼, Anthropic 도 1,024 토큰(Haiku 는 2,048)을 넘겨야 캐시가 잡힌다.

도구 정의와 시스템 프롬프트를 합쳐 8,000 토큰이고 열 턴을 돈다고 하면 API 기준으로 차이가 이렇게 난다.

```
캐시 없음   8,000 × 10                    =  80,000 토큰값
캐시 있음   8,000×1.25 + 8,000×0.1×9      =  17,200 토큰값
                                             78% 절감
```

자기 서버는 더 단순하다. 쓰기 할증이 없고, 돈 대신 **프리필 시간과 GPU 를 아낀다.**

반대로 앞을 흔들면 이 전부가 날아간다.

```
[현재 시각 2026-08-30 17:42][시스템][도구 정의]...
  매번 바뀜  ← 첫 블록부터 달라서 뒤가 전부 다시 계산된다
```

그래서 순서를 이렇게 잡는다.

| | |
|---|---|
| 고정된 것을 앞에 | 시스템 프롬프트, 도구 정의 |
| 변하는 것을 뒤에 | 현재 시각, 사용자별 정보 |
| 도구 목록을 매 턴 바꾸지 않는다 | 순서만 달라져도 해시가 깨진다 |
| 이력 압축은 앞이 아니라 뒤에서 | 앞을 요약해 갈아치우면 그 뒤가 전부 무효가 된다 |

마지막 줄이 특히 걸리기 쉽다. 대화가 길어져서 오래된 부분을 요약해 넣는 방식은 **앞부분을 통째로 바꾸는 일**이라, 아낀 컨텍스트보다 잃는 캐시가 클 수 있다.

## 정리

```
블록          KV 캐시를 자른 고정 크기 조각. 요청은 번호표만 들고 있다
              논리 번호와 물리 번호를 분리해서 흩어진 자리를 이어 쓴다

ref_cnt       몇 요청이 쓰고 있는지 세는 값. 0 이 되어야 반납된다
              여러 요청이 같은 블록을 가리키는 게 prefix caching 이다

해시 체인      앞 블록 해시를 엮어서 만든다. 한 번 갈라지면 뒤는 전부 새로 계산

캐시 조건      꽉 찬 블록만. 나머지는 버린다
              그래서 블록 크기가 캐싱 효율을 정한다

로그 읽기      GPU KV cache size 는 용량이 아니라 블록 ÷ 그룹 × 블록크기다
              hybrid 에서 용량을 볼 때는 Maximum concurrency 를 본다

프롬프트 순서   고정된 것을 앞에, 변하는 것을 뒤에
              자기 서버든 API 든 같은 규칙이다
```

블록 크기는 내가 정한 게 아니다. hybrid 모델이라 성질이 다른 두 캐시를 한 풀에서 다뤄야 했고, 페이지 크기를 맞추느라 vLLM 이 16 에서 2,096 으로 올렸다.

그 바람에 **캐싱의 최소 단위가 131배로 굵어졌다.** 다만 손해를 보는 건 2,096 을 못 채우는 짧은 요청뿐이고, 에이전트처럼 프롬프트가 긴 쪽에서는 그대로 걸린다. 실측 55.6% 가 그 결과다.
