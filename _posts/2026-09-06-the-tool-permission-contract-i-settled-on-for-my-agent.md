## 잘못 등록됐다

개인 비서에 캘린더와 가계부 도구를 붙여놨다. 일정을 잡아달라고 하면 캘린더에 등록하고, 얼마 썼다고 말하면 시트에 기록한다.

한 번 잘못 들어갔다. 내가 말한 것과 다른 값이 등록됐는데 그 자리에서는 몰랐고, 나중에 캘린더를 열고 알았다.

그 뒤로 등록할 때마다 눈으로 확인하게 됐다.

도구를 붙일 때 권한 목록은 이미 만들어뒀었다.

```
file.read      그냥 쓰게 둔다
sheets.append  물어본다
```

목록은 목록대로 동작했다. 물어보긴 물어봤다. 문제는 **한 번 허용하고 나면 그다음부터 안 물어봤다**는 것이다.

## 다른 에이전트들은 어떻게 하나

[Hermes 와 OpenClaw 를 비교한 글](/posts/hermes-agent-vs-openclaw/)에서 도구 권한이 제일 크게 갈렸다.

**OpenClaw 는 정책 단계를 여덟 개 깐다.** 프로필, 허용·차단, 소유자 전용, 그룹, 서브에이전트, 메시지 프로바이더, 샌드박스, 파일시스템 정책을 차례로 통과해야 도구가 실행된다. 여러 사람이 쓰는 환경을 상정한 설계다.

**Hermes 는 기본이 허용이다.** 대신 격리 장치를 여러 개 얹는다. 터미널 백엔드를 고르고, 승인 흐름을 붙이고, 게이트웨이 인증과 스킬 가드를 얹는다.

```
OpenClaw   막는 걸 설계로 푼다
Hermes     열어두고 조합으로 감싼다
```

둘 다 코드를 읽고 내 쪽으로 줄여서 가져왔다. 나는 혼자 쓰니까 OpenClaw 의 여덟 단계는 필요 없었고, Hermes 처럼 다 열어두기에는 캘린더와 가계부가 내 실제 데이터라 부담스러웠다.

## 내가 만든 것

### 판정하는 곳을 하나로 모았다

도구를 부르는 길이 여럿이다. 사용자와의 대화, 스킬 실행, 서브에이전트.

길마다 검사를 붙이면 하나 빠뜨리는 순간 뚫린다. 그래서 길을 하나로 좁혔다. 모든 도구 호출이 dispatcher 한 곳을 지나고 검사는 거기에만 있다.

### 세 단계로 거른다

```
1. 읽기냐          read 면 통과
2. 이름 규칙       allow · ask · deny
3. 인자 검사       ask 로 떨어진 것만
```

읽기를 먼저 빼는 이유는 단순하다. 파일 하나 읽고 검색 한 번 하는 것마다 확인을 받으면 대화가 안 굴러간다.

이름 규칙은 glob 패턴으로 쓴다.

```python
ApprovalRule("sheets.append", "ask"),
ApprovalRule("skill.create", "ask"),
ApprovalRule("mcp__*", "ask"),
```

시트 편집은 내 데이터가 바뀌니까 무엇을 어디에 넣는지 보여주고 묻는다. 외부 MCP 서버의 쓰기는 전부 확인을 받는다. 등록 안 된 도구는 쓰기로 친다. 모르는 건 막는 게 기본값이다.

세 번째 단계가 필요한 이유는 **이름만으로는 위험이 안 갈리기 때문**이다. 같은 도구라도 인자에 따라 다르다. `bash.exec` 로 `ls` 를 하는 것과 `rm -rf` 를 하는 것이 이름은 같다. 그래서 물어보기로 정해진 호출만 인자를 한 번 더 본다.

## 영구 허용 대신 대화 단위 허용

문제는 여기서 나왔다.

매번 물으면 사용하기 어렵다. 그래서 "항상 허용" 버튼을 만들고 승인을 저장해뒀다. 무엇을 허용했는지는 이렇게 남긴다.

```python
head = command.strip().split(None, 1)
return f"bash.exec:{head[0]}"
```

명령의 첫 단어만 남기고 나머지는 버린다. 사용자가 승인한 건 "이 명령어 한 줄" 이 아니라 "git 을 쓰는 것" 이라고 봤기 때문이다.

**이게 너무 넓었다.** `git` 을 한 번 허용하면 `git` 으로 시작하는 모든 명령이 열린다. 만료도 없다.

그리고 실제로 걸린 건 셸이 아니라 캘린더와 가계부였다. 등록이 잘못 들어가니 결국 매번 눈으로 봐야 했고, 그럴 거면 "항상 허용" 을 눌러둔 의미가 없었다.

하나 더 있다. 이 비서는 계속 고치는 중이다. 도구가 늘고 스킬이 바뀐다. **어제 허용한 게 오늘도 같은 걸 뜻하는지 확신할 수 없다.** 시스템이 안 바뀌어야 영구 승인이 말이 된다.

### 승인을 Redis 에 6시간

뭐가 성가셨는지 다시 따져봤다. 같은 걸 반복해서 묻는 건 대부분 **한 대화 안에서 같은 작업을 여러 번 할 때** 생긴다. 지출을 다섯 건 연달아 적을 때지, 어제 승인한 걸 오늘 또 묻는 게 아니었다.

그래서 영구 승인을 지우고 그 구간만 열어줬다. 허용은 그 대화 안에서만 유지되고, 6시간이 지나면 없어져서 다시 묻는다.

저장은 Redis 에 한다. 이 서버는 워커 네 개로 뜨는데, 승인을 프로세스 메모리에 담으면 워커마다 따로 기억한다. 새로고침해서 다른 워커에 붙는 순간 그 워커는 승인을 모른다. 스트리밍 버퍼로 쓰던 Redis 가 이미 있어서 같은 인스턴스를 쓴다. TTL 이 지나면 알아서 사라지니 정리 코드도 없다.

Redis 조회가 실패하면 승인 안 된 것으로 친다. 장애 때 문이 열리는 것보다 한 번 더 묻는 게 낫다.

## 아직 못 정한 것

지문의 단위가 맞는지 모르겠다. 명령의 첫 단어만 남기는 건 `git` 과 `rm` 을 가르기엔 충분하지만 `git push` 와 `git log` 를 못 가른다. 더 좁히면 묻는 횟수가 늘고, 넓히면 처음 버린 문제로 돌아간다.

무엇을 물을지 가르는 기준도 다시 봐야 한다. 지금은 **남에게 닿느냐**로 갈라놨다. 메일은 밖으로 나가니까 막고, 시트는 공유 문서일 수 있으니 묻는다. 캘린더와 메모리는 내 계정 안에서 끝나니까 안 묻고 통과시킨다. 테스트에도 그렇게 박아뒀다.

그런데 잘못 등록된 건 캘린더였다. 남에게 닿지 않는 건 맞는데, 대신 **내가 그 자리에서 못 알아챈다.** 밖으로 나가는 건 잘못돼도 바로 티가 나고, 내 캘린더는 나중에 열어보기 전까지 모른다.

기준을 바꿔야 하는지, 아니면 승인이 아니라 나중에 훑어볼 기록을 남기는 쪽이 맞는지 아직 못 정했다.
