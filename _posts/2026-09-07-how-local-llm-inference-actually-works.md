내 서버는 이 옵션으로 돌고 있다.

```bash
--gpu-memory-utilization 0.62
--kv-cache-dtype fp8
--max-model-len 65536
--enable-prefix-caching
--max-num-batched-tokens 8192
```

몇 달째 이대로인데 각 줄이 뭘 정하는지 제대로 몰랐다. 남의 설정을 보고 맞춰놓은 게 절반이다.

메모리를 뜯어본 글을 세 편 쓰고 나서도 그랬다. 무엇이 얼마인지는 재봤는데 **왜 그 값인지**는 안 봤다. 그래서 밑에서부터 다시 짚었다. 앞부분은 개념이고 뒤에 내 기계 숫자를 붙였다.

## 숫자를 저장하는 형식

### 파라미터 개수와 용량

모델 이름의 `35B` 는 **파라미터 350억 개**를 뜻한다. B 는 billion 이다. 용량이 아니다.

용량은 여기에 숫자 하나당 바이트를 곱해야 나온다.

```
파라미터 개수 × 하나당 바이트 = 용량

350억 × 2바이트 = 70 GB
350억 × 1바이트 = 35 GB
```

같은 35B 모델도 자료형에 따라 70GB 도 되고 35GB 도 된다.

### 비트를 세 몫으로 나눈다

부동소수점은 비트를 이렇게 쪼개 쓴다.

```
부호   양수냐 음수냐         1비트 고정
지수   얼마나 큰 수까지 되나   범위
가수   얼마나 촘촘하게 되나    정밀도
```

과학적 표기법과 같은 구조다. `3.4 × 10⁹` 에서 `3.4` 가 가수, `9` 가 지수다.

**가수만 바꾸면** 크기는 그대로고 정밀도가 달라진다. `3.14159` 냐 `3.14` 냐의 차이다.

**지수만 바꾸면** 정밀도는 그대로고 크기가 달라진다. `3.14 × 10³` 이냐 `3.14 × 10³⁸` 이냐다.

### 다섯 가지 형식

전체 비트 수가 정해져 있으니 한쪽을 늘리면 반드시 다른 쪽이 준다.

| | 부호 | 지수 | 가수 | 바이트 | 표현 최대 |
|---|---|---|---|---|---|
| fp32 | 1 | 8 | 23 | 4 | 3.4 × 10³⁸ |
| fp16 | 1 | 5 | 10 | 2 | 65,504 |
| bf16 | 1 | 8 | 7 | 2 | 3.4 × 10³⁸ |
| fp8 (E4M3) | 1 | 4 | 3 | 1 | 448 |
| fp8 (E5M2) | 1 | 5 | 2 | 1 | 57,344 |

이름 읽는 법은 단순하다. `fp` 는 floating point, `bf` 는 brain float, 뒤 숫자가 전체 비트 수다.

**bf16 은 지수를 fp32 와 똑같이 8비트로 잡았다.** 표현 범위가 fp32 와 같은 대신 가수 3비트를 잃었다.

그 3비트가 얼마나 차이나는지는 표현 가능한 값의 개수로 보면 분명하다.

```
3과 4 사이에 표현할 수 있는 값

fp16   512개    간격 0.00195
bf16    64개    간격 0.0156
```

`3.15` 를 저장하면 fp16 은 `3.150390625`, bf16 은 `3.15625` 가 된다. **bf16 이 8배 성기다.**

### bf16 이 표준이 된 이유

착각하기 쉬운데 **bf16 이 정밀해서 이긴 게 아니다.** 오히려 덜 정밀하다.

학습 중에는 아주 작은 값이 나온다. 기울기 `0.00001` 에 학습률 `0.0001` 을 곱하면 `0.000000001` 이 된다.

```
fp16   최소 표현값 0.00000006 보다 작다  →  0이 된다
bf16   범위가 넓어서 그냥 저장된다
```

**0이 되면 그 가중치는 안 고쳐진다.** 에러도 없이 조용히 학습을 멈춘다.

위쪽도 터진다. 어텐션 계산에서 값이 70,000 이 되면 fp16 은 무한대가 되고, 한 번 무한대가 나오면 그 뒤가 전부 NaN 이 되어 학습이 통째로 망가진다.

값이 조금 틀리는 건 견디는데 사라지거나 무한대가 되는 건 못 견딘다. 그래서 **정밀도를 내주고 범위를 산 쪽**이 이겼다.

fp16 으로 학습하려면 목발이 필요했다. 손실에 1024 같은 큰 수를 곱해 기울기를 범위 안으로 끌어올린 뒤 나중에 다시 나누는 방식이다. 곱하는 값을 학습 중에 계속 조정해야 하고 실패하기도 한다. bf16 은 이 장치가 통째로 필요 없다.

### fp16 과 bf8

**fp16 은 지금 거의 안 쓴다.** 크기도 속도도 bf16 과 같아서 바꿀 이유가 없고, bf16 모델의 값 중 65,504 를 넘는 게 있으면 무한대가 되어 오히려 위험하다. 지금 fp16 이 쓰이는 곳은 bf16 을 지원 안 하는 옛날 GPU 정도다.

**bf8 은 존재할 수 없다.** bf 의 정체성이 지수 8비트인데, 8비트 형식에 부호 1 + 지수 8을 넣으면 이미 9비트다. 가수에 남길 자리가 없다.

대신 `fp8 E5M2` 가 그 역할을 한다. 지수를 늘리고 정밀도를 더 버린 8비트 변형이다.

### 가중치만 내리느냐 계산까지 내리느냐

양자화에 축이 하나 더 있다. 저장한 것을 **꺼내서 계산할 때 무엇으로 하느냐**다.

```
W8A16   가중치 8비트로 저장, 계산은 16비트로 되돌려서 한다
W8A8    계산도 8비트로 한다
W4A16   가중치 4비트 (AWQ · GPTQ 가 보통 이것)
```

W 는 weight, A 는 activation 이다. **W8A16 은 메모리만 줄고, W8A8 은 연산까지 빨라진다.** 뒤에서 "fp8 로 내리면 두 배" 라고 쓴 건 W8A8 기준이다.

## 토큰과 토크나이저

### 토큰은 단어가 아니다

모델이 다루는 최소 단위가 토큰인데, 단어도 글자도 아니고 그 사이 어딘가다. 자주 나오는 조각은 통째로 하나가 되고 드문 조각은 여러 개로 쪼개진다.

**모든 계산과 비용이 토큰 개수로 매겨진다.** 컨텍스트 길이도 토큰이고 KV 캐시 크기도 토큰당으로 잰다.

### 한국어는 토큰을 더 먹는다

대부분의 토크나이저가 영어 데이터로 만들어져서, 같은 뜻이어도 **한국어가 영어보다 두세 배 토큰을 쓴다.**

프롬프트 예산을 잡을 때 이게 바로 걸린다. 시스템 프롬프트나 메모리 파일이 한글이면 예상보다 훨씬 커진다. 글자 수로 어림잡으면 틀린다.

## 모델 구조

### dense 와 MoE

자료형과는 **완전히 다른 축**이다. 헷갈리기 쉬운데 서로 무관하다.

```
축 1   구조     dense vs MoE     파라미터를 매번 다 쓰느냐
축 2   자료형   bf16 vs fp8      숫자 하나를 몇 바이트로 적느냐
```

dense 모델도 fp8 로 만들 수 있고 MoE 모델도 bf16 일 수 있다.

MoE 는 레이어마다 전문가가 여럿 있고 토큰마다 몇 명만 부른다.

```
토큰 A  →  라우터가 계산  →  3번, 17번 전문가 호출
토큰 B  →  라우터가 계산  →  5번, 41번 전문가 호출
```

### 메모리는 총 파라미터, 계산은 활성 파라미터

문제는 **누가 불릴지 그 토큰을 계산해봐야 안다**는 것이다. 다음 토큰에 다른 전문가가 불릴 수 있으니 전부 메모리에 올라가 있다.

```
메모리를 정하는 것    총 파라미터
계산량을 정하는 것    활성 파라미터
```

그래서 "총 35B, 활성 3B" 모델은 메모리를 35B 만큼 먹고 계산만 3B 만큼 한다. **MoE 가 아끼는 건 대역폭이지 용량이 아니다.**

이건 [기동 로그로 예산을 뜯어본 글](/posts/vllm-kv-cache-memory-breakdown/)에서 실제로 재봤다. 활성 3B 모델인데 가중치가 65.53 GiB 를 먹고 있었다.

## KV 캐시

### 학습에는 없다

이걸 몰라서 한참 헤맸다. **KV 캐시는 추론에만 있다.**

```
학습    문장 전체를 한 번에 계산한다. 저장해둘 이유가 없다
추론    토큰을 하나씩 만든다. 매번 앞의 것이 필요하다
```

한 번에 다 계산하면 그 자리에서 쓰고 버린다. 추론은 1,000번째 토큰을 만들려고 앞의 999개를 다시 계산할 수 없으니 저장해둔다.

**이래서 자료형을 정하는 사람이 다르다.**

```
가중치     학습으로 만들어져 파일에 저장돼 온다   →  파일이 정한다
KV 캐시    파일에 없다. 실행할 때 만든다        →  옵션으로 내가 정한다
```

가중치가 결정화된 지식이라면 KV 캐시는 지금 이 대화의 지식이다.

### 토큰당 크기

```
2 × 레이어 수 × KV 헤드 수 × 헤드 차원 × 자료형 바이트
```

맨 앞 2는 K와 V 두 개, 맨 뒤는 값 하나에 몇 바이트를 쓰느냐다. **자료형이 여기 직접 곱해진다.**

[hybrid attention 글](/posts/hybrid-attention-kv-cache-size/)에서 내 모델로 계산해보니 토큰당 40 KiB 가 나왔고 로그와 맞았다.

## 메모리는 순서대로 채워진다

vLLM 은 기동할 때 정해진 비율만큼 통째로 예약하고 그 안에서 스스로 나눠 쓴다. 순서가 정해져 있다.

```
① 가중치가 먼저 들어간다          모델을 정하는 순간 확정
② 활성화와 런타임 몫을 뺀다        더미 요청을 돌려 최대치를 잰다
③ 남은 걸 KV 캐시가 전부 가진다
```

**활성화 메모리**는 레이어를 지날 때마다 나오는 임시 계산 결과다. 다음 레이어로 넘기고 버리니 계속 쌓이지는 않는다. 대신 순간 최대치가 문제다. vLLM 이 기동에 시간을 오래 쓰는 이유 중 하나가 이걸 재기 때문이다.

여기서 중요한 게 나온다. **KV 캐시 크기는 내가 정하는 게 아니라 남은 것이다.**

```
모델을 키우면    가중치가 더 먹는다  →  KV 캐시가 줄고 컨텍스트가 짧아진다
양자화하면       가중치가 작아진다   →  KV 캐시가 늘어난다
```

둘이 같은 예산을 나눠 쓰는데 가중치가 먼저 먹는 구조다.

## prefill 과 decode

### 두 단계의 성격이 반대다

이걸 모르면 속도 얘기가 반쪽이 된다. 답변 하나를 만드는 일이 두 단계로 갈린다.

```
prefill   프롬프트 전체를 한 번에 읽고 계산한다   →  연산 병목
decode    답변 토큰을 하나씩 뽑는다              →  메모리 병목
```

**prefill** 은 토큰 수천 개를 동시에 계산하니 GPU 가 꽉 찬다. 여기서는 연산 성능이 한계를 정한다.

**decode** 는 토큰 하나씩이라 동시에 계산할 게 없다. 대신 매번 가중치와 KV 캐시를 전부 읽어야 한다. GPU 코어 대부분이 놀고 메모리에서 꺼내오는 데 시간이 다 간다.

```
읽기 ████████████████████
계산 ██
```

decode 에서는 **연산 성능을 두 배로 올려도 속도가 안 변한다.** 그래서 상한이 이렇게 나온다.

```
매 토큰 읽는 양 ÷ 메모리 대역폭 = 초당 몇 번
```

여기서 자료형이 다시 등장한다. **가중치를 fp8 로 내리면 읽을 바이트가 반이 되고, 계산은 어차피 놀고 있으니 그게 그대로 속도가 된다.**

그리고 KV 캐시도 매 토큰 전부 읽는다. 대화가 길어질수록 읽을 게 늘어서 같은 모델이어도 뒤로 갈수록 느려진다.

### TTFT 와 TPOT

재려면 이름부터 알아야 한다. 셋으로 나눠 본다.

```
TTFT         첫 글자가 나올 때까지 걸린 시간      prefill 이 정한다
TPOT         그 뒤 토큰 하나당 시간             decode 가 정한다
throughput   서버 전체가 초당 처리하는 토큰 수
```

**셋이 서로 맞바꾸는 관계다.** 배치를 키우면 throughput 이 오르고 TPOT 이 나빠진다. "빠르다" 는 말이 셋 중 어느 쪽인지에 따라 완전히 다른 얘기가 된다.

프롬프트가 크면 TTFT 가 지배적이 된다. 도구 정의가 2만 토큰이면 답변 500 토큰 뽑는 시간보다 프롬프트 읽는 시간이 길어질 수 있다.

### chunked prefill

프롬프트가 아주 크면 prefill 을 한 번에 못 한다. 활성화 메모리가 순간적으로 튀기 때문이다.

그래서 프롬프트를 조각내 여러 스텝에 나눠 처리한다. 이렇게 하면 긴 프롬프트가 들어와도 다른 요청의 decode 가 멈추지 않는다. **한 사람의 긴 프롬프트가 나머지를 세우는 걸 막는 장치다.**

### 토큰을 여러 개씩 뽑는 방법

decode 가 메모리에 묶여 있다는 건, **한 번 읽을 때 토큰을 여러 개 뽑으면 이득**이라는 뜻이다.

작은 모델이나 별도 예측 층으로 다음 토큰 여러 개를 미리 찍어보고, 본 모델이 한 번에 검증해서 맞은 만큼 건너뛴다. 이걸 speculative decoding 이라 한다.

모델 자체에 그 예측 층을 넣어둔 것을 **MTP**(Multi-Token Prediction)라고 하고, `config.json` 의 `mtp_num_hidden_layers` 로 확인할 수 있다.

## 요청을 묶는 방식

vLLM 이 알려진 이유가 여기 있다.

```
정적 배칭    요청 8개를 모아 같이 시작하고 다 끝날 때까지 기다린다
연속 배칭    끝난 요청 자리에 새 요청을 바로 넣는다
```

정적 배칭은 짧은 요청이 긴 요청을 기다린다. 연속 배칭은 그 낭비를 없앤다.

`--max-num-batched-tokens` 가 한 스텝에서 처리할 토큰 상한을 정한다. 이 값이 크면 처리량이 오르고 개별 응답이 늦어진다.

**GPU 는 원래 처리량 기계다.** 일을 몰아줘야 좋아한다. 그런데 챗봇처럼 한 사람을 기다리게 하지 않으려면 배치를 작게 가져가야 한다. 처리량과 지연시간이 여기서 정면으로 부딪힌다.

배경에서 도는 에이전트라면 답이 달라진다. 기다리는 사람이 없으니 배치를 키워도 된다.

## 무엇을 8비트로 내릴 것인가

### KV 캐시가 먼저인 이유

가중치와 KV 캐시 둘 다 내릴 수 있는데 위험도가 다르다. **KV 캐시가 훨씬 안전하다.**

**여기만 계속 커진다.** 가중치를 반으로 줄이면 빈 공간이 생기고 쓰려면 다시 배분해야 한다. KV 캐시를 반으로 줄이면 **담기는 토큰이 즉시 두 배**가 된다. 그 토큰 수가 곧 대화 길이와 동시 처리 수다.

**어텐션이 오차에 관대하다.** 어텐션은 점수를 softmax 로 비율로 바꾸고 그 비율로 값들을 가중 평균한다. 수천 개를 평균하니 개별 오차가 서로 상쇄되고, softmax 는 절대값이 아니라 상대적 크기만 본다.

가중치는 반대다. 레이어를 순서대로 지나면서 **앞 레이어의 오차가 다음 레이어의 입력**이 된다. 그리고 모든 토큰의 모든 계산에 반복해서 쓰인다.

```
KV 캐시 오차    설문 1,000명 중 몇 명이 잘못 답한 것. 평균에 묻힌다
가중치 오차     저울 자체가 틀어진 것. 재는 것마다 틀린다
```

### 8비트를 어떻게 나눌까

앞의 얘기와 헷갈리기 쉬운데 **다른 질문이다.**

```
질문 A   가중치와 KV 캐시 중 어디를 먼저 내릴까      →  KV 캐시
질문 B   그 8비트를 범위와 정밀도로 어떻게 나눌까     →  정밀도
```

KV 값은 정규화를 지나와서 크기가 고만고만하다. 극단으로 튀지 않으니 **범위는 남아돌고 부족한 건 정밀도다.**

그래서 범위를 늘린 `E5M2` 가 아니라 정밀도를 늘린 `E4M3` 을 쓴다. **bf 계열의 발상은 학습에서 맞는 답이고 KV 캐시에서는 틀린 답이다.**

### 양자화가 실제로 하는 일

저장 형식만 바꾸는 단순 변환이 아니다.

fp8 E4M3 은 최대 448 까지인데 실제 가중치는 대략 `-0.05 ~ 0.05` 범위다. 그대로 넣으면 **0 근처에서 다 뭉개진다.** 눈금이 그 좁은 구간에서는 너무 성기다.

그래서 배율을 같이 저장한다.

```
① 값에 배율을 곱해 fp8 이 잘 표현하는 구간으로 옮긴다
     -0.05 ~ 0.05   ×100 →   -5 ~ 5
② 그 상태로 fp8 에 저장한다
③ 쓸 때 다시 100 으로 나눈다
```

**배율을 얼마로 잡을지가 양자화 기술이다.** 층마다 값 분포가 다르니 배율도 다르게 잡는다. 실제로는 데이터를 흘려보내며 각 층의 분포를 관찰하고, 층마다 배율을 정하고, 임베딩이나 정규화처럼 민감한 층은 원래 정밀도로 남긴다.

공식 fp8 버전 크기가 정확히 절반이 아닌 것도 마지막 항목 때문이다. 이 배율 정보가 `config.json` 의 `quantization_config` 에 담긴다. 없으면 값을 복원할 수 없다.

**4비트에서는 범위를 다르게 해결한다.** 비트가 적으면 지수에 줄 여유가 없다. 대신 값 32개 묶음마다 배율 하나를 공유하는 방식으로 범위를 확보한다. NVFP4 나 MXFP4 가 이 방식이다.

## 모델 이름 읽는 법

이름에 붙는 자료형은 **학습 방법이 아니라 저장 형식**이다.

```
Qwen3.6  -  35B  -  A3B  -  FP8
   │         │       │       └ 저장 형식
   │         │       └ 구조 (활성 3B)
   │         └ 총 파라미터
   └ 계열과 버전
```

학습은 거의 다 bf16 으로 한다. `-FP8` 이 붙은 건 원본을 받아 저장 형식만 바꿔 다시 올린 것이다. 변환만 하는 작업이라 GPU 몇 시간이면 된다.

| 접미사 | 뜻 |
|---|---|
| 없음 | 원본. 보통 bf16 |
| `-FP8` | 8비트로 변환 |
| `-AWQ` `-GPTQ` | 4비트, 각각 다른 방식 |
| `-NVFP4` | NVIDIA 4비트 형식 |
| `-GGUF` | llama.cpp 용 파일 형식 |
| `-MLX` | Apple Silicon 용 |

확실하게 구별하려면 `config.json` 을 보면 된다. 양자화된 모델에만 `quantization_config` 가 있다.

## 내 기계에서는

DGX Spark 다. 통합 메모리 128GB, 대역폭 273GB/s. 모델은 총 35B 에 활성 3B 인 MoE 다.

`config.json` 을 열어보니 이랬다.

```
num_experts            256
num_experts_per_tok      8
num_hidden_layers       40
num_key_value_heads      2
head_dim               256
full_attention_interval  4
mtp_num_hidden_layers    1
```

**전문가 256명 중 매 토큰 8명, 3.1% 다.** 나머지 97%는 그 토큰에서 놀지만 메모리에는 있다. 40레이어 중 10개만 full attention 이고 나머지 30개는 linear attention 이다.

맨 아랫줄이 눈에 걸렸다. **MTP 층이 있는데 안 쓰고 있다.**

메모리는 이렇게 나뉜다.

```
128 GB       기계 전체
 └ 76.4 GiB   vLLM 이 예약한 것 (--gpu-memory-utilization 0.62)
    ├ 65.53    가중치            92%
    ├  6.08    KV 캐시            8%
    └  4.8     활성화 + 런타임
```

**128GB 중 76GiB 만 쓰는 건 내가 비워둔 것이다.** 같은 GPU 에서 AlphaFold2 와 ProteinMPNN 이 같이 돈다. 이 기계를 산 이유의 절반이 저 계산 도구들이었으니 LLM 이 다 먹으면 안 됐다. 다만 얼마를 비워야 맞는지는 재본 적이 없다.

자료형은 이렇게 갈려 있었다.

```
가중치     bf16    안 정했다. 모델 파일이 그렇다
KV 캐시    fp8     --kv-cache-dtype fp8 로 내가 정했다
```

**작은 쪽은 이미 줄였고 큰 쪽은 안 줄인 상태다.**

속도 쪽에서도 계산이 맞아떨어졌다. 전에 27B dense 모델을 올렸다가 접었는데, 그때는 그냥 느리다고만 생각했다.

| 모델 | 매 토큰 읽는 양 | 계산상 상한 | 실측 |
|---|---|---|---|
| 27B dense | 54 GB | 초당 5회 | 약 10 tok/s |
| 활성 3B MoE | 6 GB | 초당 45회 | 약 30~50 tok/s |

**모델이 나빠서가 아니라 읽을 게 아홉 배라서 느렸다.** 273GB/s 로 나눈 상한과 실측이 같은 자리에 있다.

다만 이 실측값은 조건을 안 적어뒀다. 프롬프트 길이도 동시 요청 수도 기록이 없어서 다시 재는 게 맞다.

## 다음에 재볼 것

찾아보니 지금 쓰는 모델의 다음 버전과 4비트 판이 나와 있었다.

| | 크기 | 자료형 | 공개 |
|---|---|---|---|
| 지금 쓰는 것 | 70.2 GB | bf16 | 2026-06 |
| 같은 버전 fp8 | 37.7 GB | fp8 | |
| 다음 버전 | 71.9 GB | bf16 | 2026-08 |
| 다음 버전 4비트 | **23.4 GB** | NVFP4 | |

**4비트 판이 23.4 GB 다. 지금의 3분의 1이다.** 다운로드 수도 fp8 판보다 많다. GB10 은 Blackwell 이라 4비트 연산을 하드웨어로 지원하니 이 조합을 쓰라고 만들어둔 셈이다.

가중치가 23 GB 로 내려가면 두 가지가 동시에 온다.

```
KV 캐시로 남는 것   6.08 GiB  →  약 45 GiB
매 토큰 읽는 양     6 GB      →  1.5 GB
```

이론상 네 배 빠르고 컨텍스트도 훨씬 길어진다. 대신 품질이 얼마나 깎이는지는 모른다.

지금 값들이 최선인지는 모른다. 넷 다 다른 값과 비교해본 적이 없다.

```
가중치를 4비트로 내리면    얼마나 빨라지고 도구 호출이 얼마나 나빠지나
MTP 를 켜면              얼마나 빨라지나
메모리 비율을 올리면       바이오 도구가 버티나
컨텍스트를 줄이면         실제로 뭐가 막히나
```

개념은 이제 알겠는데 어느 쪽이 나은지는 재봐야 안다. TTFT 와 TPOT 를 나눠서 재는 것부터 시작해야겠다.
